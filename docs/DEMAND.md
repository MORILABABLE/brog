## 0. 結論（先に4つ）

1. **主題の選び方に、外の需要が一度も入っていなかった。** シリーズ候補
   （`series-candidates.ts`）は「2社以上で同時に終わる束」という**在庫の中の偶然**で、
   読者がいまその作品を探しているかどうかを見ていない。
2. **需要と在庫を両側から挟むと、週に30件前後の候補が出る。**
   7日ぶんの話題3,053語 × 在庫3,738作品で **32件**。
   うち「いつまで観られるか」に答えられるものが **7件**。
3. **4つ目の軸が要る — 収益導線。** 話題 × 期限だけで並べると先頭が
   Netflix 単独の作品になる。Netflix と Disney+ には日本にアフィリエイトが無いので、
   **書いても収益にならない候補が最上位に来る。**
   だから**スコアを1つの数字に畳まず、軸を並べて出す**。
4. **流入の山と収益の山が別の場所にある。**
   検索流入の最大は `/posts/harry-potter`（表示324・クリック31）。
   外部リンクが実際に踏まれているのは `/works/10534`（スマホ7クリック）。
   **前者は外部クリックの上位に出てこない。** → 6節の未着手はここから出ている。

## 1. 何が無かったか

記事の主題はこれまで**在庫の側からしか決まっていなかった**。

| いままで | 見ているもの |
|---|---|
| 月次記事（`leaving` / `arrivals`） | 今月そのサービスで何が動いたか |
| シリーズ候補（`series-candidates.ts`） | 2社以上で同時に終わる束があるか |
| 書き直し（`--refresh`） | 公開済みの記事の事実が古くなっていないか |

どれも自前の観測だけで閉じている。**読者がいま何を探しているかは、どこにも入っていない。**

逆に、話題だけを見て主題を決めるのも間違い。当サイトが書けるのは**答えを持っている作品だけ**
（[STOCK.md](./STOCK.md) 4節「観測データが1行も入らない記事は書かない」）。

**だから両側から挟む。話題があり、かつ答えを持っているものだけを候補にする。**

## 2. 取得元（3つ・実測と規約）

| 取得元 | 何が返るか | 規約 | 役割 |
|---|---|---|---|
| **Wikipedia 日本語版 pageviews** | 日次 **top 1000**。7日で3,053語 | 公式API・無料・キー不要。連絡先の分かる User-Agent が要る | **発見**。いま読まれている作品を拾う |
| **Google トレンド RSS**（`geo=JP`） | **1日10語**。`ロッキン オン ソニック 2027` `藤青雲` など | `robots.txt` が拒否するのは `/explore?` と `/trends/explore?` の2つだけ。**`/trending/rss` は許可** | 補助。ニュース・人物が多数で単独では素材にならない |
| **Google サジェスト** | その語に付いている問い（`オッペンハイマー 配信終了`） | 公式APIではない。**候補が確定してから上位だけ**に叩く（0.4秒間隔） | **確認**。どの問いが付いているか＝どの記事が答えになるか |

> ★ **サジェストは発見に使えない。** 入力語（シード）が要るので、
> これで新しい主題は見つからない。[KEYWORDS.md](./KEYWORDS.md) 冒頭の★と同じ区別。

> ★ **旧 `/trends/trendingsearches/daily/rss` は 404**（同日実測）。
> 古い記事に載っているURLを使わないこと。

> 🔴 **需要の数字を記事に書かない。** Wikipedia の閲覧数を「人気ランキング」として
> 記事に載せると、**当サイトの観測ではないものを当サイトの主張として出す**ことになる。
> 使うのは主題を選ぶところまで。実装でも `DemandSignal` を `ChangeEvent` と型ごと分けてある。

## 3. 突き合わせと、誤爆の止め方

素の突き合わせは**85件**返り、`イルカ` `スイス` `ひまわり` `ジョン・レノン` のような
「作品名と同じ文字列だが、話題は作品ではないもの」が混ざっていた。歯止めは5つ。

| # | 歯止め | 効き |
|---|---|---|
| 1 | **観測（`data/events`）のある作品だけを在庫とする** | いちばん効いた。**85 → 32件**。`titles.json` や `unext-catalog` を混ぜると「当たっても書けることが1行も無い候補」が並ぶ |
| 2 | 正規化して**4文字未満を捨てる** | `イルカ` `トロイ` の類 |
| 3 | **人物名を捨てる**（`cast.json` / `directors.json` の日本語表記 10,539件） | [KEYWORDS.md](./KEYWORDS.md) 4節「人物軸は記事にしない」の機械側 |
| 4 | 前方一致は**3作以上 かつ 2社以上の束**のときだけ | 下の★ |
| 5 | 人が捨てた語（`data/demand-ng.json`） | 上の4つを通り抜けたものだけを手で足す |

> ★ **束に「2社以上」を課している理由は2つある。**
> 1つは `series-candidates.ts` と同じで、1社に閉じた束はそのサービスの月次記事が扱えること。
> もう1つが実測で見つかったほう —
> **`GACKT` `Juice=Juice` `モーニング娘。` `FUNKY MONKEY BΛBY'S` `Taka` の5件が、
> いずれも U-NEXT のライブ映像・舞台番組の束に前方一致していた。**
> 話題の中身は人物・グループであって、その映像作品ではない。
> `data/cast.json` に音楽アーティストは入っていないので、3の歯止めでは落ちない。
>
> **これは近似であって正しい判定ではない。** 1社で閉じた良い束を落とすことがある。
> 落ちて困るものが出たら `MIN_BUNDLE_SERVICES` を 1 に戻し、`demand-ng.json` 側で捌く。

**「答え」は2種類しかない。** ここが記事の型に直結する。

```
until … 未来の終了予定がある     → 「いつまで観られるか」に答えられる
where … 見放題に入った観測がある → 「どこで観られるか」に答えられる
```

`upcoming`（配信予定）は候補にしない。**個別作品の配信開始日は予測しないと決めている**
（[KEYWORDS.md](./KEYWORDS.md) 4節）。観測として持っていても、記事の答えにはしない。

## 4. 貯め方 — 取得元で変えてある

| 取得元 | 貯めるもの | なぜ |
|---|---|---|
| Google トレンド | **全行** | 過去日を取り直す口が無い。**取り逃すと戻せない。** 1日10語で安い |
| Wikipedia | **在庫に当たった語だけ** | 何年前の日付でも同じAPIで返る。1日1000行を全部抱えると**月3.6MB** |

> ★ **Wikipedia の999件を捨てているように見えるが、捨てていない。**
> 必要になったら同じ日付を投げ直せばよい。「復元できるものは貯めない」という判断で、
> `data/events` とは逆（あちらは配信APIが過去を返さないので、観測した瞬間に貯めるしかない）。

貯める先は `data/demand/YYYY-MM.jsonl`。同じ日・同じ語は1行に畳み、
数字が動いていたら**大きいほう（その日のピーク）**を残す。初回の実行で146行。

**何のために貯めるか。** その日の候補を出すだけなら要らない。あとから測るため。

- 話題はどれくらい続くか（1日で消えるのか、2週間残るのか）
- 話題が立ってから見放題が終わるまで、どれくらいあるか
- 去年の同じ時期に何が話題だったか（季節ものの先回り）

どれも [KEYWORDS.md](./KEYWORDS.md) 案2『観測レポート』が待っている素材と同じ性質で、
**1日ぶんでは何も言えず、半年貯めると言えるようになる。**

## 5. 使い方

```
npm run demand                 取得して貯めて、候補を出す（直近7日）
npm run demand -- --days 14    突き合わせに使う日数
npm run demand -- --no-fetch   取得しない（貯めたぶんだけ・通信なし）
npm run demand -- --suggest    上位10件に語形の確認をかける
npm run demand -- --all        落とした語を理由つきで出す（切り分け用）
npm run demand -- --json       機械可読
npm run demand -- --trend "ハリー・ポッターシリーズ"
                               1つの記事の日次推移（**第二波の観測**・下の★）
```

> ★ **`--trend` は「話題が戻ってきたか」を測る口**（2026-09-15 追加）。
> 日次 top 1000 に入らない語も追える（Wikipedia の per-article API）。
> 判定は「直近7日 ÷ その前7日」だけで、統計的な検定はしない。
> 使いどころは [FUNNEL.md 9-3](./FUNNEL.md) の「第二波を測る口」。

> ★ **候補には「記事あり ＜slug＞」が付く。** 既に扱った作品でも候補から外さない。
> 話題が立っているのに記事が古い状態がいちばん取りこぼしやすく、外すと
> **「書き直す」「前に出す」という手が一覧から消える。**

**API課金なし。** 無料の公開APIだけで、Streaming Availability API も LLM も呼ばない。

出力はこの形（2026-09-15 実測）。

```
  [いつまで] オッペンハイマー  話題 2,572／3日  在庫 2作  prime-video,netflix  終了 9月27日（あと12日）  導線 Amazon
      オッペンハイマー / オッペンハイマー
  [どこで  ] VIVANT  話題 45,561／7日  在庫 1作  disney-plus,prime-video  導線 Amazon
      VIVANT
```

**在庫の側は週2回（火・金 JST）しか動かない。需要の側は日次で動く。**
ずれていて構わない。話題が先に立ち、在庫は次の収集で追いつく。
収集の直後に実行すると当たりが増える。

| 実装 | どこ |
|---|---|
| 需要の取得 | `pipeline/sources/demand/`（`wikipedia-pageviews.ts` / `google-trends.ts` / `google-suggest.ts`） |
| 貯める | `pipeline/core/demand-store.ts` → `data/demand/YYYY-MM.jsonl` |
| 突き合わせ | `pipeline/core/demand-match.ts` |
| コマンド | `pipeline/cli/demand.ts`（`npm run demand`） |
| 人が捨てた語 | `data/demand-ng.json` |

## 6. 未着手 — 出口（ここからが次の作業）

**候補は出るようになった。候補を何にするかは決まっていない。**

### 6-1. 判断の材料（2026-09-15 実測）

| | 実測 |
|---|---|
| スマホ比率 | **検索流入の79.5%**（mobile 186 / desktop 39 / tablet 9・56日）。外部リンククリックは**71%がスマホ**（17/24） |
| 最大の流入 | `/posts/harry-potter` … 表示324・クリック31。**サイト全体の表示23%・クリック22%を1本で占める** |
| 最大の収益 | `/works/10534`（作品ページ・スマホ）… **外部クリック7**。全24クリック中の7 |
| 引っかかり | `/posts/harry-potter` は**38PVで次のページへ1本も出ていない**（`npm run analytics` の指摘1位）。外部クリックの上位にも出てこない |
| 収益導線 | **Amazon（prime-video）と U-NEXT のみ。** Netflix / Disney+ / Apple TV+ には日本にアフィリエイトが無い |

> ★ desktop の Direct 74セッションには**運営者自身の閲覧が混ざっている**と見てよい
> （ランディングの最上位が `/`）。スマホ比率は、実際にはこの数字より高い可能性がある。

### 6-2. 出口の案（3つ）

| 在庫の形 | 出口 | 状態 |
|---|---|---|
| 3作以上・2社以上の束になる | **`series` 記事**（既存の記事タイプに主題を供給するだけ） | 未着手。追加実装はほぼ不要 |
| 単発だが期限が近い・導線あり | **作品ページを押し出す**（記事を書かない） | 未着手。どこに出すか未定 |
| 同じ月に複数集まる | **月次 `leaving` 記事の表を話題順に並べる** | 未着手。記事を増やさずスマホの1画面目を変えられる |

> 🔴 **単発の話題作品に新しい記事タイプを作らないこと。**
> 「『リコリス・リコイル』の見放題はいつまで」という記事は `/works/14281` とほぼ同じ内容になり、
> **自サイト内で食い合う。** 作品ページを持っていることがこのサイトの強みのほう。

### 6-3. 決まっていない2点

1. **出口の重心。** ①記事生成（束になるものだけ・月2〜3本）を主にするか、
   ②既存ページの押し出し（トップの「いま話題」棚・月次記事の並べ替え）を主にするか。
   **実測は②に収益があると言っているが、①のほうが新規流入は増える。**
2. **収益導線の重み。** 強くすると U-NEXT 偏重になり（提携状況は [AFFILIATE.md](./AFFILIATE.md)）、
   弱くすると Netflix の話題作が並ぶ。
   **いまは重みを付けず、軸を並べて表示するだけにしてある**（`demand-match.ts` の
   `AFFILIATE_SERVICES` の★）。数式に畳むのは、出口を決めてからでよい。

### 6-4. ~~先にやること~~ — ✅ 2026-09-15 に実施（[FUNNEL.md 9-3](./FUNNEL.md)）

**分析の結果、原因は記事の本文に他の記事へのリンクが1本も無かったこと**（10本すべてが
1200px未満で消える右の枠の中。読者の97%はスマホ）。同日に表の直前・直後へ
「次の一手」を差し込む手を入れた（`plugins/rehype-next-step.ts`）。
**実測・位置・残りの宿題は [FUNNEL.md 9-3](./FUNNEL.md)。**

当初この節に挙げていた着眼点は次の4つで、1と2が当たりだった:

- 記事内のどこに内部リンクがあるか（38PVで0本は、**リンクが無いか、見える位置に無いか**）
- CTA の出方。この記事の作品は **Netflix と U-NEXT** で、
  **Amazon の枠が出る条件を満たしていない可能性がある**（`AfbCta.astro` / `AmazonCta.astro` の判定）
- スマホでの1画面目に何が入っているか（[FUNNEL.md](./FUNNEL.md) 5-3 の「表を最初の1画面に」）
- Search Console のクエリ … `ハリーポッター 配信終了` `ハリポタ ネトフリ 配信 終了` `ハリーポッター サブスク`。
  **読者は略称で検索しているが、タイトルの決まりは略称を禁じている**（[KEYWORDS.md](./KEYWORDS.md) 5節）

## 7. この設計が外れていたと分かる形

**測り方を先に決めておく。**

| 主張 | 外れの兆候 |
|---|---|
| 需要 × 在庫で週30件出る | 収集が進んでも候補が10件を割り続ける → 在庫（観測のある3,738作品）が話題の作品と重ならない＝**当サイトの在庫が古い作品に偏っている** |
| 話題は主題選びに効く | 需要から選んだ主題の記事が、在庫から選んだ主題の記事より **90日後の表示回数で下回る** |
| 束の「2社以上」は妥当 | 落とした束の中に、あとから見て書くべきだったものが繰り返し出る → `MIN_BUNDLE_SERVICES` を 1 に戻す |
| 数字を記事に書かない | （破ったら分かる。`verify.ts` では止められないので**人の規律**） |

> ★ **いちばん外れやすいのは「Wikipedia の閲覧数＝配信の需要」という置き換え。**
> 実際には放送・訃報・受賞でも跳ねる。`VIVANT` の45,561は**地上波の再放送**の可能性が高く、
> 「配信で観たい人が4万人いる」ではない。
> サジェスト（`--suggest`）で問いの型を確かめてから主題にすること。
