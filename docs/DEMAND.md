## 0. 結論（先に6つ）

1. **主題の選び方に、外の需要が一度も入っていなかった。** シリーズ候補
   （`series-candidates.ts`）は「2社以上で同時に終わる束」という**在庫の中の偶然**で、
   読者がいまその作品を探しているかどうかを見ていない。
2. **需要と在庫を両側から挟むと、週に30件前後の候補が出る。**
   7日ぶんの話題3,053語 × 在庫3,738作品で **32件**。
   うち「いつまで観られるか」に答えられるものが **7件**。
3. **4つ目の軸が要る — 収益導線。** 話題 × 期限だけで並べると先頭が
   Netflix 単独の作品になる。Netflix と Disney+ には日本にアフィリエイトが無いので、
   **書いても収益にならない候補が最上位に来る。**
   だから**スコアを1つの数字に畳まず、軸を並べて出す**。
4. **流入の山と収益の山が別の場所にある。**
   検索流入の最大は `/posts/harry-potter`（表示324・クリック31）。
   外部リンクが実際に踏まれているのは `/works/10534`（スマホ7クリック）。
   **前者は外部クリックの上位に出てこない。**
5. **（2026-09-16 追記）「記事が無ければ書く」という枝は、ほとんど発火しない。**
   候補42件のうち束は1件だけで、記事の無い15件は**全部が単発作品**。
   単発の受け皿は作品ページで、それはもう存在する。
   **自動で動かす価値があるのは「押し出し」のほう。** → 6-0。
6. **（同）需要の取得元に Search Console を足した。**
   当サイト最大の需要（`五等分の花嫁 netflix 配信終了`・232表示・10.1位）が、
   Wikipedia だけを見ていたときは**候補に一度も出なかった**。 → 2節★。

## 1. 何が無かったか

記事の主題はこれまで**在庫の側からしか決まっていなかった**。

| いままで | 見ているもの |
|---|---|
| 月次記事（`leaving` / `arrivals`） | 今月そのサービスで何が動いたか |
| シリーズ候補（`series-candidates.ts`） | 2社以上で同時に終わる束があるか |
| 書き直し（`--refresh`） | 公開済みの記事の事実が古くなっていないか |

どれも自前の観測だけで閉じている。**読者がいま何を探しているかは、どこにも入っていない。**

逆に、話題だけを見て主題を決めるのも間違い。当サイトが書けるのは**答えを持っている作品だけ**
（[STOCK.md](./STOCK.md) 4節「観測データが1行も入らない記事は書かない」）。

**だから両側から挟む。話題があり、かつ答えを持っているものだけを候補にする。**

## 2. 取得元（4つ・実測と規約）

| 取得元 | 何が返るか | 規約 | 役割 |
|---|---|---|---|
| **Wikipedia 日本語版 pageviews** | 日次 **top 1000**。7日で3,053語 | 公式API・無料・キー不要。連絡先の分かる User-Agent が要る | **発見**。いま読まれている作品を拾う |
| **Google トレンド RSS**（`geo=JP`） | **1日10語**。`ロッキン オン ソニック 2027` `藤青雲` など | `robots.txt` が拒否するのは `/explore?` と `/trends/explore?` の2つだけ。**`/trending/rss` は許可** | 補助。ニュース・人物が多数で単独では素材にならない |
| **Google サジェスト** | その語に付いている問い（`オッペンハイマー 配信終了`） | 公式APIではない。**候補が確定してから上位だけ**に叩く（0.4秒間隔） | **確認**。どの問いが付いているか＝どの記事が答えになるか |
| **Search Console**（2026-09-16 追加） | **当サイトが実際に出た検索語**と、その表示回数・順位 | 取り込みは `queries.yml`（週1回）。ここは `data/search-queries.json` を**読むだけ**で通信しない | **本命**。下の★ |

> ★ **Search Console を足した理由 —「当サイト最大の需要が候補に一度も出なかった」。**
>
>     「五等分の花嫁 netflix 配信終了」（表記ゆれ4語の合計・GSC 28日）
>       表示 232 ・ クリック 1 ・ 平均 10.1位 ← **サイト全体の表示の8%を1作品が占める**
>       `data/events` には観測がある（netflix・2026-09-09 に removed）
>
> 答えを持っているのに10位で、誰も踏んでいない。それでも候補に出なかったのは、
> この作品が Wikipedia の日次 top 1000 に入らないからで、**需要が無いからではない。**
> 逆向きのずれも同じ日に出ている —
> Wikipedia 最大の `VIVANT 45,561` は7節★が疑っているとおり**地上波の再放送**由来の可能性が高い。
>
> **Wikipedia は「世の中で何が読まれているか」、GSC は「当サイトが何で見られているか」。**
> 実測で 6〜20位・表示3以上が **41語・549表示（サイト全体の19%）でクリック6**。
> **順位を1つ上げれば取れる需要**がここにある。実装は `pipeline/core/demand-queries.ts`。

> 🔴 **数字を1つのスコアに畳まない。** Wikipedia は万の桁、GSC は十〜百の桁で物差しが違う。
> 畳むと GSC 側が必ず負ける（`五等分の花嫁 232` 対 `VIVANT 45,561`）。
> `DemandCandidate` は `peak`（外の話題）と `search`（当サイトの実測）を**別のフィールドで持つ**。

> ★ **サジェストは発見に使えない。** 入力語（シード）が要るので、
> これで新しい主題は見つからない。[KEYWORDS.md](./KEYWORDS.md) 冒頭の★と同じ区別。

> ★ **旧 `/trends/trendingsearches/daily/rss` は 404**（同日実測）。
> 古い記事に載っているURLを使わないこと。

> 🔴 **需要の数字を記事に書かない。** Wikipedia の閲覧数を「人気ランキング」として
> 記事に載せると、**当サイトの観測ではないものを当サイトの主張として出す**ことになる。
> 使うのは主題を選ぶところまで。実装でも `DemandSignal` を `ChangeEvent` と型ごと分けてある。

## 3. 突き合わせと、誤爆の止め方

素の突き合わせは**85件**返り、`イルカ` `スイス` `ひまわり` `ジョン・レノン` のような
「作品名と同じ文字列だが、話題は作品ではないもの」が混ざっていた。歯止めは5つ。

| # | 歯止め | 効き |
|---|---|---|
| 1 | **観測（`data/events`）のある作品だけを在庫とする** | いちばん効いた。**85 → 32件**。`titles.json` や `unext-catalog` を混ぜると「当たっても書けることが1行も無い候補」が並ぶ |
| 2 | 正規化して**4文字未満を捨てる** | `イルカ` `トロイ` の類 |
| 3 | **人物名を捨てる**（`cast.json` / `directors.json` の日本語表記 10,539件） | [KEYWORDS.md](./KEYWORDS.md) 4節「人物軸は記事にしない」の機械側 |
| 4 | 前方一致は**3作以上 かつ 2社以上の束**のときだけ | 下の★ |
| 5 | 人が捨てた語（`data/demand-ng.json`） | 上の4つを通り抜けたものだけを手で足す |

> ★ **束に「2社以上」を課している理由は2つある。**
> 1つは `series-candidates.ts` と同じで、1社に閉じた束はそのサービスの月次記事が扱えること。
> もう1つが実測で見つかったほう —
> **`GACKT` `Juice=Juice` `モーニング娘。` `FUNKY MONKEY BΛBY'S` `Taka` の5件が、
> いずれも U-NEXT のライブ映像・舞台番組の束に前方一致していた。**
> 話題の中身は人物・グループであって、その映像作品ではない。
> `data/cast.json` に音楽アーティストは入っていないので、3の歯止めでは落ちない。
>
> **これは近似であって正しい判定ではない。** 1社で閉じた良い束を落とすことがある。
> 落ちて困るものが出たら `MIN_BUNDLE_SERVICES` を 1 に戻し、`demand-ng.json` 側で捌く。

**「答え」は3種類。** ここが記事の型に直結する。

```
until … 未来の終了予定がある     → 「いつまで観られるか」に答えられる
where … 見放題に入った観測がある → 「どこで観られるか」に答えられる
ended … 終了した観測がある       → 「もう観られない。では、どこで」に答えられる
```

> ★ **`ended` は 2026-09-16 に足した。** それまで2種類しかなく、
> **当サイト最大の需要（上の五等分の花嫁）がそこから漏れていた** —
> 未来の終了予定が無く、見放題入りの観測も無いので「答えられる観測が無い」で捨てられていた。
> 「終わったこと」は答えである。記事タイプ `ended` と、シリーズ記事の
> 「◯◯はどこで見れる？」型のタイトル（`templates/naming.md`）が、
> **もともとこの問いに答えるために作ってある。**

`upcoming`（配信予定）は候補にしない。**個別作品の配信開始日は予測しないと決めている**
（[KEYWORDS.md](./KEYWORDS.md) 4節）。観測として持っていても、記事の答えにはしない。

## 4. 貯め方 — 取得元で変えてある

| 取得元 | 貯めるもの | なぜ |
|---|---|---|
| Google トレンド | **全行** | 過去日を取り直す口が無い。**取り逃すと戻せない。** 1日10語で安い |
| Wikipedia | **在庫に当たった語だけ** | 何年前の日付でも同じAPIで返る。1日1000行を全部抱えると**月3.6MB** |
| Search Console | **貯めない** | `data/search-queries.json` そのものが台帳で、同じ28日を投げ直せば同じ値が返る。**日次ではなく28日の集計**なので、日ごとの行に混ぜると「1日ランクインした」と数えてしまう |

> ★ **Wikipedia の999件を捨てているように見えるが、捨てていない。**
> 必要になったら同じ日付を投げ直せばよい。「復元できるものは貯めない」という判断で、
> `data/events` とは逆（あちらは配信APIが過去を返さないので、観測した瞬間に貯めるしかない）。

貯める先は `data/demand/YYYY-MM.jsonl`。同じ日・同じ語は1行に畳み、
数字が動いていたら**大きいほう（その日のピーク）**を残す。初回の実行で146行。

**何のために貯めるか。** その日の候補を出すだけなら要らない。あとから測るため。

- 話題はどれくらい続くか（1日で消えるのか、2週間残るのか）
- 話題が立ってから見放題が終わるまで、どれくらいあるか
- 去年の同じ時期に何が話題だったか（季節ものの先回り）

どれも [KEYWORDS.md](./KEYWORDS.md) 案2『観測レポート』が待っている素材と同じ性質で、
**1日ぶんでは何も言えず、半年貯めると言えるようになる。**

## 5. 使い方

```
npm run demand                 取得して貯めて、候補を出す（直近7日）
npm run demand -- --days 14    突き合わせに使う日数
npm run demand -- --no-fetch   取得しない（貯めたぶんだけ・通信なし）
npm run demand -- --suggest    上位10件に語形の確認をかける
npm run demand -- --all        落とした語を理由つきで出す（切り分け用）
npm run demand -- --json       機械可読
npm run demand -- --picks      サイトに出すぶんを data/demand-picks.json に書く（6節）
npm run demand -- --notify     新規記事の候補があれば Issue で知らせる（6節）
npm run demand -- --trend "ハリー・ポッターシリーズ"
                               1つの記事の日次推移（**第二波の観測**・下の★）
```

> ★ **`--trend` は「話題が戻ってきたか」を測る口**（2026-09-15 追加）。
> 日次 top 1000 に入らない語も追える（Wikipedia の per-article API）。
> 判定は「直近7日 ÷ その前7日」だけで、統計的な検定はしない。
> 使いどころは [FUNNEL.md 9-3](./FUNNEL.md) の「第二波を測る口」。

> ★ **候補には「記事あり ＜slug＞」が付く。** 既に扱った作品でも候補から外さない。
> 話題が立っているのに記事が古い状態がいちばん取りこぼしやすく、外すと
> **「書き直す」「前に出す」という手が一覧から消える。**

**API課金なし。** 無料の公開APIだけで、Streaming Availability API も LLM も呼ばない。

出力はこの形（2026-09-16 実測）。

```
  [いつまで] オッペンハイマー  話題 2,572／3日  在庫 2作  prime-video,netflix  終了 9月27日（あと11日）  導線 Amazon
      オッペンハイマー / オッペンハイマー
  [終了済み] 五等分の花嫁  検索 表示2・クリック0・7位  在庫 1作  netflix  終了 9月10日  導線なし  記事あり 2026-08-leaving-u-next ほか1本
      五等分の花嫁
  [どこで  ] VIVANT  話題 45,561／7日  在庫 1作  disney-plus,prime-video  導線 Amazon
      VIVANT
```

> ★ **`話題` と `検索` は別の欄。** 前者が Wikipedia・トレンド（外の数字）、
> 後者が Search Console（当サイトが何位で出たか）。**足し合わせない**（2節の🔴）。
> 並び順では `検索` を先に見る — そちらは「もう出ているが取れていない」で、
> **打つ手がいちばん短い**（書かなくてよい。押し出すだけでよい）。
> ただし表示5件未満は並び順に効かせない（`MIN_SEARCH_IMPRESSIONS`。
> 入れないと**表示1件が閲覧数45,561に勝つ**）。

**在庫の側は週2回（火・金 JST）しか動かない。需要の側は日次で動く。**
ずれていて構わない。話題が先に立ち、在庫は次の収集で追いつく。
収集の直後に実行すると当たりが増える。

| 実装 | どこ |
|---|---|
| 需要の取得 | `pipeline/sources/demand/`（`wikipedia-pageviews.ts` / `google-trends.ts` / `google-suggest.ts`） |
| 検索語から題名を取り出す | `pipeline/core/demand-queries.ts` ← `data/search-queries.json` |
| 貯める | `pipeline/core/demand-store.ts` → `data/demand/YYYY-MM.jsonl` |
| 突き合わせ | `pipeline/core/demand-match.ts` |
| サイトに出すぶんを決める | `pipeline/core/demand-picks.ts` → `data/demand-picks.json` |
| サイト側で読む | `site/src/lib/demand-picks.ts` ／ `site/src/components/DemandShelf.astro` |
| コマンド | `pipeline/cli/demand.ts`（`npm run demand`） |
| 自動実行 | `.github/workflows/demand.yml`（**毎日 08:13 JST**） |
| 人が捨てた語 | `data/demand-ng.json` |

## 6. 出口 — 何にするか（2026-09-16 実装）

**候補は出る。その候補を3つの出口に振り分ける。** 自動化できる範囲が出口ごとに違う。

| | 出口 | 何をするか | 自動化 |
|---|---|---|---|
| **A** | **押し出し** | 需要の順に `data/demand-picks.json` を書き、サイトが棚に出す | **完全自動**（毎日） |
| **B** | **新規記事** | 束かつシリーズ記事が無いものだけ Issue で知らせる | 通知まで自動。**書くのは人** |
| **C** | **需要の取得** | Search Console を3つ目の取得元にする（2節） | 完全自動 |

### 6-0. いちばん大事な実測 —「新規記事」の枝はほとんど発火しない

当初の設計は「注目ワードに記事が無ければ新規作成、あれば押し出し」だった。
**実測が、その前半をほぼ否定した**（2026-09-16・候補42件）。

| | 件数 |
|---|---|
| 候補 | **42件** |
| うち束（3作以上・2社以上＝シリーズ記事にできる形） | **1件**（ONE PIECE） |
| その1件に既存記事があるか | **ある**（4本） |
| 記事が無い候補 | 15件 — **全部が単発作品** |

単発の話題作品に新記事を作ることは 6-2 の🔴が禁じている（`/works/14281` と食い合う）。
つまり「記事が無ければ書く」は**週0〜1件しか起きない。**
**需要の本体（15/42件）の正しい受け皿は作品ページで、それはもう存在する。**

**→ 自動で動かすのは A（押し出し）。B は「鳴らないのが正常」な通知にする。**

### 6-1. 判断の材料（2026-09-15〜16 実測）

| | 実測 |
|---|---|
| スマホ比率 | **検索流入の79.5%**（mobile 186 / desktop 39 / tablet 9・56日）。外部リンククリックは**71%がスマホ**（17/24） |
| 最大の流入 | `/posts/harry-potter` … 表示324・クリック31。**サイト全体の表示23%・クリック22%を1本で占める** |
| 最大の収益 | `/works/10534`（作品ページ・スマホ）… **外部クリック7**。全24クリック中の7 |
| **記事への出口が無い作品ページ** | **673枚中411枚**（`nextArticle` が出るのは262枚だけ）→ **2026-09-16 に 1枚まで減らした**（下の 6-2b） |
| 収益導線 | **Amazon（prime-video）と U-NEXT のみ。** Netflix / Disney+ / Apple TV+ には日本にアフィリエイトが無い |

> ★ desktop の Direct 74セッションには**運営者自身の閲覧が混ざっている**と見てよい
> （ランディングの最上位が `/`）。スマホ比率は、実際にはこの数字より高い可能性がある。

### 6-2. 出口A — 押し出し（`--picks` → 棚）

`npm run demand -- --picks` が `data/demand-picks.json` を書き、
GitHub Actions がコミットする。**Cloudflare Pages が再ビルドして、サイトに出る。**

**出る場所は2つ。** どちらも `DemandShelf.astro`（横スクロールの棚）。

| どこ | 条件 | 枚数（2026-09-16 実測） |
|---|---|---|
| トップページ | 配信カレンダーの棚の下・シリーズの棚の上（2026-09-19 に並べ替え） | 1枚 |
| 作品ページ | **記事への出口が「ゆるい当たり」のページだけ**（6-2b の3段目に落ちたか、1本も引けなかったページ） | **410枚** |

- **作品ページでは `AfbCta` の下に置く。** あちらの位置は枠別のクリック実測で決めてある
  （[FUNNEL.md](./FUNNEL.md) 7-4）。**測って決めた収益枠を、まだ測っていない枠のために押し下げない。**
- **「1ページに1つだけ」を守る。** `nextArticle` があるページには出さない。
- 棚のカードには `data-slot="demand"` が付く。**効いているかを後から数えられるようにしてある。**

> 🔴 **「いま話題」と書かない。並び順だけが需要を反映する。**
> 画面に出る言葉は**作品ページが持っている観測**（`9月26日まで` `Netflix`）から組む。
> Wikipedia の閲覧数を根拠に「話題の作品」と名乗ると、当サイトの観測でないものを
> 当サイトの主張として出すことになる（2節の🔴）。しかも実測で当てにならない（7節★）。
> **だから枠の名前は「見放題の終了が近い作品」。** 読者にとっても、
> 急ぐ理由が書いてあるほうが押す理由になる。
>
> この決まりは**データの形でも守ってある** — `data/demand-picks.json` に
> 需要の数字は1つも入れていない。入れるとサイト側から読めてしまい、うっかり画面に出る道ができる。

> 🔴 **記事（`.md`）は1文字も自動で書き換えない。** frontmatter を機械が書き換えると、
> `data/articles.json`（台帳）・`npm run write -- --refresh`・品質ゲートと二重管理になる。
> **自動で動いてよいのは「どれを前に出すか」まで。**

**入れ替えには7日の慣性がある**（`KEEP_DAYS`）。需要は日次で動くので、そのまま出すと
棚の中身が毎日入れ替わり、内部リンクが安定しない（クローラが毎回違う先を見る）。
落ちるのは「7日まったく需要側に出てこなかった」か「終了日が過ぎた」ときだけ。

> ★ **棚の上限は候補の数ではなく、作品ページの数で決まる。** 実測で、
> 終了日が未来の候補7件のうち**作品ページがあるのは2件**だった。
> 残り5件は U-NEXT（`SID…`）などで、監督も出演者も解決できていないためページが作られない
> （`works.ts` の `isWorkPagePublishable`）。**棚を増やしたければ、まず作品ページを増やす。**
> 1件だけなら棚に見えないので、2件未満のときは枠ごと出さない（`SHELF_MIN`）。

### 6-2b. 記事への出口を全枚に通した（2026-09-16）

**棚を作ってすぐ分かったのは、作品ページ673枚のうち411枚に
記事へのリンクが1本も無いという別の穴だった。** 棚は作品ページへ送る枠なので、
これは埋まらない。

引き当てを**3段**にして塞いだ。詳しい表は [WORK-PAGES.md](./WORK-PAGES.md) 5節の★。

| 段 | 何を引くか | 枚数 |
|---|---|---|
| 1 | シリーズ記事 | 94 |
| 2 | その作品を表に載せている月次記事 | 168 |
| **3** | **同じ月・同じサービス・同じ出来事の記事**（載っていなくてよい） | **410** |
| — | 引けなかった（Apple TV+ だけの作品。**そのサービスの記事が1本も無い**） | 1 |

**262枚 → 672枚。** 例えば `/works/14281`（リコリス・リコイル・Netflix・9月26日終了予定）は、
**その作品を扱った記事がまだ無い**が、
`同じ月にNetflixで終了する作品のまとめ` → `/posts/2026-09-leaving-netflix` へ出るようになった。

> 🔴 **3段目に「この作品を載せた記事」と名乗らせないこと。**
> 載っているとは限らない。名乗ってよいのは「同じ月に同じサービスで起きたことのまとめ」まで
> （`site/src/lib/work-hub-article.ts` の `labelFor()`）。
> 混ぜると、開いた読者がその作品を探して見つけられない。

> ★ **内部リンクの配分がここで大きく動く。** 実測で320枚が `/posts/2026-08-leaving` を指す。
> 当サイトの観測は2026年8月に始まっているので、**終了済みの作品がその月に偏っている**ため。
> 収集が進むほど散る。**偏りが問題になったら、ここを見る。**

### 6-3. 出口B — 新規記事（`--notify` → Issue）

**束かつシリーズ記事が無いものだけ**を Issue で知らせる。顔ぶれが変わった日にだけ鳴る
（`data/demand-picks.json` の `notifiedSignature`。日付で持つと書くまで毎日鳴り続ける）。

**記事は自動生成しない。** 理由は2つ。

1. `/article` は課金を避けて**セッションの中で書く**作りになっている（LLM APIを使わない）。
   ここから LLM を呼ぶと、その設計を回避して毎日課金する道ができる
2. 6-0 のとおり、**単発の話題作品に新記事を作らないと決めてある**

> 🔴 **単発の話題作品に新しい記事タイプを作らないこと。**
> 「『リコリス・リコイル』の見放題はいつまで」という記事は `/works/14281` とほぼ同じ内容になり、
> **自サイト内で食い合う。** 作品ページを持っていることがこのサイトの強みのほう。

### 6-4. 「副題で需要の語形を捕まえる」をタイトルでやらない理由

当初の案は「既存記事のタイトルに、需要の高まっている語形（`ハリポタ 配信終了`）を
副題として足す」だった。**実測が3つとも否定している。**

| | 実測（2026-09-16） |
|---|---|
| 公開中のタイトルの長さ | **55〜64字**（`<title>` にはさらに `｜見放題レーダー` が付く） |
| `｜見どころ` の位置 | **39〜51字目** |
| スマホの検索結果で表示される長さ | 全角30〜35字程度 |

**`｜` 以降はいまでも1文字も表示されていない。** その後ろに副題を足しても読者には届かず、
タイトル内の語が薄まる方向に働く（Googleのタイトル書き換えも誘発しやすい）。

そして**略称は問題の所在ではなかった。**

| 検索語 | 表示 | 順位 |
|---|---|---|
| ハリーポッター 配信終了 | 25 | 7.4位（クリック3） |
| ハリーポッター ネトフリ いつまで | 13 | 10.0位 |
| **ハリポタ ネトフリ 配信 終了** | **1** | 11.0位 |

略称クエリは全体で22語・75表示＝**サイト全体の2.5%**。数字があるのは中黒なしの正式表記側で、
そこは既に7.4位で取れている。**足りないのは語形ではなく順位。**

**→ 需要の語形は、タイトルではなく次の3か所で効かせる。**

1. **内部リンクのアンカーテキスト**（棚のカードは `9月26日まで／作品名／Netflix`。
   **実装済み** — 需要の順に並べること自体が、内部リンクの配分を需要へ寄せている）
2. 本文（`plugins/rehype-next-step.ts` と同じやり方で表の直前に1文）… **未着手**
3. meta description の先頭 … **未着手**

> ★ サービス名の略称（`アマプラ` `ネトフリ`）は `titleIssues()` が **error** で止める。
> 作品の略称（`ハリポタ`）は機械的には通るが、上のとおり数字が無い。
> 読者の言葉を使うなら [KEYWORDS.md](./KEYWORDS.md) 5節の「本文で1回だけ、正式表記に添える」形にする。

### 6-5. 自動実行

`.github/workflows/demand.yml`。**毎日 08:13 JST**（= 23:13 UTC）。

> ★ **「3日に一度」ではなく毎日。** Google トレンドは過去日を取り直す口が無く
> （1日10語・4節）、3日おきにすると取り逃した2日ぶんは**二度と戻らない**。
> Wikipedia は何年前でも取り直せるので痛くない。**取り逃すと戻せないほうに周期を合わせる。**

> ★ **毎日走ってもサイトが毎日作り直されるわけではない。**
> `--picks` は中身が前回と同じなら書かない。貯めるほうは毎日増えるのでコミットは立つが、
> それは `announce.yml` が既に毎日やっていることで、再ビルドの回数は変わらない。

> ★ 分は `:00` / `:30` を避けてある（`collect.yml` の★。GitHub の schedule は毎時0分に
> 集中し、そこに置くと開始が87〜123分遅れる実測がある）。
> 日曜は `queries.yml`（22:29 UTC）の**あと**に走るので、その週の検索語が反映される。

## 7. この設計が外れていたと分かる形

**測り方を先に決めておく。**

| 主張 | 外れの兆候 |
|---|---|
| 需要 × 在庫で週30件出る | 収集が進んでも候補が10件を割り続ける → 在庫（観測のある3,738作品）が話題の作品と重ならない＝**当サイトの在庫が古い作品に偏っている** |
| 話題は主題選びに効く | 需要から選んだ主題の記事が、在庫から選んだ主題の記事より **90日後の表示回数で下回る** |
| 束の「2社以上」は妥当 | 落とした束の中に、あとから見て書くべきだったものが繰り返し出る → `MIN_BUNDLE_SERVICES` を 1 に戻す |
| 数字を記事に書かない | （破ったら分かる。`verify.ts` では止められないので**人の規律**） |
| **棚（出口A）は効く** | `data-slot="demand"` のクリックが90日で0件 → 位置か文言が届いていない。`/works/*` の回遊が90日で0件だったときと同じ測り方（[FUNNEL.md](./FUNNEL.md) 9-2） |
| **Search Console は Wikipedia より当たる** | 検索実測のある候補から選んだ主題が、話題から選んだ主題より **90日後の表示回数で下回る** |
| **新規記事の通知は鳴らないのが正常** | 毎週鳴る → 束の判定（`MIN_BUNDLE_WORKS` / `MIN_BUNDLE_SERVICES`）が緩すぎる。**逆に半年鳴らなければ**、需要の取得元が当サイトの在庫と重なっていない |

> ★ **いちばん外れやすいのは「Wikipedia の閲覧数＝配信の需要」という置き換え。**
> 実際には放送・訃報・受賞でも跳ねる。`VIVANT` の45,561は**地上波の再放送**の可能性が高く、
> 「配信で観たい人が4万人いる」ではない。
> サジェスト（`--suggest`）で問いの型を確かめてから主題にすること。
