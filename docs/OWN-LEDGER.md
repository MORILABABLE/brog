# 自前の配信台帳を積む（時間を資産にする）

最終更新: 2026-09-07

**問い**（運営者・2026-09-07）:

> U-NEXT は現状、変化率が乏しい（サイトの実稼働歴が浅い）ため自前のデータで在庫がないが、
> 将来的にデータ蓄積で「U-NEXTで何があって、配信終了はいつで、入れ替えた時期はここ」という
> 自前の台帳で管理できるか。同様の仕組みを他サービスでも用意できれば、
> 時間的蓄積によって CROSS-SERVICE の紹介に権威が生まれるのではないか。

**答え: できる。しかも U-NEXT については、8割がた既にできている。**
足りないのは網羅ではなく**履歴**で、そこは**今日から記録しないと二度と取り返せない。**

## 1. いま何を持っているか（2026-09-07 実測）

### 1-1. U-NEXT の台帳は、もう台帳の形をしている

`data/unext-titles.json` の1件はこう。**日付を最初から持っている。**

```json
{
  "id": "SID0002672",
  "title": "セイジ -陸の魚-",
  "lineup": "svod",
  "publicStartDate": "2025-09-01T03:00:00.000Z",
  "publicEndDate":   "2026-08-31T14:59:00.000Z",
  "publicEndText":   "2026年8月31日 23:59まで配信",
  "firstSeenAt":     "2026-08-28T05:06:34.278Z",
  "lastSeenAt":      "2026-08-28T05:06:34.278Z",
  "detailCheckedAt": "2026-08-28T05:06:34.278Z"
}
```

| | 件数 |
|---|---|
| 作品数 | **1,902** |
| `publicStartDate` あり | 1,163 |
| `publicEndDate` あり | **795** |
| 内訳 | 見放題 1,518 / ポイント 362 / 併存 15 / 不明 7 |
| 観測した日 | 8/24・8/25・8/28・9/1・9/3（**実稼働 11日**） |

**「何があって、配信終了はいつで」は、歩いた範囲についてはもう答えられる。**
しかも U-NEXT は作品ページに終了日を**自分で公開している**ので、
配信APIより情報が濃い（APIの `expiresOn` は日本では空。[CROSS-SERVICE 2-4](./CROSS-SERVICE.md)）。

### 1-2. 足りないのは2つだけ

| 足りないもの | 中身 | あとから取り返せるか |
|---|---|---|
| **網羅** | 1,902件は「新規入荷」と「終了予定」を歩いた副産物。カタログ全体ではない | ✅ **取り返せる。** 歩く範囲を広げれば増える |
| **履歴** | 「入れ替えた時期はここ」に当たるもの。**いまは毎回上書きで消えている** | ❌ **取り返せない。** 過去の状態は後から観測できない |

**この非対称が、この文書のすべて。**
網羅は急がなくてよい。**履歴だけは、記録を始めた日からしか積み上がらない。**

## 2. ★ いちばん値打ちのある観測を、毎週捨てていた

`npm run unext:refresh` は作品ページを開き直して、終了日が動いた作品を1件ずつ見つけている。
そして**画面に出して、捨てていた**（`cli/unext-refresh.ts` の `changes`）。

```
--- 配信終了日が動いた作品 ---
  [変更]         名探偵コナン …: 2026年8月31日 → 2026年9月30日     ← 延長された
  [終了日が消えた] …            : 2026年8月31日 → （なし）          ← 無期限になった
  [新たに判明]    …            : （なし）      → 2026年9月30日
```

**「8月31日で終わる予定だったが延長された」は、毎週見に行っている者にしか分からない。**
公式は延長を告知しないし、他のまとめサイトは「いまの終了日」しか出さない。
配信API（Movie of the Night）も、日本では終了日そのものを返さない。

**ここが権威になる。** そして、記録していなかったぶんは永久に失われている。

同じことが `data/availability.json`（4社の在庫）でも起きていた。
取り直すたびに上書きで、**前回どうだったかが毎回消えていた。**

## 3. やったこと（2026-09-07）

### 3-1. `data/history/*.jsonl` — 追記のみの履歴

`pipeline/core/history.ts`。**状態そのものではなく、状態が動いたことを1行にする。**

```json
{"observedAt":"2026-09-07T…","service":"u-next","workId":"SID0230770",
 "title":"仮面ライダーゼッツ","field":"endDate",
 "from":"2026-08-31T14:59:00.000Z","to":"2026-09-30T14:59:00.000Z",
 "via":"unext:refresh (作品ページ)"}
```

毎回の全件スナップショットは置かない。同じ答えが積み上がるだけで嵩む。

| `field` | 動いたもの |
|---|---|
| `endDate` | 見放題の終了日（延長・前倒し・取り下げ・新たに判明） |
| `lineup` | 見放題 ↔ ポイント |
| `subscription` | そのサービスの見放題に入った／外れた |

### 3-2. 差分を出していた2か所に繋いだ

| どこ | 何を積むか | 頻度 |
|---|---|---|
| `unext:refresh` | 終了日が動いた作品 | 週2（月・木の収集のあと） |
| `npm run availability` | 見放題に入った／外れた作品 | シリーズ記事を書き直すたび |

**どちらも既に差分を計算していた。** 足したのは記録だけで、取得は1件も増えていない。

### 3-3. ★ 「歩いた範囲」を必ず一緒に残す（`via`）

**この決まりが、台帳を資産にするか誤情報にするかを分ける。**

    ✕ 「9月7日の観測に無い」→「U-NEXTから消えた」
    ○ 「9月7日に新規入荷カテゴリを歩いた。そこには無かった」
       （カタログ全体を見たわけではないので、消えたとは言えない）

当サイトが歩いているのはカタログ全体ではない（[CROSS-SERVICE 3-2](./CROSS-SERVICE.md)）。
**範囲を残さない不在は「偽の不在」になる。**

> **2026-09-07 に実際に踏んだ。** 配信APIが「仮面ライダー」を14本しか知らないことを、
> **「Amazonに14本しかない」と報告した。** 実際にはAPIの日本カタログが薄いだけで、
> 運営者が画面で数えたら約50作あった。
> **持っている範囲と、世の中の実態を、取り違えてはいけない。**

## 4. サービスごとの見通し

| サービス | 自前で積めるか | 根拠 |
|---|---|---|
| **U-NEXT** | ✅ **積める。もう積み始めている** | robots.txt で `/browse/` `/title/` 許可。終了日を作品ページで公開。ヘッドレスブラウザで身分を偽らずに取得（[SOURCES-UNEXT-HULU 2](./SOURCES-UNEXT-HULU.md)） |
| **Netflix / Prime Video / Disney+ / Apple TV+** | 🔶 **APIの観測を積む形でだけ積める** | 直接の巡回はしない。積めるのは在庫APIの応答の差分で、**APIのカタログの薄さをそのまま引き継ぐ**（[CROSS-SERVICE 9-3-B](./CROSS-SERVICE.md)） |
| **Hulu** | ❌ **やらない** | 利用規約 第3条(3) が自動アクセスを明示的に禁止 |
| **DMM TV** | ❌ 未調査。データが無い | |
| **Amazon の画面そのもの** | ❌ **できない** | `amazon.co.jp` は自動取得に応答しない（2026-09-07 確認。空で返る）。突き合わせは人の目視 |

★ **Netflix / Disney+ / Apple TV+ を「自前で歩く」案は取らない。**
  U-NEXT で成立しているのは robots.txt と規約を1つずつ確かめたからで、
  同じ確認をしていないサービスに同じ仕組みを広げるのは、
  技術の問題ではなく**約束の問題**として不可。広げるなら1社ずつ調査から。

## 5. 何が書けるようになるか（時間の関数）

**どれも「毎週見に行っている者にしか書けない」記事。**

| 積み上がり | 書けるもの |
|---|---|
| 1〜2か月 | 「終了予定だったが延長された作品」— 読者にとっては**朗報**で、他所が書かない |
| 3〜6か月 | 「このサービスは平均◯日で入れ替わる」— 実測でしか言えない |
| 6か月〜 | 作品ページの**配信履歴**（`/works/<id>`）。「2026年8月にPrime Videoで開始、9月にU-NEXTでも」 |
| 1年〜 | 「毎年◯月に大量入れ替えが起きる」— 季節性。**1年経たないと絶対に言えない** |

### いつ記事になるか

**まだ決めない。** 積んでから件数を見て決める。
先に記事タイプを作ると、素材が薄いまま「延長された作品1本」の記事ができる。
`core/history.ts` に集計の口（`extensions` / `broughtForward` / `deadlineLifted`）だけ置いてある。

## 6. 権威が生まれる条件（と、生まれない条件）

運営者の見立て（「時間的蓄積によって権威が生まれる」）は正しい。
ただし**成立条件が2つある。**

### 6-1. 網羅を名乗らないこと

**持っている範囲を正直に言い続けるかぎり、範囲が狭いことは弱点にならない。**
「当サイトが観測した範囲では」と言える記事は、
「全部載っています」と言って外している記事より強い。

逆に、**一度でも「網羅しています」と読ませたら、そこで終わる。**
読者はサービスの検索結果と見比べるので、必ず見つかる。
シリーズ記事の `series-coverage-note` はそのための固定文言。

### 6-2. 観測を捏造しないこと

履歴は**追記のみ・過去は書き換えない**。
「たぶんこの日に入れ替わった」を1行でも入れた時点で、台帳全体が推測になる。

> **2026-09-07 の実装確認で、動作テストのために偽の観測を1行作って、すぐ消した。**
> テストであっても台帳に残してはいけない。**残すなら別ファイルで行う。**

## 7. まだやっていないこと

| | 内容 |
|---|---|
| **U-NEXT の網羅を広げる** | いまは「新規入荷」「終了予定」だけ。ジャンル配下を一巡すれば台帳が桁で増える。[SOURCES-UNEXT-HULU 2.2](./SOURCES-UNEXT-HULU.md) の通り全ジャンル1周で40〜60リクエスト |
| **一覧から消えた作品の記録** | いまは「終了日が動いた」しか積んでいない。消失の記録は**歩いた範囲の定義**とセットでないと偽の不在になるので、範囲を先に決める |
| **作品ページへの履歴表示** | `historyByWork()` は用意した。出す場所は [WORK-PAGES.md](./WORK-PAGES.md) と揃えてから |
| **記事タイプ** | 5節の通り、積んでから決める |
| **CI への組み込み** | **不要。** `collect-unext.yml` が既に `unext:refresh` を週2で回しており、そこに履歴の追記が乗った。**ワークフローは触っていない** |
