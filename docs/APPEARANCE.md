> **全ページの一番上に出していたヘッダーバナーは 2026-08-24 に外した。**
> 読者がすぐ一覧に入れるようにするため。画像ファイル
> （`site/src/assets/header-banner.png`）は**残してある**。
> OG画像（SNS共有画像）の元になっており、消すと 7節の生成が落ちる。

**背景（点と地色）は画像ファイルではなく CSS で描いている。** 理由は3つ。

1. サイトはライト/ダーク両対応。画像だと明暗2枚とメディアクエリが必要になる
2. 背景は全ページに乗る。画像だと表示速度（LCP）に直撃し、広告収入にも響く
3. CSS なら数百バイトで済み、`--accent` などの既存の色変数と揃えられる

> **ライトモードでも地は暗い。** 文字は必ず白いカードの中に置くこと。
> カードの外に直接テキストを置くと、`--text`（ほぼ黒）のままで読めなくなる。
> フッターだけは地の上に載るので、専用の明るい色（`--footer-text`）を持たせてある。

## 1. 背景の色と濃さを変える

`site/src/styles/global.css` の先頭にツマミがある。

```css
:root {
  --bg-tint: #1b3a6e;                      /* 地の色 */
  --dot-color: rgba(174, 208, 255, 0.13);  /* 点の色 */
  --dot-gap: 22px;                         /* 点の間隔 */

  --footer-bg: #16305c;                    /* フッターの地。--bg-tint より少し沈める */
  --footer-text: #bccbe4;                  /* フッターの文字 */
  --footer-link: #9dc4ff;                  /* フッターのリンク */
  --footer-border: rgba(255, 255, 255, 0.12);
}
```

**ライトとダークの2箇所にある。必ず両方直すこと。**
片方だけ変えると、もう一方の配色で背景が浮いたり沈んだりする。

| やりたいこと | 直す値 |
|---|---|
| 地をもっと濃くしたい | `--bg-tint` を `#142c55` などに下げる。`--footer-bg` も一段暗い値に合わせる |
| 地を明るくしたい | `--bg-tint` を `#28518f` などに上げる |
| 青みを落として黒に寄せたい | `--bg-tint` を `#1a2430` などに寄せる |
| 淡いブルーに戻したい | `--bg-tint: #eef4fd` ＋ `--dot-color: rgba(31,111,235,0.22)`。**その場合はフッターの色も明るく戻すこと**（[下記](#フッターだけ元の明るい色に戻す)） |
| 点を目立たせたい | `--dot-color` の末尾 `0.13` を `0.20` などに上げる |
| 点をまばらにしたい | `--dot-gap` を `28px` `32px` と広げる |

ダーク側の既定値はこちら。

```css
--bg-tint: #0b1d3a;
--dot-color: rgba(110, 168, 254, 0.14);
--footer-bg: #091728;
```

> **地が暗いので、点は「明るい色」で置いている。** 暗い地に暗い点を置くと何も見えない。
> 地を淡い色に戻すときは、点も暗い色に戻す必要がある。

### フッターだけ元の明るい色に戻す

`site/src/components/Footer.astro` の `footer { }` を戻す。

```css
footer {
  border-top: 1px solid var(--border);
  background: var(--bg-subtle);
  color: var(--text-muted);
}
```

同じファイルの `footer a { color: var(--footer-link); }` を消し、
`nav a { color: var(--footer-text); }` を `var(--text-muted)` に戻す。

## 2. 背景の柄を変える

点を描いているのは `body` のこの1行。

```css
background-image: radial-gradient(var(--dot-color) 1px, transparent 1.3px);
```

差し替え例。`--dot-gap` が `background-size` に効いているので、間隔はそのまま使える。

**細い格子（方眼紙）**

```css
background-image:
  linear-gradient(var(--dot-color) 1px, transparent 1px),
  linear-gradient(90deg, var(--dot-color) 1px, transparent 1px);
```

**斜めのストライプ**

```css
background-image: repeating-linear-gradient(
  45deg,
  var(--dot-color) 0 1px,
  transparent 1px 12px
);
```

もっと凝った柄が欲しいときは **Hero Patterns**（heropatterns.com・CC0）で
色と濃さを決めて CSS をコピーし、この行と差し替える。
`background-size` の指定も一緒に付いてくるので、その場合は `--dot-gap` の行を消す。

## 3. 背景をやめる

`site/src/styles/global.css` の `body` を元に戻す。

```css
body {
  margin: 0;
  background: var(--bg);   /* ← background-color / -image / -size の3行と差し替え */
  color: var(--text);
  font-size: 16px;
  overflow-x: hidden;
}
```

このとき[本文カードもやめる](#4-本文カードを調整するやめる)と、改修前の見た目に完全に戻る。

## 4. 本文カードを調整する／やめる

```css
.content-card {
  margin: 1.6rem auto 0;              /* ヘッダーとの間隔 */
  padding: 0.6rem 1.9rem 2.2rem;      /* カード内側の余白 */
  border-radius: 14px;                /* 角の丸み */
}
```

**狭い画面（47rem 以下）ではカードを全幅に戻している。**
スマホで本文の横幅を削るほうが、背景が見えることより損だという判断。
そのぶん**スマホでは背景の紺がほとんど見えない**（フッター手前の余白だけ）。
この挙動は同じファイルの `@media (max-width: 47rem)` で変えられる。

**カードをやめる**なら `site/src/layouts/BaseLayout.astro` の1行を戻す。

```astro
<main id="main" class="wrap">        <!-- content-card → wrap -->
```

### 左右の枠（1200px 以上だけ）

本文カードの左右の余白に枠を出している。見た目に関わるのは
`global.css` の `.layout` だけ。

```css
.layout { display: block; }          /* 既定。1200px 未満は枠が消えて1カラム */

@media (min-width: 75rem) {
  .layout {
    display: grid;
    grid-template-columns: minmax(0, 1fr) min(var(--max-width), 100%) minmax(0, 1fr);
  }
}
```

**本文の幅（`--max-width`）は枠があってもなくても変わらない。**
左右とも同じ列幅なので本文は中央のままで、余白に枠が載るだけ。
記事は配信終了作品の**表**が主体で横幅を食うため、本文を削るサイドバー方式は採っていない。

#### 左の枠（`LeftRail.astro`）

```
┌──────────────────────┐
│ 新着配信・終了一覧          │ ← 見出し（背景の紺の上に直接載る）
│ 最新の更新タイトルは…       │ ← 補足（.block-note。リンク先の検索窓の案内）
│ [絵] 配信終了予定 Netflix  │
│ [絵] 配信終了予定 Prime… │   常設ページ1つにつき1枚
│ [絵] 新着配信 Netflix     │
│ ⋯                     │
└──────────────────────┘
```

追従しない。本文と一緒に流れる。

> **もとは右の枠の1ブロック目だった**（2026-08-24 に左へ移動）。
> サービスが増えるほど一覧が縦に伸び、その下の新着記事とPR枠が
> 画面外へ押し出されていた。**右に戻さないこと。**

#### 右の枠（`FollowRail.astro`／中身と運用は [AFFILIATE.md](./AFFILIATE.md)）

```
┌──────────────────────┐
│ 最新記事                │ ← カテゴリ横断の最新記事（既定5本）
│ [絵] [バッジ]            │   絵は記事の heroImage（48px・記事カードと同じ絵）
│      記事タイトル…        │   画像の無い記事はカテゴリ色のタイル
├──────────────────────┤
│ PR                    │ ← 広告カード。アフィリエイト有効時のみ。**ここだけ追従**
│ Amazon …              │
└──────────────────────┘
```

**広告とそれ以外を混ぜてはいけない。** まとめて `aria-label="広告"` にすると
新着記事まで広告と称することになり、逆にPR表記を外すと
景品表示法（ステマ規制）に触れる。

カードのバッジは記事カードと同じ `.badge[data-category]` を使っている。

> **並びは全ページで固定。** 以前は「いま見ているページのカードを消す」実装に
> していたが、**移動のたびに一覧の中身と順番が変わり読者が混乱した**
> （2026-08-23 に修正）。いまは常に同じ順で全件出し、現在地だけリンクを外して
> `aria-current="page"` を付けている。**出し分ける実装に戻さないこと。**

> **ブロック見出しはカードの外＝紺の地に直接載る。**
> `--text-muted`（本文用の暗いグレー）だと沈んで読めないので、
> 地の上の文字用の明るい色（`--footer-text`）を使っている。
> この文書の冒頭に書いた「文字は白いカードの中にしか置かない」の例外なので、
> 色を変えるときはコントラストを必ず確認する。

> **追従するのは PR枠だけ。** 左の枠と新着記事はページと一緒に流れる。
>
> 枠全体を `sticky` にすると、枠が画面より高いときに上端で貼り付き
> **下端のPR枠に永久に手が届かなくなる**。枠の中をスクロールさせれば届くが、
> **読者がスクロールを2回する**ことになる。
> 新着記事を流し、PR枠（約230px＝どんな画面にも収まる）だけを追従させるのが、
> 「スクロールバーはページの1本だけ」と「広告が付いてくる」を両立する唯一の形
> （2026-08-23 の判断）。
>
> ★ **PR枠をラッパー要素でくくらないこと。** `sticky` が効く範囲は
> 直近のブロックコンテナ＝ `.follow-rail`（グリッドの列）で、
> これは記事の高さいっぱいに伸びている。`<div>` で囲むとその高さまでしか
> 追従しなくなる。だから `.follow-rail` の直下に置いてある。

#### サムネイルを置く（左の枠）

`src/assets/services/<キー>.png` を置くだけで、そのカードに48×48pxの絵が出る。
キーはサービスキー（`netflix` / `prime-video` / `disney-plus`）。
**置いていないキーはサービス名の頭文字**（`N` `A` `D`）になり、レイアウトは崩れない。
**2026-08-28 に `netflix.jpg` と `prime-video.jpg` を入れた**（Disney+ はまだ頭文字）。
詳細と注意（各社ロゴの商標リスクを含む）は
[src/assets/services/README.md](../site/src/assets/services/README.md)。

> **1枚置くと3か所に出る。** 左の枠（48）・記事一覧のカード（72）・
> 常設ページの見出し上（本文幅）。左の枠だけの絵ではない。

> **枠では短い名前を使っている。** 1200px のとき文字に使える幅は約158pxしかなく、
> 「Amazon Prime Video」は2行に折り返して**そのカードだけ背が高くなる**（実際に踏んだ）。
> `evergreen.ts` の `SHORT_LABELS` で「Prime Video」に置き換えて1行に収めている。
> 名前の長いサービスを足すときは、ここに短縮形を1行足すこと。
> 併せて `.rail-card { min-height: 64px }` を入れてあるので、
> 万一折り返しても高さは下回らない。

> **カテゴリページのカード（`EvergreenCard.astro`）にも同じ絵が出る。**
> 以前は「周りの記事カードに画像が無いので、そこだけ絵を置くと浮く」として
> 外していたが、記事側も `heroImage`（作品ポスター）が自動で入るようになり
> （2026-08-25〜）、**絵が無いほうが浮く**状態に反転したため戻してある。

| 変えたいこと | 直す場所 |
|---|---|
| 枠を出す画面幅の下限 | `global.css` の `.layout` のメディアクエリ `75rem`（下げすぎ注意・下記） |
| 枠の幅 | 各コンポーネントの `.block { max-width }`（左右とも 17rem） |
| PR枠が張り付く位置 | `FollowRail.astro` の `.rail-ad { top }` |
| 枠に出す常設ページ | `src/lib/evergreen.ts` の `EVERGREEN_PAGES` |
| 枠での短い表示名 | 同ファイルの `SHORT_LABELS`（下記） |
| 対象サービスそのものの増減 | `src/lib/events-data.ts` の `LEAVING_SERVICES` / `ARRIVALS_SERVICES` |
| 広告カードの文面 | `FollowRail.astro` の `.rail-ad` ブロック |
| サムネイル | `src/assets/services/` にファイルを置く／消す |
| 最新記事の本数 | `FollowRail.astro` の `RECENT_POSTS`（既定5） |
| 最新記事の絵 | 記事 frontmatter の `heroImage`（`public/heroes/…`）。枠側の指定は `FollowRail.astro` の `<Thumb size={60}>` |
| 追従の対象 | `FollowRail.astro` の `.rail-ad { position: sticky }` |
| ブロックの見出し文言 | 各コンポーネントの `.block-title` を持つ `<p>` |
| 左の枠の補足文（「最新の更新タイトルはコチラから検索できます」） | `LeftRail.astro` の `.block-note` を持つ `<p>` |
| **左の枠を消す** | `BaseLayout.astro` から `<LeftRail />` を外す |
| **右の枠を消す** | `BaseLayout.astro` から `<FollowRail />` を外す |

> **狭い画面（1200px未満）では左右とも枠ごと消える。**
> 常設ページへの入口がスマホで無くなるので、
> **ヘッダーのメニュー → サービス**の先にも導線を置いてある
> （`src/pages/category/[category]/[service].astro`）。片方だけ消さないこと。
> 2026-08-27 に右の枠から「サービスから探す」を外し、同じ導線を
> ヘッダーのメニューへ移したのもこの理由（枠が消える画面では存在しないのと同じだった）。

> `.rail-ad` の `position: sticky` は、`html` に `overflow` が無く
> `body` の `overflow-x: hidden` がビューポートに伝播することで成立している。
> **`html` 側に `overflow` を足すと追従が壊れる。**

### 下の枠（1200px 未満だけ・`FollowBar.astro`）

**上の左右の枠は 1200px 以上でしか出ない。その裏返しの枠**（2026-09-05 追加）。
狭い画面では画面の下に1本のバーが出る。中身と運用は
[AFFILIATE.md 6節 Phase D-2](./AFFILIATE.md)。

```
┌────────────────────────────────────────────┐
│ PR │ 「マイ・ボディガード」をPrime Videoで探す │ × │
└────────────────────────────────────────────┘
        └ ここ全体が1本のリンク（指で押す面を大きく取る）
```

**追従枠は画面に常にちょうど1つ。**

| 画面幅 | 出るもの |
|---|---|
| 75rem (1200px) 以上 | 左右の枠（`LeftRail` / `FollowRail`）。下のバーは出ない |
| 75rem 未満 | 下のバーだけ。左右の枠は出ない |

> ★ **しきい値は2か所にあり、裏返しの値になっている。**
> `global.css` の `.layout` が `min-width: 75rem`、
> `FollowBar.astro` が `max-width: 74.9375rem`（＝1199px）。
> **片方だけ動かすと「両方出る幅」か「両方消える幅」ができる。**

| 変えたいこと | 直す場所 |
|---|---|
| バーを出す画面幅の上限 | `FollowBar.astro` の `@media (min-width: 75rem)`（`.layout` と対で直す） |
| バーの文面・見た目 | `FollowBar.astro`（送り先の決め方は `lib/page-intent.ts`） |
| 出るページ | `src/lib/follow-bar.ts` の `PREFIXES`（**`AffiliateNotice` も一緒に足すこと**） |
| **バーごと消す** | `src/lib/follow-bar.ts` の `FOLLOW_BAR_ENABLED = false` |

> **`body` の下余白はこのコンポーネントが持っている**（`:global(body)`）。
> バーがフッターの文字に重ならないようにするためのもので、
> **バーが出る前から入れてある**（現れた瞬間に足すとレイアウトが動く）。
> 枠を出さないページにはこのスタイル自体が出ないので、余白も残らない。

> **出るのはスクロールしてから。** 1画面ぶん進むまでは `hidden` のまま。
> 一度出たら引っ込まない（出入りは読者の邪魔になる）。
> `×` で閉じるとそのセッション中は出ない。

## 5. ロゴ（ファビコン）を差し替える

いま入っているのは**仮のマーク**（青い角丸に再生三角）。自作ロゴができたら差し替える。

置いてあるファイルは3つ。

| ファイル | 用途 |
|---|---|
| `site/public/favicon.svg` | 本体。モダンブラウザはこれを使う |
| `site/public/favicon-32.png` | SVG非対応の古いブラウザ向け |
| `site/public/apple-touch-icon.png` | iOS のホーム画面追加用（180×180） |

### ターミナルが使える場合

`favicon.svg` を上書きしてから、PNG を焼き直す。

```powershell
cd C:\Users\grate\brog\site
node scripts/make-icons.mjs
```

### ブラウザだけで完結させたい場合

**RealFaviconGenerator**（realfavicongenerator.net）にロゴ画像を入れ、

### また画面に出したくなったら

```astro
  class="site-banner"
  src={banner}
  alt={OG_IMAGE.alt}
  widths={[736, 1200]}          {/* 元画像の幅を超える数値は指定できない */}
  sizes="(max-width: 47rem) 100vw, 736px"
  loading="eager"
  fetchpriority="high"
```

`site/src/styles/global.css` に見た目も戻す（削除済み）。


- 高さは縦横比で決まる。2.59:1 ならデスクトップで 736 × 284px。
  詰めたいなら `aspect-ratio` + `object-fit: cover` を足すか、その比率で描き直す

## 7. OG画像（SNS共有画像）を差し替える

X や Slack にURLを貼ったときに出る画像。
いまは**ヘッダーバナーから機械的に作っている**（`site/public/og-default.jpg`・61KB）。

> バナーは 2.59:1 だが、OGPの推奨は **1.91:1**。
> そのまま出すと SNS 側で左右を切られてキャッチコピーが欠けるので、
> 上下に「バナー自身を拡大してぼかしたもの」を継ぎ足して 1200 × 628 にしている。
> 単色で埋めると継ぎ目が帯として見えるため。

### バナーを差し替えたら作り直す

```powershell
cd C:\Users\grate\brog\site
node scripts/make-og.mjs
```

バナーの幅が 1200px でない場合や、バナーが 628px より高い場合は
スクリプトが理由を出して止まる。その場合は手で作る。

### 別の絵を使いたい場合

**1.** 画像編集ソフトで **1200 × 630** で作る。

**2.** `site/public/og-default.jpg` に**同じファイル名で**上書きする
（以降 `make-og.mjs` を流すと上書きされるので、使うのをやめること）。
ファイル名や寸法を変える場合は `site/src/config.ts` も直す。

```ts
export const OG_IMAGE = {
  path: '/og-default.jpg',
  width: 1200,
  height: 628,
  alt: '見放題レーダー｜主要動画サービスの配信終了と新着をまとめて追う',
} as const
```

**3.** `alt` も実際の画像の内容に合わせて直す。

> **写真は JPEG にする。** PNG のままだと1MB近くになる。
> `public/` の画像はビルドで最適化されないので、ここだけは手で軽くする必要がある。
> バナー元画像（`src/assets/`）は PNG のままでよい（ビルドが WebP にする）。

### 注意

- **文字は中央寄りに置く。** SNSによって上下左右が切られる
- **文字は大きく。** タイムラインでは実寸の半分以下で表示される
- **反映は遅い。** 各SNSがキャッシュを持つため、差し替え後も古い画像が出続けることがある。
  X なら Card Validator、Facebook なら Sharing Debugger でキャッシュを更新できる

## 8. カテゴリバッジの色を変える

記事一覧と記事冒頭に出る「配信終了予定」「新着配信」などのタグ。
**読者が文字を読む前に、観られるのか観られないのかを判別できるようにするための色分け**です。

| バッジ | 色 | 意味 |
|---|---|---|
| 配信終了予定 | アンバー | まだ観られる。急ぐ意味がある |
| 配信終了済み | グレー | もう観られない。急かす対象ではない |
| 新着配信 | ブルー | 新しく入った |
| ランキング | パープル | — |

色は `site/src/styles/global.css` の `:root` にまとまっています。

```css
--cat-leaving-bg: #fbeedb;   /* 背景 */
--cat-leaving-fg: #8a4d08;   /* 文字 */
--cat-ended-bg: #e9ecf0;
--cat-ended-fg: #55606d;
--cat-arrivals-bg: #e8f0fe;
--cat-arrivals-fg: #1a5fd0;
--cat-ranking-bg: #efe8fc;
--cat-ranking-fg: #6535bb;
```

**ライトとダークの2箇所にあります。必ず両方直してください。**
ダーク側は地が暗いので、文字を明るく・背景を沈める方向で組んであります。

### 変えるときに守ること

- **文字と背景のコントラスト比を 4.5:1 以上に保つ。**
  現在の8組はすべて 5:1 以上を実測で確認済みです。淡い色同士にすると読めなくなります
- **色だけに意味を持たせない。** バッジには必ずラベル文字を併記します。
  色覚特性のある読者や、印刷・モノクロ表示では色が届きません

### カテゴリバッジの右に並ぶ2つのバッジ

カテゴリ以外に、**枠線だけの形をした**バッジが2種類あります。塗りのカテゴリバッジと
形で区別できるようにしてあり、**1枚のカードにどちらか一方しか出ません。**

| バッジ | 出るところ | 色 | 何を伝えるか |
|---|---|---|---|
| アニメ／洋画／邦画 | ジャンル軸の記事 | **灰**（`--border` / `--text-muted`） | 何を観る話か |
| **随時更新** | **常設ページ**（`/leaving/…` `/arrivals/…`） | **緑**（`--tag-evergreen`） | **このページは古くならない** |

「随時更新」は 2026-09-05 に足しました。常設ページのカードは記事カードと
**わざと同じ体裁**にしてあり（10節・2026-08-23）、その結果**一覧の中で記事と
見分けが付かなくなっていた**ためです。読者にとって両者は別物です。

- 記事 … 書いた日のスナップショット。日付が古くなる。解説がある
- 常設 … 収集のたびに中身が入れ替わる。**古くならない。URLが変わらない**

文言は `site/src/config.ts` の `EVERGREEN_BADGE`（ページ本体に出る説明の1行も同じ場所）。

> **ジャンルは灰色なのに、なぜ随時更新だけ色を足したのか。**
> ジャンルは「何を観る話か」で、カテゴリ（何が起きたか）と**同じ「内容」の軸**です。
> 色を持たせると、隣り合う2つのバッジが同じ問いに別々の色で答えることになります。
> 「随時更新」は内容の軸ではなく「このページは古くなるのか」なので、カテゴリと競合しません。
>
> ★ **アクセント色（青）は使わないこと。** 新着配信のバッジが青系なので、
>   `/arrivals/<サービス>` で青いバッジが2つ並んで区別が消えます。緑は4色のどれとも当たりません。
>
> ★ 灰色（ジャンルと同じ扱い）に戻したくなったら、`styles/global.css` の
>   `.badge.evergreen` の2行を `--border` / `--text-muted` に替えるだけです。

### カテゴリを増やしたとき

`:root` に1組（`--cat-<スラッグ>-bg` / `-fg`）を足し、同じファイルの下のほうにある
バッジの定義にも1ブロック足します。

```css
.badge[data-category='新しいスラッグ'] {
  background: var(--cat-新しいスラッグ-bg);
  color: var(--cat-新しいスラッグ-fg);
}
```

**足し忘れても壊れません。** 指定の無いカテゴリは既定のアクセント色で表示されます。

## 9. 記事ごとのカード画像

記事をSNSに貼ったときに出る画像を、**記事1本ごとに自動生成**している。
以前はサイト共通のバナー1枚だったので、どの記事を貼っても同じ絵が出ていた。

出力先は `site/public/cards/<スラッグ>.jpg`（1200 × 630）。
記事タイトル・カテゴリ・サービス名を、サイトの配色でカードに起こしたもの。

### なぜ作品の場面写真を使わないのか

**使えないため。** 理由は3つ。

1. 作品の場面写真（作中キャプチャ）は著作権があり、広告のある当サイトでは
   「引用」の要件（引用の必要性・主従関係）を満たさない
2. 配信APIが返す画像は**ポスターとキーアートだけ**で、本編の画像は含まれない
3. Wikidata / Wikimedia Commons にも無い（実測：Wikidataに項目のある17作品中、画像は0件）

生成カードなら**第三者の権利が一切絡まない。** URLの失効も帯域制限も無い。

> **本文中のセクション画像には作品ポスターを載せている**（2026-08-25〜）。
> 配信APIが返すポスターを、提供元の許諾を得たうえで使っている。
> ここ（記事カード＝SNS共有画像）に載せていないのは、
> 契約が切れたら差し替えが要る画像をOGPに置きたくないため。
> 経緯と運用は [11節](#11-作品ポスターの取り扱い許諾取り直し契約終了)。

### 何もしなくてよい（ビルド時に自動生成される）

`npm run build` の前に自動で走る（`package.json` の `prebuild`）。
記事を書いたら、**ただコミットしてプッシュすればカードもできる。**
画像は `.gitignore` 済みで、コミットする必要も無い。

手元で絵だけ確認したいときは次で単体実行できる。

```powershell
cd C:\Users\grate\brog\site
npm run cards
```

### なぜ環境に左右されないのか

SVG の `<text>` で文字を描くと、**描画するマシンにインストールされたフォント**が使われる。
Cloudflare のビルド環境（Linux）には日本語フォントが無いので、
素直に書くと本番のカードだけ**日本語が豆腐（□□□）になる。**

実測で確認した事実：

| 試したこと | 結果 |
|---|---|
| SVG に `@font-face`（data URI）でフォントを埋め込む | **無視される。** システムフォントに代替された |
| `FONTCONFIG_FILE` でフォント探索先を指定する | **効かない**（Windows では fontconfig を見ない） |

そこで **opentype.js で文字をすべてパス（`<path>`）に変換**している。
出来上がる SVG にフォントの概念が残らないので、Windows でも Linux でも
Cloudflare でも同じ絵になる。

フォントは `site/scripts/fonts/` に同梱（Zen Kaku Gothic New・SIL Open Font License 1.1）。
**差し替えるときは `OFL.txt` も一緒に入れ替えること。**

### 見た目を変える

`site/scripts/make-cards.mjs` の `buildSvg()` を編集する。

| 変えたいもの | 場所 |
|---|---|
| カテゴリごとの色 | `CATEGORY`（**`global.css` の `--cat-*` と同じ値にすること**） |
| 出すサービス名 | `SERVICES`（theme.yaml の catalogs に合わせる） |
| 文字サイズ | `buildSvg()` の `titleSize` ほか、`textPath()` に渡すサイズ |
| 折り返しの行数 | `wrap('bold', title, titleSize, innerW, 3)` の末尾の `3` |
| フォント | `FONTS`（**同梱ファイルとライセンスも入れ替えること**） |
| 画像の寸法 | 先頭の `W` / `H`（**`site/src/config.ts` の `CARD_IMAGE` も同時に直す**） |

### カードを一覧のサムネイルにも出すか

**出していない。** カードには記事タイトルがそのまま描かれているので、
記事一覧に並べるとタイトルが隣に二重に出るだけで、読者が得る情報が増えないため。
必要なら `site/src/components/PostCard.astro` に `<img>` を1つ足せば出せる。

## 10. 本文中のセクション画像

記事の小段落ごとに、**小見出しの直後**へ画像を挟んでいる。

```
## 8月3日：Netflixで京都アニメーション作品が一斉に見放題配信開始

[![Free!（2013年）](/sections/posters/….webp)](…) [![らき☆すた（2007年）](…)](…)   ← ここ

| 配信開始日 | 作品 | 評価 | サービス |
| 8月3日 | Free! | 62/100 | Netflix |
    …

「Free!」「らき☆すた」「日常」は、いずれも京都アニメーション制作の…
```

### どこに入るか

**小見出しの直後**（見出し → 画像 → 表 → 地の文）。
読者が節に入った瞬間に絵が目に入り、そのまま表へ進む。

> 2026-08-25 に「表の直後」から移した。
> 旧位置に残っている画像は `npm run sections -- --write` が消してから入れ直す。

### 版が3つある（重要）

**上から順に試して、できたところで止まる。**

| | 中身 | 出力先 |
|---|---|---|
| **① ポスターが揃った節** | **作品ポスター2枚だけ。** 枠も日付も見出しも文字も描かない | `/sections/posters/` |
| **② ポスターが無い節** | **生成ポスター2枚。** ジャンルの色と絵柄に作品名と公開年を組んだ自前の絵 | `/sections/tiles/` |
| **③ どちらも作れない節** | 日付バッジ＋取り上げた作品名・公開年の**枠つきカード** | `/sections/` |

実測（2026-08-28・記事11本）: **ポスター39節 / 生成ポスター15節 / 文字だけ0節**。

②は 2026-08-28 に足した。それまで **U-NEXT の記事は全節が③**で、
絵が1枚も無いうえに**導線リンクにもなっていなかった**（③はリンクで包まない）。
①②③のどれになっても、読者から見た記事の作りは変わらない。

#### 生成ポスター（②）について

**大きさもレイアウトも導線リンクも、作品ポスター（①）と1つも違わない。**
480×720 で2枚並び、Amazon のビデオ内検索へのリンクで包む。CSS も共有している
（`styles/global.css` の `/sections/posters/` と `/sections/tiles/`）。
**配信元によって記事の見た目が食い違わない**ようにするため。

| | |
|---|---|
| 絵柄と色 | `scripts/genre-art.mjs` の**ジャンル別の絵柄**（表のサムネイルと同じもの） |
| 描く文字 | **作品名と公開年だけ。** 日付と節の主題は描かない |
| 権利 | **第三者の画像を1枚も使っていない。** 許諾も出典表記もURLの失効も無い |
| コード | `make-sections.mjs` の `buildTileSvg()` |

> **生成ポスターにだけ作品名を描いているのはなぜか。**
> ポスターは絵柄で作品が分かるが、ジャンルの絵だけでは**何のリンクか分からない**。
> リンクである以上、押す前に行き先が分かる必要がある。
> 下の「絵の側に文字を描かない」原則より、こちらを優先した。

> **どの外部データベースを導入しても、②は無くならない。**
> U-NEXT 台帳776件のうち 音楽・ライブ111 + 舞台・演劇57 + 報道45 = **213件（27%）**は、
> 映画データベースに存在しない種類の作品（コンサート映像・舞台中継など）。
> ②は「ポスターが取れるまでの間に合わせ」ではなく、**常時3割を支える土台**。

**絵の側に文字を描かないのは、すぐ上の小見出しと重複するから。**
日付も主題も作品名も見出しに書いてある。画像にも入れると同じ文字が2回出る。
文字情報は**代替テキスト（alt）とすぐ下の表**に残っているので、
読者にも検索エンジンにも伝わる情報は減らない。

同じ理由で、**文字だけの版からも見出しを外してある。**
描くのは日付と「取り上げた作品」だけ（見出しに必ずしも書かれていない情報）。

### 何が選ばれるか

**その段落の地の文が実際に取り上げた作品を、先頭から2本。**
節の全作品を並べるとすぐ上の表と同じものが二度出て過密になるため、
**2本だけ**にしている。本数は `MAX_HIGHLIGHT` で変えられる。

選び方は「地の文に最初に出てくる順」。読者が読む直前の文章と画像の中身が一致する。
地の文がどの作品にも触れていない段落は、評価の高い順で代替する。

### ポスターが無くても崩れない

ポスターも生成ポスターも、**その節の2本ぶんが揃ったときだけ**使う。
1枚だけ欠けた状態で並べると、片方だけ絵という中途半端な見た目になるため。

ポスター（①）が付かないのは次の場合。

- **U-NEXT 由来の作品**（メニュー経由で集めているので画像が付いてこない。台帳776件すべて）
- **APIがポスターを持っていない作品**（題名を書いただけのSVGが返る。使わない）
- URLが失効している／取得に失敗した（下の11節）

このとき②に落ちる。②も作れないのは、**表の作品名が収集ログのどれとも一致せず、
ジャンルが引けないとき**（人が記事を手直しして題名が変わった場合など）。
そこだけ③になる。

> **文字だけの版（③）は必ず保守すること。** ②が自前の生成物である以上
> 消える理由は無いが、③は「画像の仕組みを全部止めても記事が成立する」という
> 最後の足場になっている。コードは `make-sections.mjs` の `buildSvg()`。

### ポスターはアフィリエイトの導線を兼ねる

ポスターは **Amazonのビデオ内検索（レンタル・購入）へのリンク**で包んである。

```markdown
[![Free!（2013年）](/sections/posters/…-1.webp)](https://www.amazon.co.jp/s?k=Free%21&i=instant-video)
```

- トラッキングIDは**記事に焼き込まない。** ビルド時に
  `plugins/rehype-affiliate.ts` が `tag=` と `rel="sponsored"` を付ける
- リンク先を変えるのは `site/scripts/posters.mjs` の `posterLink()` 1か所
- **U-NEXT の提携が通ったら**、リンク先を U-NEXT の検索URLに替えるだけでよい。
  LinkSwitch がブラウザ側で自動変換するのでIDは要らない（[AFFILIATE.md](./AFFILIATE.md)）

なぜ Amazon かというと、対象4社のうち**アフィリエイトが成立するのが Amazon だけ**
だから（Netflix は提携先が無い、Disney+ はクローズド、Apple TV+ は招待制）。
サービスを問わず全作品に出せるので、ポスターが出る節すべてが導線になる。

### 対象になる段落

**日付の `##` 見出しの配下にある表**が対象。`###` の小見出しで分かれている場合は
小見出しごとに1枚できる。「全終了作品リスト」「まとめ」には入らない。

表の列構成は記事タイプによって違う（4列と3列）が、
**見出し行から「作品」列を探す**ので、どちらでも動く。

**シリーズ記事（`--type series`）だけは日付を見ない。** 保存版なので見出しに日付を
書かない決まりで、上の規則のままだと節が0件になり、本文に画像が1枚も入らなかった
（2026-09-01 に修正）。**日付見出しを1つも持たない記事に限って**、見出しの形を問わず
「作品」列のある表を節として拾う。「他のサービスで探す」「まとめ」は表が無いので入らない。

> 日付見出しを持つ記事の見え方は変わらない。あちらは節が1つ以上取れるので、
> この拾い直しに入らない。

### 記事を書いたら1度だけ実行する

画像そのものはビルド時に自動生成されるが、**記事への `![…]()` の挿し込みだけは
明示的に実行する**。ビルドが記事ファイルを書き換えるのは避けたいため。

```powershell
cd C:\Users\grate\brog\site
npm run sections -- --write
```

何度実行しても同じ結果になる（既にある行を書き換えるだけ）。

> 画像のファイル名は**見出しのハッシュ**にしてある。
> 節を並べ替えても参照が壊れない。

### あとから画像が付いたら差し替わる（`images` ワークフロー）

**どの版になるかは記事を書いた日のデータで決まる。**
告知（`kind: upcoming`）から書いた記事は**配信が始まる前**なので作品がどこにも無く、
画像の経路が空振りして③（文字だけ）で出る。実測: 2026年9月の Prime Video 告知84件のうち
**47件が画像なし**、その結果 `2026-09-upcoming-*` の7節が③だった。

ところが**配信が始まれば配信APIが同じ作品を返す。**
`npm run backfill:images` が告知イベントに画像を入れる（[ANNOUNCEMENTS.md 4-3](./ANNOUNCEMENTS.md)）ので、
翌日のビルドでは①が作れるようになる。**このとき記事はまだ③を指したまま**で、
放っておくと2つのことが同時に起きる。

| | 起きること |
|---|---|
| 1 | 差し替えが起きない。いつまでも文字だけのカードのまま |
| 2 | **本番の絵が消える。** ①を作った回は③を作らないので、記事が指す `.jpg` がどこにも無くなる |

2 が見つけにくい。`public/sections/` は git に入れず**ビルドのたびに作り直す**ので、
手元は前の回の残りが居座って気づけないが、**Cloudflare のビルドはまっさらなので本番だけ 404 になる。**

**どちらも自動で塞いである。**

| 誰が | いつ | 何をするか |
|---|---|---|
| `.github/workflows/images.yml` | 毎日 05:30 JST | `npm run sections -- --write` を回して**記事の参照を新しい版に差し替え、コミットする** |
| `make-sections.mjs`（`--write` なし＝ビルド） | ビルドのたび | **記事がいま指している画像も作り直す。** 差し替えが commit されるまで本番の絵が消えない |

ビルドの出力にも状態が出る。**差し替え待ちがあれば必ず名前が出る**ので、
手元で気づいたときは `--write` を打てばよい（毎日のワークフローを待たなくてよい）。

```
セクション画像: 164枚を生成（ポスターの節 56 / 生成ポスターの節 23 / 文字だけの節 7）
差し替え待ちの節: 1件
  2026-09-upcoming-prime-video-japanese  9月1日：「旅と日々」「白夜行」…  文字だけ → ポスター
  → cd site && npm run sections -- --write で記事に反映されます
    （それまでは記事がいま指している画像も作り直すので、本番の絵は消えません: 1枚）
```

> ★ **①だけは作り直せない。** ②③は自前の生成物なので必ず描けるが、
> ポスターは第三者の画像なので、取得できなければ手元に無い。
> 記事が①を指したまま取得に失敗した節は、警告だけが出る（11節の失効の話と同じ）。

> ★ **`--write` だけを単体で走らせたときは `data/image-manifest.json` を commit しない。**
> このスクリプトは台帳を「自分が使った作品だけ」に絞って書き、
> 表のサムネイルと作品ページのぶんは**このあと走る `make-thumbs.mjs` が足し戻す**。
> `npm run build`（prebuild）は両方をこの順で呼ぶので揃うが、
> `images.yml` は台帳を `git checkout` で戻してから commit している。

### 手元で確認するときのフラグ

```powershell
npm run sections -- --refresh     # キャッシュを無視してポスターを取り直す
npm run sections -- --no-posters  # ①を使わない → 全節が②（生成ポスター）になる
npm run sections -- --no-posters --no-tiles   # ①②とも使わない → 全節が③（文字だけ）
```

`--no-posters` は**「配信APIとの契約を終えたらどう見えるか」**の確認に使う。
2つ重ねると、画像の仕組みを全部止めた姿になる。

## 11. 作品ポスターの取り扱い（許諾・取り直し・契約終了）

セクション画像に載せている作品ポスターは、配信API（Movie of the Night）が
返す画像を**ビルド時に取得して、自分のドメインから配信**している。

### 許諾は取ってある（2026-08-25）

規約には再ホストの明示が無く、「データを再配布してはならない」という条項が
あったため、実装前に提供元へ照会した。**回答は "Yes, you can."**
併せて「**画像は最低でも6ヶ月ごとに取り直すこと**」を推奨された。

> 契約終了後は画像を使えない条項について「規約は更新された」との回答があった。
> **更新後の規約は未確認。** 変更点は
> https://developers.movieofthenight.com/terms-and-conditions で確認すること。
> このリポジトリは「契約終了時には消す」という**厳しい側の前提**で組んである
> （下の「契約を終えるとき」）。

### なぜホットリンクにしないのか

APIが返す画像URLは**署名付きで、6〜12ヶ月で失効する**。
読者のブラウザに直接読ませると、期限が切れた時点で**過去記事の画像が一斉に壊れる。**
読者のアクセスがそのまま提供元のCDN帯域（無料枠 1GB/月）を食うという問題もある。

ビルド時に1回取得する方式なら、消費は**1回のビルドあたり約3.3MB**（実測・58枚）。
読者が何人来ても増えない。

### 取得したものは git に入れない

| 置き場所 | 中身 | git |
|---|---|---|
| `site/.image-cache/` | 取得した元画像 | **入れない**（`.gitignore` 済み） |
| `site/public/sections/posters/` | 記事に出すポスター（WebP） | **入れない**（毎ビルド再生成） |
| `site/public/sections/tiles/` | 生成ポスター（自前の絵） | **入れない**（毎ビルド再生成） |
| `site/public/sections/` | 文字だけの版のカード画像 | **入れない**（毎ビルド再生成） |
| `site/public/thumbs/` | 表に出すサムネイルとジャンル汎用画像 | **入れない**（毎ビルド再生成） |
| `data/image-manifest.json` | 使っている作品のURLの台帳 | **入れる** |

**コミットすると git の履歴から消せなくなる。**
提供元には「ビルドごとに取得する」と説明して許諾を得ており、
契約終了後は画像を使えない。ここは変えないこと。

Cloudflare のビルド環境は毎回まっさらなので、キャッシュは効かない（毎回取得する）。
`.image-cache/` は手元で同じ画像を何度も落とさないためだけのもので、消しても動く。

### 6ヶ月ごとに取り直す

```powershell
cd C:\Users\grate\brog
npm run refresh:images            # 期限が90日以内に迫ったものだけ
npm run refresh:images -- --dry-run   # APIを叩かず対象だけ見る
```

**1作品につきAPIリクエストを1消費する**（無料枠 500回/月）。
そのため対象は**サイトが実際に使っている作品だけ**に絞ってある。
その一覧は `npm run sections` と `npm run thumbs` が
`data/image-manifest.json` に書き出す（2026-08-25 時点で**590件**）。

> ★ **表のサムネイルを入れた時点で、台帳は58件から590件に増えた**（2026-08-25）。
>   全部を取り直すと無料枠（500回/月）を超える。既定では
>   「期限が90日以内」に絞り、1回あたり300件で止まるので、
>   **2回に分けて回すことになる**（実際は失効日がばらけるので自然に分かれる）。
>   月をまたいで実行すること。残量は `data/api-usage.json` で見られる。

`npm run sections` は期限が60日を切ると警告を出す。**警告が出たら実行する。**

```
! 画像URLの期限が近い作品が 12件。最短 2026-12-21
  → npm run refresh:images で取り直してください
```

> **失効しても記事は壊れない。** その節が文字だけの版に戻るだけ。
> 気づかないまま放置すると絵が減っていく、という壊れ方をする。

### 契約を終えるとき

```powershell
cd C:\Users\grate\brog\site
npm run posters:purge          # キャッシュとセクション画像を消す
npm run sections -- --write    # 生成ポスターに置き換える（--write が要る）
```

> ★ **`--write` を忘れないこと。** 記事に残っている `/sections/posters/…` の参照は
>   消したファイルを指しているので、書き換えないと画像が壊れたままになる。
>
> ★ **サイトの見た目はほとんど変わらない。** ポスターが生成ポスターに置き換わるだけで、
>   大きさもレイアウトも導線も同じ（10節）。契約終了の影響は
>   「作品の絵が、ジャンルの絵になる」に収まる。

そのうえで `data/image-manifest.json` を削除し、コミットする。

### ポスターは動画に使わない（2026-08-25 決定）

YouTube ショート等の**動画にポスターを載せてはいけない。**
サイトに載せているからといって、そのまま動画に持ち出せる素材ではない。
理由は3つ、重い順に:

1. **このリポジトリは「契約を終えたら画像を全部消す」前提で組んである**（すぐ上）。
   **公開した動画は同じようには消せない。** 拡散・引用・保存されたあとでは
   取り返しがつかず、purge の手順が意味を持たなくなる
2. 提供元から得た許諾は「**自分のドメインから再ホストしてよいか**」への回答であって、
   第三者プラットフォームへの動画素材としての投稿は含まれていない
3. YouTube へのアップロードは、YouTube に対する**再許諾可能なライセンスの付与**を意味する。
   再ホストの許可しか持っていない画像について、その許諾は出せない

なお **ポスターの著作権は提供元ではなく配給元にある。** 提供元の回答は自社規約の
範囲の話で、原権利者の権利は別のレイヤー。サイト上の紹介利用と違い、動画は
権利者側が自動照合と申立ての手段を持っており、申立てはチャンネル単位で累積する。

> **動画で使うのは自前生成の画像だけ。** カット画像は
> `site/scripts/make-shorts.mjs` が台本から作る（1080×1920）。
> 第三者の権利が一切絡まず、`make-cards.mjs` / `make-sections.mjs` と同じ手法。
> 運用は [shorts/README.md](../shorts/README.md)。

## 12. 記事のヘッダー画像（frontmatter の `heroImage`）

記事1本に1枚。**いまは一覧カードの左サムネイルにだけ出る。**

| 出る場所 | 大きさ | 部品 |
|---|---|---|
| 記事一覧のカードの左サムネイル | 72×72（正方形で切り抜き） | `PostCard.astro` |
| 右の枠「最新記事」の左サムネイル | 60×60 | `FollowRail.astro` |
| 右の枠「シリーズから探す」の左サムネイル | 60×60 | `SeriesRail.astro`（2026-08-31 追加） |
| ~~記事ページの見出し（h1）の直上~~ | **2026-08-25 に非表示**（下記） | `LeadImage.astro` |

> **どこも同じ1枚を、同じ部品（`Thumb.astro`）で出している。**
> 場所ごとの画像は作らないこと。増やしても読者には同じ記事に見えるうえ、
> 取り直し（`npm run refresh:images`）の対象だけが増える。

自動処理は**必ず1枚を用意する**（ポスターが取れなければジャンル別の汎用画像）。
それでも未設定の記事があればカードは**カテゴリ色のタイル**になり、
レイアウトは崩れない。

### 記事の冒頭には出していない（2026-08-25）

表の全作品にサムネイル付きのリンクが並ぶようになり（13節）、
冒頭にもう1枚ポスターを置く意味が無くなった。
**記事の本題（表）に届くまでのスクロールを削るほうが効く。**

生成（`npm run sections`）も frontmatter の `heroImage` も**そのまま**なので、
カードのサムネイルは今までどおり出る。

> **また出したくなったら**、`site/src/pages/posts/[...slug].astro` の
> `<h1>` の直前に `<LeadImage src={post.data.heroImage} alt="" />` を戻して
> import を足すだけでよい。理由と手順はそのファイルのコメントにも書いてある。
> **`LeadImage.astro` は常設ページが今も使っているので消さないこと。**

### 自動で選ばれる（記事を書いたら勝手に入る）

`npm run sections -- --write` が frontmatter に書き込む。優先順は2つ。

> ★ **日付見出しを持たない記事にも入る**（2026-08-30 に対応）。
> 本文のセクション画像は `## ◯月◯日…` で始まる見出しの節にだけ挿しているが、
> ヘッダー画像はその判定に**巻き込まない**。
> シリーズ記事（`--type series`）は保存版なので見出しに日付を書かず、
> 以前は**記事ごと処理から外れてカードの絵だけが付かなかった**。
> いまはヘッダー画像だけ、記事中の**すべての表**（`workTables()`）から選ぶ。
> **セクション画像の対象は広げていない。**「全終了作品リスト」のような節に
> わざと画像を入れていない既存記事の見た目を変えないため。

1. **記事タイトルが名指しした作品**のポスター（**タイトルに出てくる順**）
2. 取れなければ、**記事に最初に出てくる作品**のポスター

**この2つで尽きたら、ジャンル別の汎用画像**（13節の絵柄をポスター大にしたもの）。
記事の全作品を最後まで舐めることはしない。

一致は前方一致で見る。記事タイトルが「…クレヨンしんちゃん劇場版」で
作品名が「クレヨンしんちゃん オラたちの恐竜日記」でも拾えるようにするため。
**4文字以上**一致したものを候補にする（`HERO_MATCH_MIN`）。
それより短い題名は、**題名まるごとが区切り（`・` `と` `｜` など）に挟まれて
出ているときだけ**候補になる。「日常系アニメ」の中の「日常」は拾わない。

> **同じ作品を2本の記事のヘッダーには使わない。** 先に取った記事が勝ち、
> 後の記事は次の候補へ送られる。一覧でカードが縦に並ぶので、
> 隣り合う2枚が同じ絵だと更新が止まって見えるため。

> **ポスターが1枚も取れない記事（U-NEXTだけの記事）は汎用画像になる。**
> U-NEXT 由来の作品には画像が1枚も無いので、この2本がそれに当たる。
> 絵柄は**その記事の作品に多いジャンル**から選ぶ（記事全体でジャンルを数える。
> 集合をまとめて `genreKeyOf()` に通さないこと。あれは rank の小さいものが勝つので、
> どこかに1本ホラーがあるだけで記事全体がホラー扱いになる）。
> 汎用画像どうしも絵柄が重ならないようにしてあり、
> 取られていたらその記事の2番目に多いジャンルへずらす。

#### ここで一度踏んだこと（2026-08-28）

新着の最新2件が**どちらも「ディア・ファミリー」**の絵になっていた。原因は2つ。

| 記事 | 何が起きたか | 直し方 |
|---|---|---|
| 邦画・国内ドラマ | タイトルは「｜**告白**・来るとディア・ファミリー」なのに、候補を**一致の長さ順**に並べていたため、最後に書いた9文字の「ディア・ファミリー」が2文字の「告白」に勝っていた（「告白」は4文字未満で候補にすら入らなかった） | 並びを**タイトルでの登場順**に変更。短い題名も区切り付きなら拾う |
| U-NEXT | U-NEXTの作品にはポスターが無い（配信情報の出どころが別で画像を持たない）。候補が全滅したあと**記事の全作品へ落ちる3段目**があったため、記事が一言も触れていない「ディア・ファミリー」に行き着いていた | 3段目を**削除**。候補が尽きたら**ジャンル別の汎用画像** |

> **記事タイトルに作品名を書くときは、見せたい作品を先に書くこと。**
> ヘッダー画像はその順に従う。

> 「007シリーズ5作と五等分の花嫁」のように**シリーズ名**で書いた部分は
> 作品名と一致しないので拾えない（作品名は「007 カジノ・ロワイヤル」）。
> この記事は「五等分の花嫁」の絵になる。先頭の絵にしたいなら
> 作品名そのものをタイトルに書くか、下の手で差し替える方法を使う。

### 気に入らない絵は手で差し替えてよい

**frontmatter に書いてある値が最優先。** 自動処理は
`heroImage` が空のとき、または自分が入れた `/heroes/<スラッグ>.webp` のときしか触らない。
**別のパスを書いた瞬間、その記事は自動処理の対象から外れる。**

> ★ いま差し替えが効くのは**一覧カードの左サムネイル**。
>   記事の冒頭には出ない（上記のとおり非表示にしてある）。

```yaml
heroImage: '/my-hero.jpg'   # site/public/my-hero.jpg を置く
```

好きな画像を `site/public/` に置いて、そのパスを書けばよい。
`site/public/` はビルドで最適化されないので、**置く前に自分で軽くしておくこと**。

> 別の作品のポスターにしたいだけなら、`/heroes/…` ではなく
> `/sections/posters/…`（その記事の節に出ているポスター）を指してもよい。
> ファイル名は記事の本文に書いてある。

## 13. 表の作品サムネイル（と、画像が無いときのジャンル汎用画像）

記事と常設ページの**表の各行**に、48×72 の小さな作品画像が出る。
絵と作品名はひとつのリンクで、押すとその作品のページへ飛ぶ
（送り先の決め方は [AFFILIATE.md](./AFFILIATE.md) の「表の作品リンク」）。

### なぜ表に絵を入れたか

作品はすべて表に載っているのに、表が文字だけだと
「なんとなく気になった作品」を掴む手掛かりが無い。
絵が1枚あるだけで、行そのものが導線になる。

### 何もしなくてよい（ビルド時に自動生成される）

    npm run build            前処理で自動的に走る
    npm run thumbs           単体で試す
    npm run thumbs -- --refresh      キャッシュを無視して取り直す
    npm run thumbs -- --no-posters   取得せず全部ジャンル汎用画像にする
    npm run thumbs -- --audit        ジャンル名の取りこぼしを一覧する

出力は `site/public/thumbs/`。

    <作品ID>.webp      配信APIのポスターを縮めたもの
    genre-<key>.webp   ジャンル別の汎用画像（26枚）

### 画像が無い作品はジャンル別の汎用画像になる

**U-NEXT 由来の作品718件には画像が1枚も無い**（収集がメニュー経由で、
APIのように画像URLが付いてこない）。全部を同じ色のタイルで埋めると
表が一色に潰れるので、**ジャンルごとに絵柄と色を変えた画像**を用意してある。

    定義   site/scripts/genre-art.mjs の GENRE_ART
    絵柄   同ファイルの MOTIF（100×150 の座標系で描く図形）

作中の画像もポスターも使わない**幾何学図形だけ**なので、
許諾も出典表記も要らず、URLの失効も無い（9節のカード画像と同じ考え方）。

| 変えたいもの | 直す場所 |
|---|---|
| ジャンルの色 | `GENRE_ART` の `hue`（彩度と明度は全ジャンル共通。色相だけ変える） |
| ジャンルの絵柄 | `MOTIF` の該当キー |
| ジャンルを増やす | `GENRE_ART` に1行足す（`aliases` に収集データのジャンル名） |
| どのジャンルを優先するか | `GENRE_ART` の `rank`（**小さいほうが勝つ**） |

> **`rank` を触るときの注意。** `Drama` と `Comedy` はほぼ全作品に付いてくる。
> 順位を上げると表がドラマ一色になる。特徴的なジャンル（SF・ホラーなど）を
> 上に置くこと。

> **絵柄に文字を入れないこと。** 48×72 では読めないうえ、SVG のテキストは
> 描画するマシンのフォントで出るので Cloudflare（Linux）では豆腐になる
> （9節と同じ理由）。**要素は3つまで、線は太く。**細い線は潰れる。

### 大きさを変えるとき

**4か所を揃える。1か所だけ直すとずれる。**

    表示の寸法   site/src/styles/global.css の .work-thumb
    記事側の属性 site/plugins/rehype-work-links.ts の THUMB
    常設側の属性 site/src/components/WorkTable.astro の THUMB
    書き出す実寸 site/scripts/make-thumbs.mjs の THUMB（表示の2倍）

`width` / `height` を属性に書いているのは、画像が届くまで行の高さが
決まらないと**表全体がガタつく**ため。消さないこと。

### ビルドの負荷

対象は715作品、うち画像を取得するのは590件（実測 2026-08-25）。
Cloudflare のビルドは毎回まっさらなので毎回取得する。
同時8本で走らせて1分ほど、書き出しは合計3.5MB。

> 対象の決め方は `make-thumbs.mjs` の `worksToRender()`。
> **常設ページの条件は `src/lib/events-data.ts` から書き写してある。**
> 片方だけ直すと、ページに出るのに絵が無い作品が生まれる。


## 画像ファイルの置き場所

| 置き場所 | 最適化 | 使うもの |
|---|---|---|
| `site/src/assets/` | **される**（WebP変換・srcset自動） | 記事やページに `<Image>` で載せる画像 |
| `site/public/` | されない（そのまま配信） | favicon、OG画像、CSSの `url()` から参照する素材 |

**判断基準はひとつ。`<Image>` で読むなら `src/assets/`、
URLで直接指す必要があるなら `public/`。**

### 環境について（確認済み）

- 画像最適化（sharp）はインストール済み。Cloudflare のビルド環境（Linux）でも動く
- `.gitattributes` で画像はバイナリ指定済み。改行変換で壊れることはない
- `/_astro/` 配下（最適化後の画像）には `site/public/_headers` で永久キャッシュを設定済み

## 14. 作品画像をどこから持ってくるか（2026-08-28 調査）

**U-NEXT 由来の作品には画像が付いてこない**（台帳776件すべて）。
これを外部から埋められないかを調べた結論をここに置く。
**同じ検討を繰り返さないために、採らなかった道も理由ごと残す。**

### 結論

| 案 | 商用利用 | 入手条件 | 導線との整合 | カバー範囲 | 判断 |
|---|---|---|---|---|---|
| **自前の生成ポスター** | 権利が絡まない | 即日 | ◎ | **100%** | ✅ **これを採った**（10節） |
| **Amazon Creators API** | ✅ 明示のライセンス | **売上3件が必要** | ◎ 導線が既に Amazon | 中〜高 | 🔶 実績が出たら |
| TMDB | 🔶 商用ライセンスが要る | 要照会 | — | 〜63% | 🔶 費用を聞くだけ聞く |
| 楽天ブックスAPI | ✅ 即提携できる | 即日 | ✗ 楽天リンクの併記が必須 | 中 | ❌ 採らない |
| U-NEXT から取得 | ❌ | — | — | — | ❌ 採らない |

### U-NEXT との提携では解決しない

U-NEXT のアフィリエイト掲載ガイドラインに明記がある。

> 配信中作品の画像・動画素材について、U-NEXTからはお渡ししておらず、
> パートナー様にて集められた画像・動画等を使用された場合の責任を、弊社は一切負いません

**二重の意味で行き止まりになる。**

1. **提携しても素材は増えない。** ASP が配るのは U-NEXT のロゴとキャンペーンバナーだけで、
   作品単位の画像は存在しない
2. **U-NEXT は許諾を出せる立場にない。** 作品ポスターの権利は配給元・製作委員会にある。
   上の一文は許諾ではなく**免責**で、「こちらは関知しない」と言っているだけ

> **ASP との提携は進める価値があるが、それは収益の話**（[AFFILIATE.md](./AFFILIATE.md)）。
> **画像の問題とは無関係**なので、切り分けて考えること。

### 逆に、ここは開いている

**作品名は事実で、事実に著作権は無い。U-NEXT 以外から画像を引く限り、
U-NEXT の規約は一切かからない。** Netflix / Prime でやっていることと構造が同じで、
法的リスクの質は増えない。問題は「どこから引くか」だけになる。

### なぜ自前の生成ポスターを土台に選んだか

**どの外部データベースを導入しても3割は埋まらないから。**
U-NEXT 台帳776件の内訳（実測）:

```
113 洋画      111 音楽・ライブ   102 邦画       85 韓流・アジア
 71 TV番組     61 アニメ          57 舞台・演劇   45 報道・スペシャル
 45 海外ドラマ  44 国内ドラマ      42 キッズ
```

**音楽・ライブ111 + 舞台・演劇57 + 報道45 = 213件（27%）。**
「モーニング娘｡ コンサートツアー2006春」も「森山良子 デビュー45周年記念プレミアムLIVE」も、
TMDB にもどの映画データベースにも**存在しない**。
2026-08 の配信終了記事は6節中2節がこれだった。

**フォールバックは何をやっても永久に必要**で、そこが常時3割を占める。
だからフォールバックの質を上げるのが投資効率で最も高い。
権利の検討がゼロで、今日から着手できるという利点もある。

### Amazon が次点である理由（構造的に一番きれいに嵌まる）

- **導線がもう Amazon になっている。** `posterLink()` はビデオ内検索へリンクしている
- Amazon のライセンスは「Program Content を自サイトに表示する限定ライセンス」で、
  **Amazon リンクとセットで出すこと**が条件 → 既存の形と完全に一致し、
  記事に新しいリンクが1本も増えない
- **権利の筋が一番きれい。** Amazon は商品を売る当事者で、商品画像の掲載許諾を出す立場にある。
  「画像の所有権は主張しない」と明言する集約サービスとは質が違う

**障壁は2つ。**

1. **売上3件で API 資格**（流入ゼロ→売上ゼロ→API使えず、のにわとり卵）
2. **PA-API v5 は 2026-05-15 に終了済み。** いま使うなら **Creators API**
   （[AFFILIATE.md](./AFFILIATE.md) はまだ PA-API 前提の記述のまま）

### 楽天を採らない理由

規約上は使える（アフィリエイト目的の商用利用は明示的に許可されている）。
ただし**「リンク先が楽天市場だとわかる掲載」が必須**なので、
U-NEXT の記事に楽天リンクが混ざる。
[AFFILIATE.md 5節](./AFFILIATE.md) の「複数を並べない／選択肢を増やすと読者が選べなくなる」と
正面から衝突する。

加えて楽天ウェブサービスの規約は「別途定める方法以外での複製」を禁じており、
**自ドメインへの再ホストには個別の照会が要る**（Movie of the Night のときと同じ手順）。

### TMDB について

`.env.example` の「無料枠は非商用限定」という記述は**いまも正しい**。
判定は "commercial if the primary purpose is to create revenue for the benefit of the owner"。

ただし `sales@themoviedb.org` という窓口があり、
**Movie of the Night に照会して "Yes, you can." を貰った実績がある以上、同じ手が使える。**
聞くだけならタダなので、費用だけ確認しておく価値はある。

なお TMDB は**「画像の所有権は主張しない」と明言している** = API のライセンスであって
著作権のライセンスではない。これは Movie of the Night と同じ構造で、
**当サイトが既に受け入れているリスク**。増えるものではないが、減るものでもない。

### 採らないと決めたこと

| | 理由 |
|---|---|
| **U-NEXT の作品ページ画像を取得** | [UNEXT.md 4節](./UNEXT.md) の「表現は取らない」に反する。かつリポジトリは public なので「取っただけ・非公開」が成立しない |
| **「引用」で押し切る** | 著作権法32条は主従関係・必然性・明瞭区別・出所明示が要件。装飾目的のポスター貼付は引用にならない。広告のあるサイトでは特に厳しい |
| **Wikipedia のポスター** | 英語版に載っているのは米国フェアユースによるもの。Commons 外なので再利用できない |
| **生成AIで「それらしい」ポスターを作る** | 作品を誤認させる。読者を欺くことになる |

## 素材のライセンス（重要）

**このサイトは広告を載せる＝商用サイト。** 素材は必ず商用利用可のものを使う。

### 使ってはいけないもの

| | 理由 |
|---|---|
| 映画・ドラマのポスター、場面写真、キービジュアル**を自分で拾ってきて使う** | 著作権。配信ブログで最も起きやすい事故 |
| ライセンスを確認していない写真素材 | **現在のヘッダーバナーの映画館写真も、出所と商用可否を確認しておくこと** |
| Netflix / Disney+ / Prime Video / Apple TV+ のロゴ | 商標＋各社ブランドガイドライン。サービス名は**テキストのまま**が安全 |
| Canva の無料素材を「ロゴ・商標として単独で」使う | Canva のライセンス上禁止（デザインの一部ならOK） |

> **唯一の例外が、配信APIが返す作品ポスター。**
> 提供元（Movie of the Night）に照会して再ホストの許諾を得ており、
> 帰属表示もサイトと各記事に出している。**API経由で取得したものだけ**が対象で、
> 検索で拾ってきたポスターは対象外。運用は [11節](#11-作品ポスターの取り扱い許諾取り直し契約終了)。

### 使える無料素材

| サイト | 内容 | ライセンス |
|---|---|---|
| unDraw（undraw.co） | イラスト。色を `--accent` に合わせて書き出せる | 帰属不要・商用可 |
| Hero Patterns（heropatterns.com） | 背景パターンSVG | CC0 |
| Unsplash / Pexels | 写真 | 帰属不要・商用可 |
| O-DAN（o-dan.net） | 上記を日本語で横断検索 | 各サイトの規約に従う |
| Lucide / Tabler Icons | アイコン | ISC / MIT |
| Google Fonts | フォント | OFL |

> **日本語Webフォントは重い（数MB）。** ロゴに使いたい場合は、
> Google Fonts で組んだ文字を**アウトライン化して SVG に埋める**。
> Webフォントの読み込みがゼロになる。

## 困ったとき

### 画像を差し替えたのに古いまま表示される

**`npm run dev` でだけ起きる。** 開発サーバーの画像URL（`/_image?href=...`）は
ファイルを差し替えても変わらないので、ブラウザが古い画像を持ち続ける。

1. ブラウザで**ハードリロード**（Windows: `Ctrl` + `Shift` + `R`）
2. それでも直らなければ dev を止めてキャッシュを消し、開き直す

```powershell
cd C:\Users\grate\brog\site
# dev サーバーを Ctrl+C で止めてから実行する
Remove-Item -Recurse -Force node_modules\.vite, .astro -ErrorAction SilentlyContinue
npm run dev
```

> **本番では起きない。** ビルド後のファイル名には内容のハッシュが入る
> （`header-banner.BuN91i8f_276sbD.webp`）ので、中身が変われば URL も変わる。
> ただし `public/` に置いたもの（`og-default.jpg`・favicon）はファイル名が
> 固定なので、本番でもブラウザやSNSのキャッシュが残ることがある。

### `Could not resolve '../assets/xxx.png'` でビルドが落ちる

`site/src/assets/` のファイル名が `import` 側と**完全一致していない。**
よくあるのは**拡張子の前の半角スペース**（`header-banner .png`）で、
見た目では気づけない。ファイル一覧で名前を確認して直す。

### `widths` に元画像より大きい数値を指定してビルドが落ちる

`<Image>` の `widths` は**元画像の幅を超えられない。**
1200px 未満で書き出した画像なら、この数値を下げる。

### 収集し直したのに、記事の表のリンクとサムネイルが古いまま

**Astro が記事の描画結果をキャッシュしている。**
表のリンクはビルド時に貼っているが、記事の `.md` が変わらないかぎり
Astro は「この記事は変わっていない」と判断して前回の結果を使い回す。

```powershell
cd C:\Users\grate\brog\site
Remove-Item -Recurse -Force node_modules\.astro, dist -ErrorAction SilentlyContinue
npm run build
```

> ★ 消すのは **`node_modules\.astro`**（中の `data-store.json` が本体）。
>   ルートの `.astro\` は型定義なので、そちらを消しても記事は作り直されない。

> **公開されるものは常に最新。** Cloudflare のビルドは毎回まっさらなので、
> このキャッシュは存在しない。手元で確認するときだけ気をつける。

### 表に絵が出ない（作品名のリンクだけ出る）

`site/public/thumbs/` が無い。`npm run thumbs` を実行する
（`npm run build` なら前処理で自動的に走る）。
**絵が無くてもリンクと表は成立する**ので、ビルドは落ちない。

### 作品検索を打っても何も起きない

常設ページ（`/leaving/…` `/arrivals/…`）の検索窓は
**JavaScript が動かないと出ない**（出ても押せない窓を見せないため）。
出ているのに当たらない場合は、`site/src/lib/normalize.ts` の
ならし方だけを直す。**ビルド時と実行時が同じ関数を使っている**ので、
片方だけ変えると全件外れる。
