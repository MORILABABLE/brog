# 翌月ラインナップの告知（配信開始「予定」の収集）

最終更新: 2026-08-30（Netflix・在庫・画像の後入れを追加）

配信各社が前月末に出す「翌月の配信開始ラインナップ」を読み、
**配信が始まる前に記事を書く**ための仕組み。

> **なぜ要るのか。** Streaming Availability API の `upcoming`（配信開始予定）は、
> 日本のカタログでは4社とも **0件のまま**（`theme.yaml` の実測）。
> 一方で各社は前月末に翌月のラインナップを自社サイトで告知している。
> 先出しの記事を書ける素材は、いまのところここにしかない。

---

## 1. コマンド

| コマンド | 内容 |
|---|---|
| `npm run collect:announce -- --check` | 告知が**出ているか**だけ見る。何も書かない・APIを使わない |
| `npm run collect:announce` | 翌月ぶんを取り込む（画像も用意する） |
| `npm run collect:announce -- --month 2026-09` | 月を指定する |
| `npm run collect:announce -- --dry-run` | 解析結果だけ見る |
| `npm run collect:announce -- --no-images` | 画像を取りに行かない（API消費 0） |
| `npm run backfill:images` | **配信が始まって画像が取れるようになった告知を埋める**（API消費 0） |
| `npm run stock` | **いま何が貯まっているか**を `data/UPCOMING.md` に書き直す（API消費 0） |

取り込むと `data/events/{YYYY-MM}.jsonl` に **`kind: "upcoming"`** のイベントが増える。
形は他の収集と同じなので、通知（`digest.ts`）も記事の仕組みも無改修で通る。

---

## 2. 何を取り、何を取らないか

取るのは**事実だけ**。作品名・配信開始日・見放題／独占の区分の3つ。

**紹介文と画像は取らない。**

- 紹介文は先方が書いた文章そのもので、引用の範囲を超えて使えば複製になる
- 画像は再配信の許諾が無い。記事の画像は `posters.mjs` の経路
  （Movie of the Night に照会して 2026-08-25 に許諾済み）だけを使う

記事の文章はこちらで書く。告知は「何がいつ始まるか」の一次情報としてだけ扱う。

### 相手への負荷

About Amazon の robots.txt は `User-agent: * / Crawl-delay: 10` のみで、
Disallow は無い（2026-08-28 実測）。読むのは月に1ページだが、
同じホストへの連続取得には10秒空ける（`MIN_INTERVAL_MS`）。
U-NEXT の `min_interval_ms` と同じ考え方で、**速くしたくなっても下げないこと。**

## 3. 各社の告知の出方（2026-08-30 調査）

| サービス | 出どころ | 出る時期 | 解析器 |
|---|---|---|---|
| **Prime Video** | About Amazon（`…/amazon-prime-video-new-content-{月}-{年}`） | 前月末（9月分は8月28日） | `about-amazon` |
| **Disney+** | 公式サイト（`disneyplus.disney.co.jp/recommend/{YYMM}`） | 前月25日前後〜月初 | `disney-recommend` |
| **Netflix** | 公式の新作情報（`about.netflix.com/ja/new-to-watch`） | **常時更新（ローリング窓）** | `netflix-new-to-watch` |
| U-NEXT | プレスルームの月次リリースは**止まっている** | — | **要らない**（下） |

### Disney+（2026-08-30 実装）

**日付つきURL（`/recommend/2609`）だけを読む。** 同じ内容が3か所にあるが、
読んでよいのは1つだけ。

| URL | robots.txt | 可否 |
|---|---|---|
| `disneyplus.disney.co.jp/recommend/{YYMM}` | `User-agent: *` に `/` の禁止なし | **これを読む** |
| `disneyplus.disney.co.jp/news/{年}/{MM}_recommend` | 同上（同じホスト） | 同内容。可 |
| `disneyplus.disney.co.jp/recommend/latest` | → `www.disneyplus.com` へ 301 | **読まない** |

`latest` の転送先 `www.disneyplus.com` の robots.txt は **`User-agent: * / Disallow: /`** で、
許可されているのは名指しされた検索・SNS・広告のボットだけ。
そこで `fetchAnnouncement` は **ホストをまたぐ転送を追わず、例外で止まる**
（`redirect: 'manual'`）。転送先を読みたくなったら、そのホストの robots.txt を
確かめてから `theme.yaml` の url を書き換えること。**黙って追わせてはいけない。**

★ **日付つきページは月初にならないと立たないことがある。**
2026-08-30 時点で `/recommend/2609`（9月分）は 404 で、9月の内容は
`latest`＝読めないホストにしか無かった（8月分の `/recommend/2608` は 7月25日公開）。
404 は「まだ出ていません」と出るので、**月初に `--check` をもう一度走らせる。**

ページの「配信スケジュール」以降が全ラインナップ。**第2話以降は落とす**
（放送中シリーズの毎週のエピソードが全部載るため。8月は約570行 → 24作品）。

### Netflix（2026-08-30 実装）

**月次ラインナップの「記事」は無いが、新作情報の「ページ」がある。**
`about.netflix.com/ja/new-to-watch` が一次情報・構造化・robots許可の3つを満たす。

| ホスト | robots.txt | |
|---|---|---|
| `about.netflix.com` | `User-agent: *` に `Disallow: /api/` だけ | **読める** |
| `www.netflix.com` | `User-agent: * / Disallow: /` | **読まない**（別ホスト） |

禁止は `/api/` なので**ページ本体だけを読む**。続きを取りに行くクライアント側の
リクエストは `/api/` 配下なので叩かない。結果、1回で取れるのは**先頭20件・約11日先まで**。

データは Next.js の `__NEXT_DATA__` にそのまま入っていて、HTMLの見た目に依存しない。

```
{ title1: "恋わずらい", startTime: 1788310800000, videoID: 81262894 }
```

`videoID` は Netflix の作品ID。**作品IDになる**（`announcedWorkId`）ので、
題名＋日付のハッシュより強い（配信日が後から変わっても同じ作品と分かる）。
`https://www.netflix.com/title/{videoID}` が作品ページのURLになる。

#### ★ ローリング窓なので、扱いが月次ページ型と違う

1. **毎日読んで貯める。** 月末に1回では月の前半しか取れない。
   `announce.yml` を月末だけ → **毎日**に変えたのはこのため。
2. **対象月で絞らない**（`theme.yaml` の `rolling: true`）。
   収集の既定の対象月は「翌月」なので、月の途中に翌月で絞ると、窓に入っている
   **当月ぶんが毎日そのまま捨てられる**。落としたぶんは後日どこからも拾えない。
   取り込みすぎても台帳が重複を弾くだけだが、取りこぼしは取り返しがつかない。
   月の切り分けは記事側（`shared.ts` の `isTargetMonth`）がやる。

#### 取れないもの

- **旧作のライセンス作品。** このページは新作（オリジナル中心）で、
  実測では Netflix の `new` イベントの**61%が2024年以前**の作品だった（2026-08・214件）。
  つまりこれは月次ラインナップの全部ではなく、**先出しできる部分**。
  残りは従来どおり配信APIが配信開始日に拾う。
- **ポスター。** 未配信のオリジナルは Wikidata にまだ項目が無く、
  許諾済みの画像経路（4節）が空振りする（実測 20件中0件）。
  記事の行はジャンル別の自前タイルになる。配信開始後は API が同じ `videoID` で
  返すので、そこで後入れできる（**未実装**）。

### 報道各社を使わない理由

robots.txt 上は読める（SCREEN ONLINE は `Allow: /`、RBB・モデルプレスも記事パスは可）。
使わないのは**公式のほうが確実だから**。

- 実測（SCREEN ONLINE の2026年9月ラインナップ記事）で**30〜40件の抜粋**であり全件ではない
- **出典が明記されていない**。当サイトは「◯◯が公表した公式発表にもとづきます」と書いており、
  出どころの弱い情報を同じ体裁に混ぜると記事全体の信用が落ちる
- 誤りがあれば**そのまま引き継ぐ**。公式なら誤りは公式の訂正で追える

まとめサイト（Get Freax・whats-on-netflix など）も同様に使わない。
あちらが編集して作った**データベースそのもの**で、事実の抜き出しとは別の話になる。

### ほかのサービスはどうか（2026-08-30 調査）

サービス軸で先出しを出すなら、各社にも同じ「先出しの入口」が要る。調べた結果:

| サービス | 先出しの入口 | 判断 |
|---|---|---|
| Prime Video | About Amazon の月次記事 | ✅ 実装済み |
| Disney+ | 公式の月次ページ | ✅ 実装済み（日付つきURLが立つまで404） |
| Netflix | 公式の新作情報（ローリング窓） | ✅ 実装済み |
| **U-NEXT** | **無い** | 下記 |
| **Apple TV+** | 調べていない | **作る価値が無い**。下記 |

**U-NEXT には先出しの入口が無い。** 自前収集のメニューにあるのは「新規入荷作品」＝
**すでに配信中**のものだけで、配信予定の区分が存在しない（`theme.yaml` の `unext.genres`）。
月次のプレスリリースも止まっている（下）。
ただし U-NEXT は直接収集しているので**配信開始日は当日に分かる**。
足りないのは先出しだけで、`arrivals-service --service u-next` は従来どおり書ける。

**Apple TV+ は規模が記事にならない。** 2026年8月のイベントは**合計8件**
（`new` 6 / `removed` 2）で、記事1本の下限（10件）にも届かない。
解析器を作っても書ける記事が無いので、作らない。増えたら考え直す。

### U-NEXT を足さない理由

`/ja/press-room/{年}-{月}-unext-lineups` は 2026-02 までは残っているが、
**2026-08 も 2026-09 も 404**（2026-08-30 実測）。月次のプレスリリース自体が
止まったとみられる。そもそも U-NEXT は自前で直接収集していて（`npm run collect:unext`。
docs/UNEXT.md）、告知を読む必要が無い。直接収集は配信開始日を当日に拾う仕組みなので、
**「先出し」だけができない**という違いが残る。

### 解析器を増やす

1. **足す前に、そのURLの robots.txt を読む。** 転送されるなら**転送先の**robots.txt も読む
2. `theme.yaml` の `announcements:` に1件足す（`service` / `label` / `publisher` / `parser` / `url`）
3. `pipeline/sources/announcement.ts` の `PARSERS` に解析関数を1つ足す

url に使える差し込みは `{year}` `{month_en}` `{month}` `{yymm}`。
パイプラインの他の場所は触らない。記事側（`special --kind upcoming`）も無改修で新サービスを含む。

**目印が消えていたら例外を投げる。0件を返さない**（1節の「静かに0件にならないこと」）。

## 4. 画像

告知には画像が無い。**邦題から作品を特定して、許諾済みの経路で取ってくる。**

```
告知の邦題 → Wikidata（ja ラベル）→ IMDb ID → API /shows/{imdbId} → ポスター・年・ジャンル
```

- **特定できた作品1件につき1リクエスト。** 上限は `--max-lookups`（既定60）
- 実測（2026年9月・84件）: **37件で画像を取得**、47件は Wikidata に項目が無し
- 1件に絞れないときは**画像を諦める**（記事はジャンル別の自前タイルに落ちる）

同名作品で絞れなかったものは、候補つきでログに出る。決めたいものは
`data/announcement-pins.json` に手で書く。

```json
{ "pins": { "ダンケルク": "tt5013056" } }
```

> **なぜ間違えるくらいなら載せないのか。** ポスターが1枚違うと、記事の信用が落ちる。
> 一方、画像が無い行はすでにサイト中にある（U-NEXT 由来の718件）。天秤は明らかに片方に傾く。

## 4-2. 在庫を把握する（`npm run stock`）

通知（`npm run notify`）は**差分**しか送らない。1通読み逃すと、その月に何が貯まって
いるのか分からなくなる。そこで**現在の在庫**を1枚に書き直すコマンドを別に置いた。

`data/UPCOMING.md` はリポジトリに入るので、**GitHub 上でいつでも今の状態が見られる**。

```
| 対象月 | サービス | 件数 | 画像 | 配信開始日の範囲 | 記事 |
| 2026-09 | Netflix | 20 | 0/20 | 2026-09-01 〜 2026-09-11 | **未作成（書ける）** |
| 2026-09 | Amazon Prime Video | 84 | 37/84 | 2026-09-01 〜 2026-09-30 | ✅ ジャンル軸で3本 |
```

「いま書けるもの」には**そのまま貼れる書き出しコマンド**が並ぶ。
記事が書かれているかは `site/src/content/posts/` のスラッグを見て判定している
（サービス軸・ジャンル軸のどちらで書いてあっても拾う）。

## 4-3. 画像を後から入れる（`npm run backfill:images`）

告知は配信が**始まる前**の情報なので、その時点では作品がどこにも無く、
4節の経路が空振りする（Netflix の9月ぶん20件は Wikidata に1件も項目が無かった）。

ところが**配信が始まれば配信APIが同じ作品を返す**。画像は「取れない」のではなく
「まだ取れないだけ」なので、後から突き合わせれば入る。

**突き合わせは強いIDだけを使う。**

| キー | 効くもの |
|---|---|
| サービス側の作品ID（`netflix.com/title/{videoID}`） | Netflix |
| `imdbId`（Wikidata で解決できた告知） | Prime Video 由来に多い |

> ★ **題名では突き合わせない。** 同名の別作品やシリーズの各シーズンが混ざり、
> ポスターが1枚違うだけで記事の信用が落ちる（4節「間違えるくらいなら載せない」と同じ判断）。
> 強いIDが無い作品は画像なしのままでよい。

書き換えるのは `posterUrl` / `backdropUrl` / `year` / `rating` / `genres` / `directors` / `cast` だけ。
**題名・日付・`meta` は触らない**（告知が一次情報である部分を上書きしないため）。

`.github/workflows/announce.yml` が毎日、告知の有無に関係なく走らせる
（画像が付くのは配信開始日で、告知が出た日とは無関係なため）。

## 5. 記事にする

記事タイプは**2つある。告知元がジャンルを持っているかで選ぶ。**

| 記事タイプ | 軸 | 使うサービス | スラッグ |
|---|---|---|---|
| `upcoming-service` | サービス | **Netflix / Disney+**（ジャンルが取れない） | `2026-09-upcoming-netflix` |
| `upcoming` | サービス × ジャンル | **Prime Video**（告知に区分がある） | `2026-09-upcoming-prime-video-anime` |

> ★ **どちらか片方を選ぶ。** 同じ月に両方書くと同じ作品の記事が2本立ち、
> 同じ検索語を自分同士で奪い合う（`docs/ARTICLE-RULES.md`）。
> 両方書けるのは Prime Video だけで、そこは運用で選ぶ。

### サービス軸（`upcoming-service`）

```bash
npm run write -- --type upcoming-service --service netflix --month 2026-09 --emit
npm run research          # ← 素材の作品を日本語版 Wikipedia で下調べ（1作品2.5秒）
npm run write -- --type upcoming-service --service netflix --month 2026-09 --emit
```

**ジャンルを要求しない。** `genres.ts` は「区分が決まらない作品は落とす」方針なので、
ジャンル軸で書くと Netflix と Disney+ の告知が**丸ごと消える**
（実測: Netflix 20件中、区分が決まったのは**0件**）。当て推量で振り分けないための逃げ道がこちら。

下限は10件（`upcoming-service.ts` の `MIN_ITEMS`）。割らない1本なので、
これを下回る月は記事にしないほうがサイトの価値を保てる。

### ジャンル軸（`upcoming`）

記事タイプは **`upcoming`（サービス × ジャンル）**。1サービスにつき3本出す。

```bash
npm run write -- --type upcoming --genre anime --service prime-video --month 2026-09 --emit
npm run research          # ← 素材の作品を日本語版 Wikipedia で下調べ（1作品2.5秒）
npm run write -- --type upcoming --genre anime --service prime-video --month 2026-09 --emit
```

`--genre` を `western` / `japanese` に変えて、1サービスにつき3本出す。
**`research` は `--emit` のあとに走らせる**（`data/draft/context.json` に確定した
作品リストが入っているので、調べる対象を二重に持たずに済む）。下調べが入ると、
作風・評判・広がり方を**事実で**書けるようになる（`templates/writing.md` 3節）。

区分は月次記事（`arrivals --genre`）と同じ3つ。**サイト内でジャンルの呼び方を増やさない。**

| `--genre` | 記事 | 2026年9月・Prime Video の実測 |
|---|---|---|
| `anime` | アニメ | 10本 |
| `western` | 洋画・海外ドラマ | 53本 |
| `japanese` | 邦画・国内ドラマ | 17本 |

> **1本にまとめないのは、80件超の表を読者が読めないから。**
> 薄い月・薄いジャンルが出ることは織り込んでいる（それでも軸がはっきりしているほうが読まれる）。
> ラインナップを1本残らず1本の記事にしたい月は、特報として書ける
> （`--type special --kind upcoming --from/--to`）。

**スポーツ・バラエティーはどの記事にも載らない。** ジャンルの3区分のどれでもなく、
当て推量で邦画記事に入れるほうが害が大きいため（`genres.ts` の方針）。

### タイトルの型

    【{年}年{月}月配信開始】{サービス}の見放題{ジャンル}{本数}本｜{見どころ}

> 【2026年9月配信開始】Amazon Prime Videoの見放題アニメ10本｜ゆるキャン△3期分

**先頭の【】が「配信開始」まで名乗る唯一の記事タイプ。** 同じ月には
「【2026年9月】…見放題配信が終了予定の作品36本」も並ぶので、
**先頭の数文字で開始と終了を取り違えさせない**ための形（`templates/naming.md`）。
そのぶん本文側の動詞句は求めないが、**「見放題」は必ず入れる**（品質ゲートが見ている）。

`--kind new`（もう始まっている）と**意味が正反対**なので、品質ゲートが取り違えを止める。

- 「配信中です」「配信が始まりました」「今すぐ観られます」→ **公開が止まる**
- 末尾に「公式発表」の出典表記が要る（`attribution-announcement`）。
  **API を出典として書くと止まる**（取得していないAPIを出典として偽ることになるため）

書いたあとは他の記事と同じ。

```bash
npm run write -- --apply
cd site && npm run sections -- --write
```

> **節の見出しは「◯月◯日：」で始める。** `make-sections.mjs` は日付で始まる見出しの節だけを
> 画像の対象にするので、これを外すと**その節だけ絵が入らない**。

## 6. 自動化（毎日）

`.github/workflows/announce.yml` が **毎日** JST 05:00 に動く
（2026-08-30 に「25〜31日だけ」から変えた。理由は3節の Netflix の項）。

```
① --check   出ているか・記事1本ぶん（20件）あるかを見る。何も書かない
② 取り込み  出ていれば記録し、画像も用意する
③ 画像      配信が始まって取れるようになった告知を埋める（API消費 0）
④ 在庫      data/UPCOMING.md を書き直す（API消費 0）
⑤ 通知      Issue → メール。本文に記事の書き出しコマンドが入る
```

★ **③④は告知の有無に関係なく毎日走る。**
③ 画像が付くのは「配信が始まった日」で、告知が出た日とは無関係。
④ 在庫は差分ではなく現在の姿なので、毎日書き直しておけば通知を読み逃しても分かる。

出ていない日は 404 で静かに終わる（**エラーにしない**。出るまでの数日は必ず404になるため）。
取り込み済みの日は「新しい告知はありません」で終わり、API も消費しないし通知も鳴らない。

⑤のあと記事を書くのは人（`/article`）。**生成まで自動化するのは P3。**

### 運用者が見る場所は2つ

## 7. データの形

```jsonc
{
  "collectedAt": "2026-08-28T11:20:00.000Z",
  "service": "prime-video",
  "kind": "upcoming",              // ★ new ではない。まだ始まっていない
  "at": "2026-08-31T15:00:00.000Z", // 配信開始予定日（JST 9月1日 00:00）
  "work": {
    "id": "ann-3f9c1a2b7d",         // 告知には作品IDが無いので題名と日付から作る
    "title": "Inception",           // API で特定できたものは原題が入る
    "localizedTitle": "インセプション", // ★ 告知の表記そのまま。これが正
    "posterUrl": "https://cdn.movieofthenight.com/...",
    "meta": {
      "source": "announcement",     // ★ 出典表記の切り替えに使う
      "publisher": "About Amazon",
      "announcementUrl": "https://www.aboutamazon.jp/news/...",
      "category": "映画（海外・韓国）",
      "note": "見放題配信",          // ＊以降の区分
      "apiShowId": "70",            // refresh:images はこれで引き直す
      "raw": "インセプション"          // 告知の行そのもの
    }
  }
}
```

`data/announced-works.json` は邦題→IMDb IDの記録（機械が書く。手で編集しない）。
`data/announcement-pins.json` は人が決める対応表。**役割が違うので混ぜない。**

## 8. サイトには出さない

配信開始「予定」は**作品ページに出していない**（`site/src/lib/works.ts` で落としている）。

作品ページは「いま観られるか・いつまで観られるか」を伝える場所で、
`stateOf()` は `expiring` / `removed` 以外をすべて「配信開始」として扱う。
予定を混ぜると**まだ始まっていない配信を「配信開始」と表示してしまう。**

告知は記事の素材としてだけ使う。
