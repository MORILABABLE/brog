# 横断の「いま観られるサービス」表示（設計・保留中）

**シリーズ記事の表に「この作品はいまどこで観られるか」を出す施策。**
2026-09-05 に実現性を調べた。**技術的にも規約的にも可能だが、実装は保留にした。**

保留の理由は 6節。**規約でも工数でもなく、収益とデータの穴が噛み合わないこと。**

> ★ **2026-09-06 追記。** 保留の判断は**シリーズ記事の表**についてのもので、
> **作品ページ517枚には別の結論が出ている** — [FUNNEL.md 7-1](./FUNNEL.md)。
> 実測で「作品ページの89%が『終了しました』で終わっていて、同じ順位帯の記事の
> 1/3.4 しかクリックされていない」ことが分かったため。**6節の前提と読み比べること。**

- 実装するときの手順 → 5節
- 再検討する条件 → 7節
- 関連: [SOURCES-UNEXT-HULU.md](./SOURCES-UNEXT-HULU.md)（各ソースで何が取れるか）
  / [AFFILIATE.md](./AFFILIATE.md)（提携可否と掲載順の規律）
  / [WORK-PAGES.md](./WORK-PAGES.md)（作品ページの状態表示）

## 1. 何をしたいのか

シリーズ記事は「◯◯シリーズ、いつまで観られる？」に答える記事だが、
読者が次に知りたいのは **「じゃあどこで観られる？」**。

いまの答えは記事末尾の**検索リンク**しかない。
「U-NEXTで検索」「Huluで検索」を並べているだけで、
**あるかどうかは読者が自分で確かめる**形になっている。実質は丸投げ。

ここを「Amazon Prime Video と Netflix で見放題」と**裏付き**で書けるようにしたい、
というのがこの施策。読者が観る先を選べることが利益になる。

## 2. 技術的にできること（2026-09-05 実測）

### 2-1. 在庫が取れる。**これは変化ログとは別のもの**

パイプラインが使っているのは `/changes`（変化のログ）で、
だから当サイトは**「配信中」と書けない**という決まりがある
（`site/src/lib/works.ts` 冒頭「絶対に守ること」／`pipeline/core/cross-service.ts`）。

**この禁止は `/changes` の性質から来ていて、APIの限界ではない。**

`/shows/search/filters` と `/shows/{id}` が返す `streamingOptions.jp[]` は
**その時点の在庫そのもの**で、サービスごとに取扱区分とリンクを持っている。

| フィールド | 中身 |
|---|---|
| `service.id` | `prime` `netflix` `disney` `apple` |
| `type` | `subscription`（見放題）/ `addon`（チャンネル）/ `rent` / `buy` |
| `link` | そのサービスの作品ページへの直リンク |
| `expiresOn` / `expiresSoon` | 終了日（**実測では空。2-4**） |

★ **`catalogs` で絞っても、他社の取扱は返ってくる。**
  `catalogs=prime.subscription` で投げたバイオハザードの応答に
  `apple:rent` `apple:buy` が入っていた。
  **1回の問い合わせで横断の在庫が揃う**ということ。

### 2-2. コストは安い。**作品単位ではなくシリーズ単位**

`/shows/search/filters` はキーワードで複数作品をまとめて返す。
バイオハザードは **7件が1リクエスト**（`hasMore: false`）で取れた。

| | 見積もり |
|---|---|
| シリーズ記事1本 | 1〜3リクエスト（大きいシリーズはページング） |
| 公開中のシリーズ記事6本を全更新 | **10リクエット前後** |
| 無料枠 | 500/月（2026-08 の実績 101、2026-09 は5日で29） |

月1回の書き直しに載せるなら枠は問題にならない。

### 2-3. コードの下地はほぼ揃っている

| | 状態 |
|---|---|
| `ApiStreamingOption` の型 | **定義済み**（`service` / `type` / `link` / `expiresOn` / `expiresSoon`） |
| `collectWorks()`（`/shows/search/filters` を叩く） | **実装済み・未使用** |
| `fetchShow()`（1作品を引く。IMDb ID も渡せる） | **実装済み** |
| `toWork()` | ⚠️ **`streamingOptions` をリンク1本だけ拾って捨てている**（`streaming-availability.ts`） |

**足りないのは実質この最後の1点だけ。**

### 2-4. 「いつまで」は増えない

バイオハザード6作すべてで `expiresOn` は空だった。
終了日は引き続き `/changes` の `expiring` 頼みで、**それが取れるのは Netflix と Prime Video だけ**。

つまりこの施策が増やすのは **「どこで観られるか」だけ**で、
シリーズ記事の本来の問い（「いつまで」）の答えは1件も増えない。

## 3. カバーできない範囲

### 3-1. サービスごと

| サービス | 在庫が取れるか |
|---|---|
| Netflix / Amazon Prime Video / Disney+ / Apple TV+ | ✅ APIから取れる |
| **U-NEXT** | ❌ **APIの日本カタログに存在しない**（2026-08-24 再確認）。自前台帳を使うしかない → 3-2 |
| Hulu / DMM TV | ❌ データが無い。検索リンクのまま |

### 3-2. ★ U-NEXT の台帳は「観測したものだけ」で、カタログではない

**この施策のいちばん大きな穴。**

`data/unext-titles.json` は収集で歩いた範囲（新規入荷ページ＋終了予定ページ）しか持たない。
**U-NEXTの全カタログではない。**

2026-09-05 時点の実測:

| | |
|---|---|
| 台帳の作品数 | **1,902件**（U-NEXTの実カタログは桁がいくつも違う） |
| 終了日あり / 開始日あり | 795 / 1,163 |
| 「バイオハザード」 | **0件** |
| 「ミッション:インポッシブル」 | **0件** |
| 「ハリー・ポッター」 | **1件**（ベイキング番組のみ。本編7作は無い） |
| 「名探偵コナン」 | 32件（終了予定として拾ったぶん） |

**台帳に無いことは「U-NEXTに無い」を意味しない。「まだ観測していない」だけ。**

横断表示にU-NEXTを混ぜると、ここが**偽の不在**になって出る。
読者は「U-NEXTには無いのか」と読むが、実際にはあるかもしれない。
**単価が最も高いサービス（1,320円）で、いちばん質の悪い誤情報を出す**ことになる。

> ★ 出さなければ嘘にはならないが、**それなら横断表示の値打ちが半減する。**
>   4社ぶんだけ出して、収益になる1社が空欄というのは読者にとっても中途半端。

## 4. 規約・運用の条件

**規約上できないことは無い。** ただし守る条件が4つある。

### 4-1. ★ `addon` を見放題と書かない（いちばん事故りやすい）

`type` には `subscription` と `addon` が**同じ作品に併存する**。
実測でバイオハザードの各作に `prime:subscription` と `prime:addon` の両方が付いていた。
`addon` は Prime Video チャンネル（**別料金**）。

混同すると「別料金の作品を見放題と書く」ことになり、
性質としては U-NEXT ガイドライン【4】の誤認訴求と同じ。

> **`type === 'subscription'` だけを見放題として扱うこと。** ここは実装の必須条件。
> 2026-09-05 にバイオハザードのシリーズ記事で「すべてが見放題」が
> `check:unext` に止められた事故と、同じ種類の間違い。

### 4-2. 「配信中」と書けるようになるが、根拠と時点を明示する

現行の禁止（`works.ts`「絶対に守ること」）は
**変化ログを根拠に在庫を断定するな**という趣旨なので、
在庫レスポンスを根拠にするなら射程外になる。

- **取得時点を明記する**（既存の「◯月◯日時点」と同じ作法）。在庫は日々変わる
- U-NEXT・Hulu・DMM TV への断定禁止は**そのまま残る**（データが無い／別の規律）

★ **在庫レスポンスが間違っていることがある**（2026-09-09 に踏んだ。9-3-C）。
  APIが `subscription` を返していても、その社の画面に無い作品がある。
  目視で確かめた否認は `data/availability-ng.json` に置き、記事にも表にも出さない。

### 4-3. ★ 掲載順は機械的に固定する

[AFFILIATE.md 7節](./AFFILIATE.md) で
**「紹介料の高いサービスを優先して掲載しない」**と決め、
プライバシーポリシーにも明記した。横断表示はこの規律に正面から触れる。

**Amazon を上に置く実装にした時点で、明記した方針に反する。**
並び順はデータ由来の機械的な順（サービスキーの定義順など）に固定すること。

### 4-4. 帰属表示を落とさない

APIは各記事への出典表記が義務（[SOURCES-UNEXT-HULU.md 4節](./SOURCES-UNEXT-HULU.md) の比較表）。
既存の固定文言でカバーされているので、**表示を足しても文言は必ず残す。**

## 5. 実装するときの手順

保留を解いたときのために、順番だけ残す。**上から順に、1つずつ確かめながら。**

1. **`toWork()` で `streamingOptions` を保持する**
   `Work.meta` に `{ service, type, link }[]` を持たせる。
   `type === 'subscription'` の絞り込みは**保持のときではなく使うときに**行う
   （`rent`/`buy` は将来アフィリエイトの導線になりうるので捨てない）

2. **取得の口を1つ作る**
   `collectWorks()` をシリーズ記事の主題（`--match`）で叩く CLI。
   **書き直し（`/refresh`）のときだけ走らせる。** 毎ビルドで叩かない

3. **`series.ts` の表に「視聴可能サービス」列を足す**
   - `subscription` のみ
   - 順序固定（4-3）
   - 取得時点を記事に明記（4-2）
   - **U-NEXT は入れない**（3-2。入れるなら 7-1 が先）

4. **品質ゲートを足す**
   `addon` が「見放題」として本文に出ていないかの検査（4-1）

★ **`/changes` の収集は変えないこと。** 終了日はそちらでしか取れない（2-4）。
  この施策は**別の口を1つ増やす**話で、既存の収集を置き換える話ではない。

## 6. 保留の理由（2026-09-05）

**規約でも工数でもない。収益とデータの穴が噛み合わないこと。**

### 6-1. 在庫が取れる4社のうち、収益になるのは1社だけ

[AFFILIATE.md 3節](./AFFILIATE.md) の実測より:

| サービス | 在庫 | 提携 |
|---|---|---|
| Amazon Prime Video | ✅ | ✅ Amazonアソシエイト |
| Netflix | ✅ | ❌ **公式プログラムが存在しない** |
| Disney+ | ✅ | 🔶 招待制 |
| Apple TV+ | ✅ | 🔶 招待制 |
| **U-NEXT**（単価 1,320円で最有力） | ❌ **3-2 の穴** | afb で提携交渉中 |

**在庫が取れるサービスと、収益になるサービスが、ほとんど重なっていない。**
横断表示を作り込むほど、**収益にならない導線を厚くする**ことになる。

### 6-2. 読者の利益は本物だが、いま出せる形では半端

「どこで観られるか」を裏付きで出せるのは読者にとって明確な前進で、
検索リンクへの丸投げより良い。**それは疑いない。**

ただし、いま出せるのは
**「4社ぶんの在庫」＋「U-NEXTは空欄」＋「Hulu・DMM TVは検索リンクのまま」**
という形。読者から見て「結局どこで観られるのか」が1画面で閉じない。

### 6-3. 「いつまで」は1件も増えない（2-4）

シリーズ記事の本来の問いに対しては、この施策は何も足さない。

## 7. 再検討する条件

**どれか1つでも変われば、判断は変わる。**

### 7-1. ★ U-NEXT の台帳がカタログに近づいたとき（いちばん効く）

いまの台帳は「新規入荷」と「終了予定」を歩いた副産物でしかない（3-2）。
**作品名から引ける形**になれば、3-2 の穴と 6-1 の収益の穴が**同時に埋まる。**

考えられる道:

- **作品名での検索**（`video.unext.jp` のフリーワード検索）を、
  シリーズ記事の主題ぶんだけ叩いて台帳に足す。
  **既存の巡回とは別の口**で、件数も限られる（記事1本あたり数十件）
- ★ ただし [SOURCES-UNEXT-HULU.md 5節](./SOURCES-UNEXT-HULU.md) の規律がそのままかかる。
  `min_interval_ms` を下げない。負荷の議論（岡崎市立図書館事件）は
  規約より重い問題として扱うこと

> **これが本命。** U-NEXT は在庫も単価も揃う唯一のサービスで、
> ここが埋まればこの施策は「読者の利益」と「収益」が初めて同じ方向を向く。

### 7-2. Disney+ か Apple TV+ の提携が通ったとき

在庫が取れる4社のうち収益になるのが2社に増える。6-1 の計算が変わる。

### 7-3. `expiresOn` が返るようになったとき

2-4 が解消し、**Disney+ と Apple TV+ の終了日**が初めて手に入る。
そうなればシリーズ記事の本来の問い（「いつまで」）にも効くので、
この施策は「あれば嬉しい表示」から「記事の中身そのもの」に変わる。

## 8. この調査で分かった、すぐ使える事実

**保留とは別に、記録しておく価値のあるもの。**

- `streamingOptions` は `catalogs` で絞られない（2-1）。
  **1リクエストで横断の在庫が取れる**のは、他の用途にも使える
- `collectWorks()` と `fetchShow()` は実装済みで未使用（2-3）。
  ランキング記事など、在庫を前提にした記事タイプを作るときの土台になる
- `type` に `addon` が混ざる（4-1）。
  **これは今後どの機能で在庫を使うときも効く注意**で、この施策に限らない

## 9. ★ 保留を解く（2026-09-06・実測）

**6節の保留理由は、シリーズ記事には当てはまらないことが実測で分かった。**
サイト最大の流入記事（`/posts/harry-potter`）で実際に叩いて確かめた結果を置く。

### 9-1. 叩いた結果 — **1リクエストで8作品ぶんの在庫が揃った**

```
npm run probe -- /shows/search/filters country=jp "keyword=Harry Potter"   output_language=en series_granularity=show
```

| 取扱区分 | 件数（9作品中） |
|---|---|
| `netflix:subscription` | 8 |
| **`prime:subscription`** | **8** |
| `prime:rent` | 8 |
| `apple:rent` / `apple:buy` | 7 / 7 |
| `prime:buy` | 4 |

★ **`addon` は1件も無かった。** 4-1 の事故（別料金チャンネルを見放題と書く）は
このシリーズでは起きない。**ただし毎回確かめること。**

### 9-2. 6節の保留理由が、この面では逆に働く

保留の根拠は **6-1「在庫が取れる4社のうち、収益になるのは1社（Amazon）だけ」**だった。

**その1社が答えだった。**

`/posts/harry-potter` は「Netflixで9月30日に見放題終了」を伝える記事で、
読者の本当の問いは「**では9月30日以降どこで観るのか**」。
その答えが **Amazon Prime Video の見放題**で、これは:

| | |
|---|---|
| **裏付きで書ける** | API の在庫レスポンス（4-2 のとおり射程外なので「見放題」と書ける） |
| **唯一収益になるサービス** | Amazonアソシエイト |
| **プライム無料体験LPが初めて事実として成立する** | 「Prime Videoの見放題」が答えなので、会員訴求と噛み合う（[FUNNEL 7-6-1](./FUNNEL.md)） |

> **6-1 は「収益にならない導線を厚くすることになる」という懸念だった。**
> シリーズ記事では**収益になる導線が答えそのもの**なので、懸念が成立しない。
> **判断が変わるのは施策の中身ではなく、当てる面のほう。**

### 9-2-B. Disney+ の提携が申請中（2026-09-06）

**7-2 の条件が満たされる可能性が出た。**

> 7-2. Disney+ か Apple TV+ の提携が通ったとき
> 在庫が取れる4社のうち収益になるのが2社に増える。6-1 の計算が変わる。

afb に申請中（[AFFILIATE 12-0-A](./AFFILIATE.md)）。通れば

- **「この作品は Disney+ で見放題」が、裏付きかつ収益になる答えになる**
- 6-1 の「収益になるのは1社だけ」が **2社**に

★ **Disney+ の価値は自社の面ではなく、他社の記事の答えになること。**
Disney+ は終了予定日を返さない（2-4）ので、Disney+ の作品ページ74枚は
永久に「終了済み」しか無い。**「Netflixで終わる作品が Disney+ にある」**
という形でだけ効く。

★ **U-NEXT と Hulu が通っても、この節の話には効かない。** 在庫が取れないため
（9-3）。**提携と在庫は別の軸**で、混ぜると「提携が増えたから横断表示が強くなる」
という誤った推論になる。

### 9-3. ただし「網羅」はできない。**U-NEXT と Hulu は入らない**

**ここを取り違えると、書けないことを書くことになる。**

| サービス | 在庫が取れるか |
|---|---|
| Netflix / Prime Video / Disney+ / Apple TV+ | ✅ API から取れる |
| **U-NEXT** | ❌ 自前収集はあるが**カタログとして使わないと決めてある**（[GROWTH 2-3](./GROWTH.md)）。台帳は作品名から引けない（3-2） |
| **Hulu** | ❌ **データが無い。** 利用規約 第3条(3) が自動アクセスを明示的に禁止（[SOURCES-UNEXT-HULU](./SOURCES-UNEXT-HULU.md)） |
| DMM TV | ❌ データが無い |

★ **「他社を網羅する」とは書かない。** 出せるのは**4社ぶん**で、
残りは今までどおり検索リンク。**そこは丸投げのまま**であることを隠さない。

★ **「大半は U-NEXT だろう」は推測。** 実測では逆で、
ハリー・ポッターの答えは Prime Video だった。**面ごとに叩いて確かめること。**

### 9-3-B. ★ 在庫を「素材」にした（2026-09-07 実装）

**それまで在庫は素材の注釈でしかなく、素材そのものは `/changes` だけから作っていた。**
変化ログは収集を始めた日（2026-08-01）以降しか無いので、
**それ以前から在庫にある作品は、何年経っても記事に出てこない。**

#### 実測 — 「仮面ライダー」で何が抜けていたか

在庫API（`/shows/search/filters`, `keyword=Kamen Rider`）は**日本で93作**を返す。
Prime Video での扱いを種別ごとに数えるとこうなる（`catalogs=prime.*` で1つずつ数えた）。

| 内訳 | 件数 | 記事に出せるか |
|---|---|---|
| **Prime Video の見放題（subscription）** | **14** | ✅ 出せる |
| Prime Video の**別料金チャンネル**（addon） | 26 | ❌ 見放題ではない（4-1） |
| Prime Video のレンタル | 36 | ❌ |
| Prime Video の購入 | 30 | ❌ |
| **いずれかの形で Prime にある作品（重複除く）** | **42** | — |

**変化ログから作った素材は11本だった。** すべて8月31日に `new` が立った分で、
`シン・仮面ライダー`（2023）・`仮面ライダーBLACK SUN`（2022）・`風都探偵`・
`東島丹三郎は仮面ライダーになりたい`（Netflix）が丸ごと欠けていた。

★ **「Amazonに在庫が豊富なのに記事が薄い」と感じたら、まずこの内訳を疑う。**
  Amazonの検索結果に大量に並ぶのは、たいてい **addon（東映オンデマンド / MY HERO）と
  レンタル・購入**で、見放題はその一部でしかない。
  **見えている数と、記事に書ける数は違う。**

#### ★ それでも数は合わない。**APIの日本カタログ自体が薄い**

運営者の目視では、Amazonの「プライム会員特典」に**約50作**並んでいた。
APIが見放題と言うのは14作で、**差は説明しきれない。** 調べた範囲でこう。

| 確かめたこと | 結果 |
|---|---|
| `keyword` は日本語で引けるか | **引けない。** `keyword=仮面ライダー` は**0件**（索引はラテン文字だけ） |
| ページ打ち切りのせいか | **違う。** 5ページで `hasMore=false` まで到達しても93作 |
| テレビシリーズは入っているか | **ほぼ入っていない。** 93作のうち `series` は**7本だけ**（実在するのは30本以上） |
| 最近の作品はあるか | **無い。** `仮面ライダーガッチャード` は**どのキーワードでも0件** |

つまり**この IP については、APIの日本カタログが実際の品揃えを反映していない。**
クエリを直しても届かない範囲がある。

★ **ここが記事の信用に直結する。** 読者は記事とサービスの検索結果を見比べるので、
  **数が合わないこと自体は避けられない。** できるのは
  **何を載せていないかを先に言うこと**だけで、それが
  `series-coverage-note`（`templates/fixed-phrases.md`）。**外さないこと。**

★ **Amazon の画面と突き合わせる自動化はしない。** `amazon.co.jp` は自動取得を
  受け付けない（2026-09-07 に確認。応答が空で返る）。
  **突き合わせが要るときは人が目視する**、という前提でこの節を書いている。

#### 引き方も直した — **`catalogs` で絞る**

見放題を探すのに絞らずに引くと、応答がレンタル・購入で埋まって
**見放題の作品が後ろのページへ押し出される。それは「在庫が無い」に化ける。**

| 引き方 | リクエスト | 返り | 見放題 |
|---|---|---|---|
| `keyword=Kamen Rider`（旧） | 5 | 93 | 14（`風都探偵` を取りこぼし） |
| ＋ `catalogs=…subscription`（新） | **1** | 15 | **15**（`hasMore=false`） |

絞っても**他社の取扱は応答に残る**（`apple:rent` 等）ので、
表の下に出す「他社の在庫」は今までどおり作れる（2-1）。
**安いうえに取りこぼさない**ので、`--adopt` は常にこちらで引く。

#### やり方

```bash
npm run availability -- --adopt --keyword "Kamen Rider" --match "仮面ライダー|風都探偵"
npm run write -- --type series ... --emit      # ← 素材に入る
```

`--adopt` は在庫検索が返した作品のうち、**`--match` に当たり、かつ見放題**のものを
**作品ごと**台帳に入れる（`WorkAvailability.work`）。
`article-types/series.ts` の `stockEvents()` がそれを「見放題配信中」の素材にする。

★ **`at`（配信開始日）は持てない。** 在庫は「いまある」としか言わない。
  プロンプトは日付の行そのものを出さず、記事は表の終了日欄に `—` と書く。
★ **変化ログにある作品は変化ログを優先する。** あちらは終了日を持ちうる。
★ **`--match` を必ず渡す。** 絞らないと無関係な作品が台帳に入り、次の記事に混ざる。

#### ページングの打ち切りが「在庫が無い」に化けていた

9-3 の下に「Transformers は60作を返しながら、こちらの5作を1件も含んでいなかった。
**後ろのページに居たとみられる**」と推測で書いてあったが、**実測でそのとおりだった。**

| ページ上限 | 返った作品 | こちらの作品 |
|---|---|---|
| 3（旧・既定） | 60 | 3作が入らない |
| 8（新・既定） | 93（`hasMore` が尽きた） | 全部入った |

`fetchAvailability` の既定を **3 → 8** に上げた。1ページ1リクエストなので、
枠より取りこぼしのほうが高くつく。

#### リードの本数の言い方も直した

`series-lead-first-sentence` は「{本数}本の終了日が判明しています」と書くが、
`{本数}` は**記事が扱う作品数**（タイトルと揃える決まり）であって、
終了日が分かっている数ではない。**状態が混ざる記事ではそのまま嘘になる**
（対象14本・終了予定1本で「14本の終了日が判明」と書いていた）。
在庫から素材を拾うぶん混ざる回が普通になったので、
`series-lead-partial-first-sentence` を足して文言のほうを分けた。

### 9-3-C. ★ 逆もあった — APIが「見放題」と言うのに、画面には無い（2026-09-09）

9-3 は**取りこぼし**（Amazonの画面に約50作あるのにAPIは14作）の話だった。
**反対向きの食い違いが出た。こちらのほうが害が大きい。**

> 運営者の目視: 「名探偵コナン」の劇場版は Amazon Prime Video の見放題に**1本も無い**（レンタル・購入だけ）。
> 公開中の記事: リードが「同じ時点でAmazon Prime VideoとDisney+でも一部タイトルが見放題で配信されています」、
> 表には8作に ○（見放題）が並んでいた。

**取りこぼしは「載っていない」で済むが、これは読者に嘘を見せている。**

#### 調べたこと

| 確かめたこと | 結果 |
|---|---|
| こちらの取り違えか（IDが別作品を指している等） | **違う。** `/shows/45173` は `名探偵コナン 時計じかけの摩天楼` を返し、`streamingOptions.jp` に `prime` の `subscription` が入っている |
| 古い在庫を使っていたか | **違う。** `fetchedAt` は 9月6日で `MAX_AGE_DAYS`（14日）の内側 |
| `addon`（Prime Video チャンネル）を見放題と誤ったか | **違う。** `type` は `subscription` そのもの。`addon` は別に返ってくる |

**つまり、APIの日本カタログには2025年4月の見放題の行が残ったままで、消えたことが流れてこない。**
在庫レスポンスを「その時点の在庫の直接の根拠」として扱う前提（4-2）が、この面では崩れている。

#### なぜ機械で気づけないのか

- `amazon.co.jp` は自動取得を受け付けない（9-3 の★）。**突き合わせは人が目視する**前提でこの仕組みは書かれている
- 変化ログにも出ない。収集開始より前から在庫にある扱いなので `new` は流れず、消えたことも `removed` として流れてこない
- 記事の品質ゲートも止められない。ゲートは「在庫が裏付けているか」を見るので、**在庫そのものが嘘なら通る**

**→ 気づけるのは人の目だけ。だから、目視の結果を置く場所を作った。**

#### どう直したか — `data/availability-ng.json`

**目視で「そこには無い」と確かめた（作品・サービス）から、見放題だけを取り下げる。**

```json
{ "service": "prime-video", "match": "名探偵コナン", "ids": ["45173", "…"],
  "checkedAt": "2026-09-09", "evidence": "見放題（プライム会員特典）に1本も出ていない。レンタル・購入はある。" }
```

| どこ | 何をするか |
|---|---|
| `pipeline/core/availability-ng.ts` | 一覧を読んで `deniesSubscription(service, workId, titles)` を1つ返す |
| `pipeline/core/availability.ts` | `subscriptionServices()` が落とす。**作品IDと題名を渡さないと呼べない形**にしてある |
| `site/src/lib/availability-ng.ts` | 同じ規則の写し（site は pipeline を import しない決まりのため）。**両方直すこと** |
| `site/src/lib/availability.ts` | 表の印を ○ → △（レンタル・購入が残っていれば）／ **—（未確認）**（何も残らなければ）にする |
| `pipeline/cli/availability.ts` | `--adopt` の素材にしない。**画面には「★目視で否認ずみ（APIは見放題と言っている）」と出す** |

★ **台帳（`data/availability.json`）は書き換えない。** あれは**APIが何と言ったかの記録**で、
  消すと次に取り直したとき同じ嘘が戻り、食い違いの証拠も消える。落とすのは読む側。

★ **取り下げるのは見放題だけ。** レンタル・購入はAPIのまま残す（表では △）。
  **「取り扱いなし（×）」にはしない** — 目視で確かめたのは「見放題に無い」ことだけ。

★ **`match`（題名の部分一致）を持たせたのは、自動更新で戻ってくるから。**
  IDだけで否認すると、次に `npm run availability -- --adopt --match "名探偵コナン"` を走らせたとき
  **別IDの同じシリーズの作品**（`vs 怪盗キッド` `エピソード“ONE”`）が素材に入って、同じ嘘が戻る。

#### 運用

- **目視で確かめたことしか書かない。**「たぶん無い」で足さない
- **`checkedAt` と `evidence` を必ず書く。** 書かないと、あとで消してよいか誰にも分からなくなる
- **事実が変わったら1行消す。** また見放題に入ったら、消すだけで元に戻る
- **他のシリーズも同じ形で疑える。** いま在庫が Prime Video の見放題と言っている作品は、
  記事にする前に一度画面を見ること（`npm run availability` の出力に出る）

★ **効くのは在庫にだけ。** 変化ログ（`/changes`）がそのサービスの `new` を返し始めたら、
  それは**新しい観測**なので素材に入り、記事に出る。**そこは塞いでいない**
  （観測の記録を否認で消すと、変化ログが変化ログでなくなる）。
  その形で戻ってきたら、それは「本当に入った」可能性があるということなので、
  画面を見て、入っていれば否認の行を消す。

### 9-4-B. ★ 月の枠を誰が使っているか（2026-09-07 実測）

**APIを使う定期実行は2つだけ。** 残りは0回なので、そこを疑わない。

★ 0件になっても**告知の取り込み自体は続く。** 作品名と日付は記事に出せる。

### 9-7. **答えは文章ではなく表に置く**（2026-09-06・一度書いて撤去した）

**在庫を段落で説明する形を一度作って、同じ日に撤去した。** 経緯を残す。

| | |
|---|---|
| 最初にやったこと | 表の直後に「9月30日以降はどこで観られるか」の節（3段落）を足した |
| なぜ撤去したか | **文章では届かない。** スクロール90%到達は22%（[FUNNEL 5-3](./FUNNEL.md)）。そして表と文章で**同じ事実が2か所**になり、書き直すたびに片方だけ古くなる |
| 代わりに | **サイトが表に列を足す**（`site/plugins/rehype-availability.ts`） |

```
| 終了日  | 作品                      | 状態     | 評価   | サービス |
| 9月30日 | ハリー・ポッターと賢者の石 | 終了予定 | 77/100 | Netflix  |
|  配信中  ● Amazon Prime Video   × Disney+   △ Apple TV+  |   ← 足す行

● 見放題　△ レンタル・購入　× 取り扱いなし（9月6日時点・4サービス分。各社の都合で変わります）
```

**表は本文の9%の位置にある。** 読者が確実に見る範囲に答えが入る。

#### 9-7-0. ★ その行のサービスは出さない

上の例で **Netflix が出ていない**のは、その行が「Netflixで9月30日に終了」の行だから。
そこに「Netflix ●」を出すと、**終わるのか観られるのか読者に判別できない**
（2026-09-06・運用者の指摘。実際に誤解を生む形で出ていた）。

出すのは**行き先になりうる残りのサービス**だけ。判定はサイト側が行の
「サービス」列から読み取る（`workOf()`）。

★ **残りは × も含めて全部出す。** 「調べたうえで取り扱いが無い」と
  「そもそも調べていない」は違う。×を省くと読者に区別が付かない。

★ 見放題は **●（塗りつぶし）**。△や×と並べたとき、輪郭だけの○では強さが伝わらない。

#### 9-7-0-1. ★ ラベルは枠で囲い、文字と色をその行の印で変える（2026-09-09）

行の頭のラベルは**枠付き**で、**文字も色もその行に並ぶ印から自動で決まる。**

| その行の印 | 文字 | 枠と文字の色 |
|---|---|---|
| ○ が1つでもある | 配信中 | ブルー |
| ○ が無く △ がある | 有料で配信中 | アンバー |
| × だけ | 取り扱いなし | 赤 |
| — （未確認） | 配信状況 | グレー |

★ **文字を全部「配信中」にしない。** ×だけの行が「赤い枠の『配信中』」になり、
  **文字だけ読むと逆の意味に取れる。** 色は補助でしかない以上、
  文字が単体で正しくなければならない（`LABEL_TEXT`）。

★ **判定は `labelStateOf()` の1か所**（`site/plugins/rehype-availability.ts`）。
  記事は**作成も書き直しも同じビルドを通る**ので、ここだけで全記事に効く。
  記事の `.md` には何も書かない。

★ **色を決める材料は「その行に実際に出ている印」**。台帳の全サービスではない。
  その行のサービス（9-7-0）を外したあとの並びで決めるので、
  「Netflixで終了」の行が Netflix の ○ を根拠に青くなることはない。

★ **色だけに意味を持たせない**（`global.css` の決まり）。
  ラベルの文字と ○ △ × が意味を持っているので、色が届かない読者でも落ちない。

#### 9-7-1. 「列」で作って、作り直した

**最初はサービスごとの列にした。スマホで収まらなかった。**
playwright で実測した数字がこれ。

| 画面幅 | 列にしたとき | 行にしたとき |
|---|---|---|
| 360px | 表 407px / 領域 321px → **横スクロール** | 表 321px / 321px → **なし** |
| 375px | 表 407px / 領域 336px → **横スクロール** | 表 336px / 336px → **なし** |
| 390px | 同上 | **なし** |
| 414px | 同上 | **なし** |

**横スクロールしないと見えないなら、表に入れた意味が消える。**
行なら幅を食わず、しかも**サービス名をそのまま書ける**ので、
記号だけの列と違って凡例を読まなくても意味が通じる。

★ 幅を空けるために、サイト側が2つの列を落としている。
  **「サービス」列**（足す行がサービス名を書くので重複）と、
  **中身が全行同じ「状態」列**（情報を持たない列が幅を食う）。
  **「終了日」は全行同じでも落とさない** — この記事の核心の事実だから。

#### 9-7-2. 守っている線

★ **出すのは在庫を持つ4社だけ。** U-NEXT / Hulu / DMM TV は出さない。
