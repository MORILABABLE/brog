## 1. 対象の決め方（掲載判定）

薄いページを大量に出すと、まとめて「クロール済み — インデックス未登録」に落ちる。
**出す条件を1つの関数に閉じ込め、そこを通らないものはページ自体を作らない。**

### 段階ごとの実測

| 段 | 条件 | 残る |
|---|---|---|
| 収集した全作品 | — | 1,760 |
| **U-NEXT由来を落とす** | `service` が API の4社のいずれか | 1,042 |
| 出さないと決めた作品を落とす | `isPublishable()`（`data/excluded-works.json`） | 1,042 ※現状の該当0件 |
| **終了日を言える** | `expiring` **または** `removed` のイベントを持つ | **653** |
| **人の名前が出せる** | **監督 または 出演**がいる | **508** ← 第1弾 |

参考: 緩める場合の候補は「監督 or 出演 or 原語」で **575件**。

### なぜこの2段なのか

**「終了日を言える」が独自性の条件。** 配信中かどうかは JustWatch も Filmarks も出す。
**終了日を出すサイトはほぼ無い**（[GROWTH.md 1節](./GROWTH.md)）。
`new` しか持たない作品のページは「◯月◯日に配信が始まった」しか言えず、
他所と同じ的を撃つことになる。第2弾で条件を見直す。

**「人の名前」で切るのは、実装して条件を変えた結果**（2026-08-27）。

当初は「あらすじがあれば厚い」と数えていたが、これは誤りだった。
配信APIの `overview` は**780件すべてが英語**で、日本語のページには出せない。
**出さないものを厚みとして数えると、実際には
「題名・日付・年・ジャンル」しか無いページを厚いと判定してしまう。**

監督と出演は Wikidata の**日本語ラベル**で入るので、そのまま読者に出せる。
原語も日本語にできるが1語しか増えないので数えない。

### 実装

`site/src/lib/works.ts`（新規）に1つだけ置く。

```ts
/** そのIDの作品ページを作ってよいか。getStaticPaths がこれだけを見る。 */
export function isWorkPagePublishable(w: WorkPage): boolean
```

> ★ **`noindex` で逃げない。** 出さないと決めたものは `getStaticPaths` が返さない。
> ページを作ってから隠すと、サイトマップに載せない工夫と
> リンクを張らない工夫が別々に要る。**作らなければどちらも要らない。**

> ★ U-NEXT を落とすのは [GROWTH.md 2-3](./GROWTH.md) の決定による。
> 作品IDが `SID` で始まるので目視でも分かる。**13節のチェックリストで必ず確認する。**

## 2. URL とルーティング

```
/works/<作品ID>          例: /works/132442
site/src/pages/works/[id].astro
```

> ★ **邦題をURLに入れない。** Wikidata の邦題解決率は78%で、
> **あとから邦題が付くとURLが変わる。** 変わったURLは評価を捨てることになる。
> 作品IDは配信API側の内部IDで、動かない。邦題は h1 と `<title>` に出す。

> ★ `astro.config.mjs` の `build.format: 'file'` により、出力は
> `dist/works/132442.html`、公開URLは `/works/132442`（拡張子なし）。
> canonical は `BaseLayout` の `toPublicPath()` が処理済みなので**何もしなくてよい。**

## 3. データの組み立て

`site/src/lib/works.ts`（新規）。**既存の3つを繋ぐだけ。収集は増やさない。**

```
data/events/*.jsonl ─────────┐
data/directors.json          ├──→ WorkPage
data/cast.json               │
data/origins.json ───────────┤
public/thumbs, public/posters ┘
```

### 結合キー

| 何を | どこから | キー |
|---|---|---|
| 配信状況・日付・ジャンル・あらすじ・年 | `data/events/*.jsonl` | `work.id` |
| 邦題 | イベントの `localizedTitle`（収集時に解決済み） | — |
| **監督・出演・原語** | `data/{directors,cast,origins}.json` | **`work.meta.imdbId`、無ければ `` `tmdb:${work.meta.tmdbId}` `` ** |
| 絵 | `public/thumbs` `public/posters` | `work.id` |

> ★ **`origins.json` は「製作国」ではなく「原語」**（Wikidata の P364 = original language）。
> 値は `English` `Japanese` のような**言語名**。
> 製作国だと思って出すと、画面に「製作国: 英語」と出る（2026-08-27 に実際に出した）。
>
> ★ **`overview`（あらすじ）は使わない。** 実測780件すべてが英語で、
> 日本語のページに英文を貼ることになる。日本語のあらすじを持てるようになったら、
> **掲載判定（1節）と一緒に**見直すこと。
>
> ★ **ジャンルは英語で入っている**（`Action` `Drama`）。
> `scripts/genre-art.mjs` の `GENRE_ART` が英語名→日本語ラベルの対応表を
> すでに持っているので、それで訳す。訳せなかったジャンルは**落とす**（英語のまま出さない）。
> `npm run thumbs -- --audit` が「取りこぼしなし」と出る状態を保つこと。

> ★ **結合キーの規則は `pipeline/sources/wikidata.ts:84` の `titleCacheKey()` と同一。**
> 片方だけ直すと、**全作品の監督とキャストが静かに空になる**（例外もビルドエラーも出ない）。
> `search-links.ts` や `excluded.ts` と同じ「site/ は theme-pack を読めない」事情で、
> 同じ規則を2か所に持つことになる。**両方直すこと。**

### 型

```ts
export type WorkState = 'leaving' | 'passed' | 'ended' | 'started'

export interface WorkServiceState {
  service: string          // 'netflix'
  label: string            // 'Netflix'
  state: WorkState
  at: Date                 // その状態の日付
  url: string              // 送り先（work-links.ts の resolveUrl がそのまま使える）
}

export interface WorkPage {
  id: string
  title: string            // 邦題優先
  originalTitle?: string   // 邦題と違うときだけ
  year?: number
  type: 'movie' | 'series'
  rating?: number          // 0 は「評価なし」。undefined に落とす
  genres: string[]         // 日本語に訳したもの。訳せなければ落とす
  languages: string[]      // 原語（Wikidata P364）。**製作国ではない**
  directors: string[]      // Wikidata
  cast: string[]           // Wikidata。主演順ではない。10人まで
  poster?: string          // /posters/<id>.webp
  services: WorkServiceState[]
  state: WorkState         // ページ全体。4節の優先順で決まる
  dataAsOf: Date           // 収集した最も新しい時刻
}
```

> ★ `rating` の 0 は「評価なし」。そのまま出すと最低評価に見える
> （`events-data.ts` の `toRow()` と同じ扱いにそろえる）。
>
> ★ キャストの並びは**主演順ではない**（HANDOVER.md 1節）。
> 「主演」と書かない。「出演」とだけ書く。**10人で切る**（実測22人並ぶ作品があった。
> 重要な順に並んでいないので、全部出しても読者の役に立たない）。
>
> ★ **人名は「、」で区切る。「・」で繋がない。**
> カタカナの人名は「ヒラリー・ダフ」のように中黒を含むので、中黒で連結すると
> 区切りが消えて1人の名前に見える（2026-08-27 に実際にそうなった）。

## 4. 状態の判定と、言ってよいこと

**この節がこのページで最も重要。**

> **このサイトが持っているのは「変化の観測」であって「現在の在庫」ではない。**

`new` を観測して `removed` を観測していないことは、「いま配信中」を意味しない。
Disney+ と Apple TV+ は `expiring` を返さず、`removed` も棚卸しの都合で遅れて出る。
**「配信中です」と書かない。**

### 4値

| 状態 | 判定（そのサービスの最新イベント） | ページの言い方 |
|---|---|---|
| `leaving` | `expiring` かつ日付が**未来** | **9月30日**に見放題終了予定 |
| `passed` | `expiring` かつ日付が**過去** | 見放題終了予定日: **8月31日**（この日を過ぎています） |
| `ended` | `removed` | **8月31日**に見放題配信が終了しました |
| `started` | `new` | **8月1日**に見放題配信が始まりました |

ページ全体の状態は **`leaving` > `passed` > `ended` > `started`** の優先順で決める
（複数サービスに出る作品は17件ある）。**読者にとって行動が要るものを先に出す。**

### 3つの禁止

> ★ **`passed` を `ended` に丸めない。**
> 予定日を過ぎたことは観測しているが、**実際に終わったことは観測していない。**
> 丸めると、配信が延長された作品に「終了しました」と書くことになる。
>
> ★ **`started` に「配信中」と書かない。**
> 必ず「その後の配信状況は変わることがあります。ご視聴前に公式サイトでご確認ください」を
> 添える。文言は既存の常設ページ（`pages/leaving/[service].astro` の `.notice`）にそろえる。
>
> ★ **手書きの説明文を1文字も置かない。**
> 文言はすべて状態と日付から組み立てる。手で書くと、ビルドのたびに古くなる。
> これは常設ページが LLM を使わないのと同じ理由（`events-data.ts` 冒頭）。

### h1

| ページの状態 | h1 |
|---|---|
| `leaving` / `passed` / `started` | **「{邦題}」（{年}年）はいつまで見られる？** |
| `ended` | **「{邦題}」の見放題配信は終了しました** |

年が無ければ省く。`<title>` は `BaseLayout` が `｜見放題レーダー` を後置するので、
h1 と同じ文字列をそのまま渡す。

> ★ **作品名だけの h1 にしない。** 公式・Wikipedia・レビューサイトと同じ的になる。
> **答えられる質問をそのまま見出しにする**ほうが、勝てる語に当たる
> （[GROWTH.md 3-1](./GROWTH.md)）。

`description` は状態と日付から組む。全角120字以内（`config.ts` の `SITE.description` と同じ基準）。

上から順に。

| # | 中身 | 既存の部品 |
|---|---|---|
| 1 | パンくず（ホーム › 配信終了予定 › {サービス} › {作品名}） | `leaving/[service].astro` と同じ形 |
| 2 | h1 | — |
| 3 | **配信状況の表**（サービス / 状態 / 日付 / 送り先） | 新規 |
| 4 | 広告表記 | `AffiliateNotice` |
| 5 | 基準日の注意書き | `leaving/[service].astro` の `.notice` |
| 6 | 作品の情報（ポスター・原題・年・種別・ジャンル・原語・監督・出演・評価） | 新規 |
| 7 | 他のサービスで探す | `otherServiceLinks()`（`search-links.ts`） |

> あらすじを読みに来ていない。答えを先に出す。

> ★ 7 の「他で探す」は**断定しない**現行の扱いをそのまま使う。
> U-NEXT / Hulu / DMM TV は在庫データを持っていないので検索リンクどまり
> （`search-links.ts` の冒頭コメント）。

## 6. 関連リンク（内部リンクの受け皿）

> **✅ 実装済み（2026-08-29）。** 組み立ては `src/lib/works.ts` の `relatedWorks()`、
> 描画は `src/pages/works/[id].astro` の「関連する作品」。
> **実測: 514/516枚に出て、作品ページ同士のリンクが 6,207本（1枚あたり12.0本）。リンク切れ0。**
> 監督の枠が出たのは123枚（監督が2作品以上を持つ作品だけ出るため）。

| 枠 | 中身 | 上限 |
|---|---|---|
| 同じ日に見放題が終わる作品 | 同じサービス・同じ日付 | **8件** |
| 同じ監督の作品 | Wikidata の監督が一致 | 6件 |
| 同じジャンルで終了予定の作品 | 同じサービス・同じジャンル | 6件 |

> ★ **上限を必ず置く。** 8月31日のように80本以上が同じ日に終わることがある
> （実測: U-NEXT のウルトラシリーズ13作を含む日）。
> 全部並べると、そのページはリンクの塊になる。
>
> ★ **作品ページがある作品にだけリンクする。** 1節の判定を通らない作品を混ぜると、
> 404 か「リンクの無い行」になる。判定関数を必ず通してから並べる。
>
> ★ **同じ作品を2つの枠に出さない**（実装時に足した決めごと）。
> 先に出た枠が勝つ。同じ題名が2度並ぶと、読者には
> 「同じリンクが増えている」ようにしか見えない。
>
> ★ **並びを実行のたびに変えない。** 既定は「評価の高い順 → 製作年の新しい順 → ID順」で、
> **最後に必ずIDを見る**（`byNotability()`）。ここが無いと、評価も年も無い作品どうしの
> 順が不定になり、ビルドのたびに差分が出る。
>
> ★ **関連を題名で引かない。IDで引く。**
> 同じ題名の別作品が別サービスに入ることがある（`work-links.ts` の `Entry` の注意書き。
> 実例「ディア・ファミリー」）。作品ページはIDで引くので当たらないが、
> **関連リンクを題名で組むとそこだけ再発する。**

## 7. 送り先とアフィリエイト（GROWTH 3-2）

### 変える前と後

```
現在:  記事の表 ──→ Netflix / Amazon（離脱）
        ↑ サイト内に戻る経路が無い

改善:  記事の表 ──→ /works/<id> ──→ そのサービスの作品ページ
                      │              ├→ Amazonで買う・借りる
                      │              └→ 他のサービスで探す
                      ├→ 同じ日に終わる作品
                      └→ 同じ監督の作品
```

### 変える場所は2か所だけ

| ファイル | 変更 |
|---|---|
| `src/lib/work-links.ts` | `WorkLink` に `pageUrl?: string` を足す。`toLink()` が、**その作品にページがあるときだけ**埋める |
| `plugins/rehype-work-links.ts` / `components/WorkTable.astro` | `href` を `pageUrl ?? url` にする |

`work-links.ts` が「送り先を決める唯一の場所」として作られているので、
**記事本文・常設ページの表の両方に、この1か所で効く。**

### アフィリエイトは切れない（確認済み）

| 仕組み | 内部リンクへの挙動 | 場所 |
|---|---|---|
| `rehype-affiliate` | `if (!isExternal(href)) return` — **何もしない** | `plugins/rehype-affiliate.ts:50` |
| `relFor()` | 内部リンクには `''` を返す | `src/lib/affiliate.ts` |
| `withAmazonTag()` | Amazon 以外は素通し | 同上 |

**`/works/…` に変えても `tag=` も `rel="sponsored"` も付かない。**
自サイトへのリンクに `sponsored` を付けるのは誤りなので、これが正しい挙動。
**追加の分岐は要らない。**

### 正直に見込んでおくリスク

**クリックが1回増えるので、短期的にはアフィリエイト成果が落ちうる。**
いまは「表の1行を押す＝サービスへ」が最短で、そこに1枚挟むことになる。

見返りは3つ。

- **508枚へのクロール経路。** これが無いと 3-1 は検索に載らない（記事以外に入口が無い）
- 作品ページ側で**送り先を並べられる**。いまは `resolveUrl` が1つに決め打ちしているが、
  「そのサービスで観る / Amazonで買う / 他社で探す」を同時に置ける
- 直帰が回遊に変わる

> ★ **切り戻せる形にしておく。** `toLink()` が `pageUrl` を返さないだけで元に戻る。
> GA4 で `/works/` からの外部クリックを見て、**1か月で判断する。**

## 9. 構造化データ

`Movie` / `TVSeries`（`work.type` で決める）。

## 14. 配信の記録（履歴）

> **✅ 実装済み（2026-08-29）。** 位置づけは [STOCK.md](./STOCK.md) の S-2。

### 何を出すか

`data/events/*.jsonl` に残っている**その作品のできごとを、古い順に並べた表**。

| 日付 | サービス | できごと | 判明した日 |
|---|---|---|---|
| 2026年8月23日 | Netflix | 見放題終了予定 | 2026年8月9日 |
| 2026年8月24日 | Netflix | 見放題配信が終了 | 2026年8月25日 |

上の「配信状況」が**いまどうなっているか**の1行なのに対して、
こちらは**いつ入って、いつ消えたか**。同じ素材から作るが役割が違う。

### なぜ作るか

終了済みのページ（実測388枚）は「もう観られない」しか言えず、
**公開した時点で用済みに近い**。履歴があると
「いつからいつまで観られたか」「他社で復活したか」を言えるページになり、
**収集を続けるほど行が増える**（[STOCK.md](./STOCK.md) 2節の「複利」）。

### 決めごと

| | |
|---|---|
| **1行しか無いときは節ごと出さない** | 上の「配信状況」と同じことを繰り返すだけになる |
| **重複の鍵はサービス・種別・日付** | 同じできごとを2回収集しても1行。二重に出ると履歴の信用が落ちる |
| **`foundAt` は最初の観測を残す** | 終了予定が何日前に判明したかを示す値。後の観測で上書きしない |
| **観測開始日を必ず添える** | それ以前の出入りは1件も持っていない。添えないと、観測していないことを主張することになる |
| **U-NEXT は入らない** | 作品ページ自体が配信API由来のみ（[GROWTH.md](./GROWTH.md) 2-3） |

**実測（2026-08-29）: 履歴の節が出たのは 68/516枚。**
観測が1か月ぶんしかないので今は少ない。**毎月増える一方で、減ることはない。**

★ 状態（`WorkState`）の言い回しと**混ぜないこと**。
履歴は「その日に何が起きたか」だけを言い、過去か未来かで言い換えない。
「配信中」に類する言葉は履歴にも書かない（4節の3つの禁止はここにも効く）。
