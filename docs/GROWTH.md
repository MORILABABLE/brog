## 0. 何が起きているか

**公開しているページは36枚しかない。**

| | 枚数 |
|---|---|
| 記事（`/posts/…`） | 11 |
| 常設の作品一覧（`/leaving/…` `/arrivals/…`） | 5 |
| 記事一覧（`/category/…` `/service/…`） | 15 |
| 固定ページ（about / contact / privacy / stats / index） | 5 |
| **合計** | **36** |

そして11本の記事はすべて「Netflix 配信終了 2026年8月」型の**ヘッドワード狙い**になっている。
この語は各サービス公式・映画メディア・大手まとめが押さえていて、
ドメイン評価の無い新規サイトが入る隙間はない。

**「見放題」で勝てないのは実力不足ではなく、当てている的が違う。**
ヘッドワードは月間検索数が大きいぶん、上位20サイトが全部同じ的を撃っている。
新規サイトが取れるのは**1件ずつの作品名**のような、
検索数は小さいが競合がほぼ居ない語の集合になる。

いま、その的に当てられるページが1枚も無い。

## 2. データの出どころと、出してよい範囲

**すべての施策がこの節に従う。ここを曖昧にしたまま面を増やさない。**

### 2-1. Streaming Availability API — 自サイトの読者に見せるのは明示的に許可

[TERMS.md](https://github.com/movieofthenight/streaming-availability-api/blob/main/TERMS.md) の原文:

> The API User shall use the streaming availability data ... **only for its application
> and/or websites' end-users, and consumers.** The API User shall not reshare/resell/
> redistribute ... **to other businesses or platforms** in any way, including but not
> limited to: offering APIs, offering access to databases, and offering data exports.

禁じているのは **B2B の再配布**。自分のサイトの読者に見せることは、まさに許可されている使い方。

- 作品ページを1,000枚作ってよい（読者向けの表示であって再配布ではない）
- **やってはいけないのは、JSON / CSV / API としての出力口を作ること**
  （`dist` に出してよいのは HTML と RSS とサイトマップだけ。現状もそうなっている）

### 2-2. Wikidata — CC0。制約なし

邦題・監督・キャスト・原語・製作会社は Wikidata 由来（`pipeline/sources/wikidata.ts`）。
（`origins.json` は P364 = original language。**製作国ではない**）
CC0 なので商用利用も再配布も自由。**人物ページ（3-3）が成立するのはこの性質による。**

### 2-3. U-NEXT — 規約に明言が無い。台帳として扱わない

U-NEXT は API の外側にあり、実ブラウザで公開ページを読んで取っている（[UNEXT.md 2節](./UNEXT.md)）。
robots.txt は `/browse/` `/title/` を許可しており、負荷対策も入れてあるが、
**取得したデータをどう使ってよいかについて、規約に明言が無い。**

明言が無いものは、こちらの解釈で広げない。**安全側の原則を1つだけ置く:**

> **`data/unext-titles.json` は収集を効率化するための内部状態であって、公開物の素材ではない。**

台帳は「どの作品ページを開き直すか」を決めるためにある（[UNEXT.md 3.2](./UNEXT.md)）。
これを公開ページの供給源にすると、回を追うごとに育つカタログを
そのまま公開し続ける形になり、[UNEXT.md 7-C](./UNEXT.md) の「危険side」に寄っていく。

#### 記事と常設ページで扱いを変える理由

| | 記事 | 常設ページ |
|---|---|---|
| URL | `2026-08-leaving-u-next` = **日付が入っている** | `/leaving/u-next` = 永続 |
| 中身 | 公開時点で固定。あとから増えない | ビルドのたびに入れ替わる |
| 性質 | **その月の断面**。読み物 | 常に最新のカタログ |

**同じデータでも、記事は「断面」に、常設ページは「台帳の写し」に近づく。**
だから U-NEXT は**記事だけ**でやる。

#### 決めたこと

| | 判断 |
|---|---|
| `/leaving/u-next` `/arrivals/u-next`（**常設の作品一覧**） | **作らない** |
| 作品ページ（3-1）に U-NEXT 由来の作品を載せる | **載せない** |
| 作品ページに「U-NEXTでも配信中」を併記する | **しない**（台帳を参照することになる） |
| U-NEXT の月次記事（`--service u-next`） | **続ける**。実装済み・断面として成立している |
| `/service/u-next` `/category/leaving/u-next`（**記事の一覧**） | **今のままでよい** |

> ★ **最後の行を取り違えないこと。** `/service/u-next` は既に公開されているが、
> あれは frontmatter の `tags` で**記事を拾う**ページで、作品データを1件も出していない。
> 出しているのは記事のタイトルと日付だけ。実装は `site/src/lib/service-pages.ts`。
>
> 一方 `/leaving/<service>` は `site/src/lib/events-data.ts` が**作品を直接読む**ページ。
> 名前が似ているが供給源がまったく違う。**この施策で分けているのは供給源のほう。**

> ★ 収集の側で「事実だけを取り、表現（あらすじ・キャッチコピー・画像）は取らない」と
> 決めてあることは前提として維持する（[UNEXT.md 4節](./UNEXT.md)）。
> この節が足すのは「**取った事実をどこまで出すか**」の線引き。

**「配信中」と断定しない**という現行の扱いを崩さない。

## 3. 施策（着手順）

### 3-1. 作品ページ `/works/<id>` — 最優先

> **✅ 実装済み（2026-08-27）。設計と実行結果は [WORK-PAGES.md](./WORK-PAGES.md)。**
> 第1弾は **508枚**（サイト全体で 36 → **544枚**）。
> 当初 620枚と見積もったが、厚みの条件にしていた「あらすじ」が
> **実測780件すべて英語**で日本語ページに出せず、条件を「監督 or 出演」に変えた。
> **記事からの内部リンク（3-2）はまだ張っていない**ので、入口はいまサイトマップだけ。

**36枚 → 650〜1,042枚。検索面が約20〜30倍になる。**

#### 何を狙うか

| 検索語の形 | 例 |
|---|---|
| 「〇〇 どこで見れる」 | ボリューム最大。競合は JustWatch / Filmarks |
| **「〇〇 いつまで Netflix」「〇〇 見放題 終了」** | **競合がほぼ居ない。ここが本命** |
| 「〇〇 配信」「〇〇 見放題」 | 上2つの派生で自然に取れる |

作品名は1件あたりの検索数が小さいが、**653件ぶん積み上がる**。
しかも「いつまで観られるか」を知りたい読者は、答えを見たら即座にサービスへ向かう。
**流入の質がヘッドワードより高い。**

#### h1 は作品名にしない

```
×  ボヘミアン・ラプソディ
○  「ボヘミアン・ラプソディ」はいつまで見られる？
```

作品名だけの h1 は、公式・Wikipedia・レビューサイトと同じ的を撃つことになる。
**答えられる質問をそのまま見出しにする**ほうが、勝てる語に当たる。

#### 出す範囲（品質ゲート。ここを外すと逆効果）

薄いページを1,042枚出すと、まとめて「クロール済み — インデックス未登録」に落ちる。
**段階的に出す。**

| | 対象 | 枚数 | 各ページが必ず持つ独自の事実 |
|---|---|---|---|
| **第1弾** | `expiring` / `removed` を持ち、監督か出演がいる作品 | **508**（実装済み） | **終了日または終了実績** |
| 第2弾 | 監督も出演も無いが原語がある作品（+67枚で575枚） | 残り | 年・ジャンル・原語 |
| 出さない | 上のどちらにも当たらない | — | — |

**第1弾から始めること。** 508枚すべてに「他所が持っていない事実」が1つ入るので、
最初のインデックス率がそのまま次の判断材料になる。

#### ページの中身（すべて既存データで組める）

- 配信状況の表 — サービス／状態（見放題中・終了予定・終了済）／**終了日**
- ポスター（100%）、年（100%）、ジャンル（日本語に訳す）、原語、監督、出演
- 既存の `otherServiceLinks()` で他社検索へ（**断定しない**現行の扱いを維持）
- **同じ日に終わる作品** / **同じ監督の作品** — 内部リンク（3-2 の受け皿になる）
- `Movie` / `TVSeries` の JSON-LD（3-7）

> ★ **終了済みの作品に「観られます」と書かせない。**
> `pipeline` 側の `MISLEADING_AFTER_END` と同じ考え方をページ側にも持たせる。
> 状態は3値（見放題中 / 終了予定 / 終了済）で、**文言をデータから決める**。
> 手書きの説明文を挟むと、ビルドのたびに古くなる。

> ★ **URL に作品名を入れない。** 邦題は Wikidata の解決率78%で、
> あとから邦題が付くと URL が変わる。作品IDで固定する（`/works/132442`）。
> 邦題は h1 と `<title>` に出す。

#### なぜこれが1番なのか

- **今日ある材料だけで作れる。** 追加の収集も API 消費も要らない
- `site/` の中で完結する。パイプラインを触らない
- U-NEXT を1件も使わない。2-3 の制約と競合しない
- 3-2 / 3-3 / 3-5 がすべてこのページを前提にしている。**ここが土台**

### 3-2. 記事の表の作品名を、内部リンクに向け直す

> **✅ 実装済み（2026-08-29）。** 判断は `src/lib/work-destination.ts` の1か所。
> **実測: 記事から279本・常設ページから128本**の内部リンクが生え、
> 作品ページ同士も6,207本で繋がった（[WORK-PAGES.md 6節](./WORK-PAGES.md)）。
> **内部リンクに `tag=` と `rel="sponsored"` は付いていない**（確認済み）。

> **設計は [WORK-PAGES.md 7節](./WORK-PAGES.md)。**
> アフィリエイトが切れないことは確認済み（`rehype-affiliate.ts:50` が内部リンクに触らない）。
> **短期的に成果が落ちうる**点と切り戻し方も同節に書いてある。

**タダで効く。3-1 とセットでやる。**

いま記事の表の作品名は `site/plugins/rehype-work-links.ts` が **全部を外部リンクにしている**
（Netflix / Amazon / U-NEXT の作品ページか、各社の検索）。
記事本文のリンクが**1本残らずサイトの外に出ている**。

| 起きていること | |
|---|---|
| 読者は表の1行を押した瞬間に離脱する | PV/セッション ≒ 1 |
| ページからページへ渡る経路が無い | **内部リンクが実質ゼロ** |
| クローラは記事11本を読んだら行き止まり | 新しいページが見つけられない |

作品ページができれば、**表の作品名は内部リンクにでき、
アフィリエイトリンクは作品ページの側に置ける。**

```
現在:  記事の表 ──→ Netflix（離脱）
        ↑ サイト内に戻る経路が無い

改善:  記事の表 ──→ 作品ページ ──→ Netflix / Amazon / 他社検索
                      ├→ 同じ日に終わる作品
                      └→ 同じ監督の作品
```

- SEO — 508枚へのクロール経路が記事から生える
- 収益 — 「1行押して離脱」が「作品ページで比較してから送る」に変わる。
  送り先を1つに決め打ちする必要も無くなる

> ★ **リンクを差し替える場所は `site/src/lib/work-links.ts` の `resolveUrl` 1か所。**
> あのファイルが「送り先を決める唯一の場所」として作られているので、
> 分岐を足すだけで記事本文・常設ページ・ポスターの3経路すべてに効く。
>
> ★ **アフィリエイトの計測が切れないこと**を必ず確認する。
> `tag=` と `rel="sponsored"` はビルド時に `rehype-affiliate` が付けている。
> 内部リンクには付いてはいけない（自サイトへの `sponsored` は誤り）。
> 付与の対象が外部リンクだけになっているか、実際の HTML で見る。

### 3-6. 再訪の仕掛け — ウォッチリスト

検索は入口だが、**純アクセスを底上げするのは再訪**。サーバー不要でできる。

- 作品ページに★。`localStorage` に作品IDだけ保存
- `/watchlist` で一覧。**終了7日前を赤く出す**
- サイトのタグライン「消える前に、気づける。」が、**初めて機能として成立する**

> ★ 保存するのは作品IDだけ。読者の情報をこちら側に持たない。
> `localStorage` は読めないことがある（プライベートウィンドウ等）ので、
> 必ず try/catch で包み、空でも正しく描画する。
>
> ★ **これは JS が要る2つ目の機能になる**（1つ目は `WorkSearch`）。
> サイトは基本 JS ゼロで作られているので、`/watchlist` と作品ページの★に閉じ込める。
> 一覧ページと記事ページにスクリプトを増やさない。

### 3-7. 構造化データ

`site/src/layouts/BaseLayout.astro` に JSON-LD の口はすでにある。足すもの:

| ページ | 型 |
|---|---|
| 作品ページ | `Movie` / `TVSeries` |
| 常設の作品一覧・記事一覧 | `ItemList` |
| 全ページ | `BreadcrumbList`（パンくずの HTML はあるが JSON-LD が無い） |

リッチリザルトが出るわけではない。**作品を実体として認識させるためのもの**で、
3-1 と 3-3 の紐付けを検索側に伝えるのが目的。単体では効果を測れないので、
3-1 と同時に入れて、以後は触らない。

### 3-8. 信頼性の面 —「当サイトの運営方針および活用について」（2026-08-29 実装）

`site/src/pages/guide.astro`。入口は**左の枠の最上段**（`LeftRail.astro` の1ブロック目）と
**フッター**の2か所で、全ページから1クリックで届く（2026-08-29 のビルドで557枚）。

書いてあるのは2つだけ。

- **画像の掲載方針** — 権利者が使用を認めていない画像・ポスターは載せない。
  提供を受けられない作品は自前の汎用画像になる（U-NEXT 由来の718件はすべてこれ）
- **「新着配信・終了一覧」の使い方** — 常設の一覧であること、作品を探す入力欄があること

■ なぜ施策の一覧に入れるか

3-1〜3-7 が「**的を増やす**」施策なのに対して、これは**サイトの評価そのもの**に効く枠。
作品の画像が汎用画像であることを説明せずに置くと、読者にも評価する側にも
「素材が足りていないサイト」に見える。方針として書けば、同じ状態が
**選んでそうしている**ことになる。
`/about`（運営者情報）が「誰が・どこから・どう作っているか」を引き受けているのに対して、
こちらは**読者が画面で気づくこと**だけを引き受ける。重なる話は書かず、末尾から `/about` へ送る。

■ 期待していないこと

**このページ自体の検索流入。** 「運営方針」で検索して来る読者はいない。
効くのは E-E-A-T の材料と AdSense 審査の側で、**単体では効果を測れない。**
5節の見方（インデックス枚数 → 表示回数 → クエリの形）には現れない種類の施策なので、
**数字が動いたときの原因候補にも入れないこと。**

## 4. やらないと決めたこと

| | 理由 |
|---|---|
| **U-NEXT の常設作品ページ** | 2-3。台帳の写しに近づく |
| **作品ページへの U-NEXT 併記** | 2-3。1行でも台帳を参照することになる |
| **JSON / CSV の出力口、作品データを返すエンドポイント** | 2-1 が明示的に禁止（`offering data exports`） |
| **全作品を横断する絞り込み・並べ替え UI** | カタログ検索サービスに近づく。[UNEXT.md 7-C](./UNEXT.md) の「危険side」 |
| **Hulu のデータ収集** | 利用規約 第3条(3) が自動アクセスを明示的に禁止（[SOURCES-UNEXT-HULU.md](./SOURCES-UNEXT-HULU.md)） |
| **あらすじを LLM に書かせて薄いページを埋める** | 誤情報。終了日・年・ジャンル・監督・出演だけで足りる |
| **邦題を URL に入れる** | 解決率78%。あとから付くと URL が変わる |

> `WorkSearch` の検索窓は**このリストに入らない**。
> あれは描画済みの行へ `scrollIntoView` するだけで、
> ページに出ている以上の情報を1件も提供していない（[UNEXT.md 7-C](./UNEXT.md) で確認済み）。

## 5. 効果の測り方

**3-1 の第1弾（508枚・2026-08-27 実装）を出したあと、Search Console で見るのはこの順。**

1. **インデックス登録済みの枚数** — 出した枚数のうち何枚が入ったか。
   ここが1〜2割で止まるなら品質ゲート（3-1 の出す範囲）を締める
2. **表示回数**（クリックではなく）— 検索結果に出ているか。
   表示があってクリックが無いなら `<title>` の問題で、ページの問題ではない
3. **クエリの形** — 「作品名＋いつまで／どこで」が出てくれば狙いどおり。
   出てこないなら h1 と `<title>` の当て方を変える

**GA4 の数字は最後に見る。** 流入が0の段階では、GA4 に見るべき差は出ない。

> ★ **1つずつ出す。** 3-1 と 3-3 と 3-5 を同じ週に出すと、
> どれが効いたのか分からなくなる。3-1 → 数週間 → 3-3 の順で、
> 間に Search Console の反応を挟む。
