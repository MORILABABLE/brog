---
description: 収集済みデータから記事を1本生成する（API課金なし・このセッションで執筆）
argument-hint: "[記事タイプ] [区分] 例: arrivals anime / special 007。省略時は一覧から選ぶ"
---

収集済みデータから記事を1本書く。**LLM APIは使わず、このセッションで執筆する**（課金の節約が目的）。

> **このコマンドは記事タイプごとの書き方を持たない。**
> 構成・文体・禁止事項は `data/draft/prompt.md` に埋め込まれて渡される。
> 記事の種類が増えてもこのファイルは変わらない。
> 記事を増やす手順は `theme-packs/<テーマ>/article-types/index.ts` の冒頭にある。

引数: `$ARGUMENTS`（1つ目が記事タイプ、2つ目が区分。どちらも省略可）

**特報・シリーズを書く場合は、引数が自由な指示になる。**「9月にNetflixで終わる007シリーズの特報」
「ウルトラマンのシリーズ記事」のように書きたい主題を渡してもらい、
下の「シリーズ記事を書く」「特報を書く」に従ってフラグへ翻訳する。

## 手順

### 1. 何が作れるかを見る

```
npm run write -- --list
```

「記事 / 素材件数 / 状態（未作成・作成済・素材なし） / スラッグ」が出る。

- **引数が指定されている場合**: その記事の行を見て、素材件数を確認してから進む
- **引数が無い場合**: 一覧をユーザーに見せ、**未作成で素材が多いもの**を提案して選んでもらう
- 素材が0件なら「先に `npm run collect` を実行してください」と伝えて終了する
- **素材が20件に満たない記事は、書く前にユーザーに確認する。**
  薄い記事を出すより、その月は見送るほうがサイトの価値を保てる
- `special`（特報）は「要指示」と出る。**素材件数は指示を決めるまで分からない**（下の「特報を書く」）

#### 「シリーズ候補」が出ていたら、必ずユーザーに伝える

一覧の下に**「シリーズ候補（サービスを横断して終わる作品群）」**が出ることがある。

```
  シリーズ候補（サービスを横断して終わる作品群）
  ------------------------------------------------------------------------
  ウルトラマン…              10作  U-NEXT / Amazon Prime Video  最短 8月14日
      ウルトラマンタロウ（HDリマスター版） / ウルトラマンレオ（HDリマスター版） / …
      npm run write -- --type series --topic "「?」シリーズ" --slug ? --match "ウルトラマン" --dry-run
```

**同じシリーズが2社以上で同時に終わっている、という意味。**
配信終了の月次記事は**サービス軸なので他社を混ぜられない**（`naming.md`）。
このままだと2本の記事に割れ、読者の「◯◯シリーズ、いつまで観られる？」に
**どちらの記事も答えていない**状態になる。横断してよいのは主題軸だけなので、
`series`（保存版）で1本立てられないかをユーザーに提案する。

- **`--topic` と `--slug` は人が決める。** 束の名前（先頭6文字）をそのまま主題にしない
  （`ウルトラマン…` → 主題は `「ウルトラマン」シリーズ`、スラッグは `ultraman`）
- 先に `--dry-run` で件数を確かめてから提案する
- **既にシリーズ記事がある束は候補に出ない**ので、出ているものは未着手と考えてよい

★ この一覧は**見放題終了の記事を `--emit` した直後にも出る**。
  そのときも同じように扱うこと（書き終えた気になって読み飛ばさない）。

### 2. プロンプトを書き出す

```
npm run write -- --type <記事タイプ> [--genre <ジャンル>] --emit
```

ジャンルの要否は記事タイプによる。`--list` の表記（`arrivals --genre anime` など）を
そのまま `--type arrivals --genre anime` に読み替えればよい。
必要なのに省くとエラーが有効な値を教えてくれる。

### 2a. シリーズ記事を書く（`series` のときだけ）

シリーズ記事は「◯◯シリーズは、いつまで見放題で観られるのか」に1本で答える**保存版**。
**この記事タイプだけURLにもタイトルにも月が入らず、配信状況が変わるたびに同じURLを書き直す。**

| フラグ | 必須 | 中身 |
|---|---|---|
| `--topic` | ● | 記事の主題。**タイトルと本文にそのまま出る**（例: `「ウルトラマン」シリーズ`） |
| `--slug` | ● | URL。半角英数字とハイフン。**月を入れない**（例: `ultraman`） |
| `--match` | ● | 作品名を絞る正規表現（例: `ウルトラマン`） |
| `--service` | | 1社に絞るときのキー。**ふつうは指定しない**（横断できるのがこの記事タイプの値打ち） |

```
npm run write -- --type series --topic "「ウルトラマン」シリーズ" --slug ultraman --match "ウルトラマン" --emit
```

★ **`--kind` は無い。** 「終了予定」「終了済み」「見放題に復帰」は
  **素材から自動で決まる**（`article-types/series.ts` の `stanceOf()`）。
  同じURLを何か月も書き直すので、人が選んだ値だけが古くなるため。
  タイトルの動詞句・リードの固定文言・記事のカテゴリがまとめて切り替わる。

★ 素材に **「見放題に復帰」** の行が混ざることがある。
  一度見放題から外れたあと、別のサービスで見放題に戻った作品。
  **終了日は無いので、表の終了日の欄は `—`**。
  「いつまで観られるか」を書くと推測になる（品質ゲートが止める）。

**書き出す前に、素材が何件になったかを必ず `--dry-run` で確認する。**
3件に満たないと生成が止まる（作品ページ2枚で足りてしまうため）。

### 2b. 特報を書く（`special` のときだけ）

特報は「ユーザーが明示的に作りたい時期・内容」を記事にするもの。
**構成も文体も品質ゲートも月次記事と同じ**で、違うのは素材の絞り方と、軸が主題であることだけ。

ユーザーの指示を次のフラグに翻訳する。**分からないものは推測せず聞く。**

| フラグ | 必須 | 中身 |
|---|---|---|
| `--kind` | ● | `new`=配信開始 / `expiring`=終了予定 / `removed`=終了済み |
| `--topic` | ● | 記事の主題。**タイトルと本文にそのまま出る**（例: `「007」シリーズ`） |
| `--slug` | ● | URL。半角英数字とハイフン（例: `007-netflix`）。日本語からは作れないので必ず決める |
| `--match` | | 作品名を絞る正規表現（例: `007|ジェームズ・ボンド`） |
| `--service` | | 1社に絞るときのキー（例: `netflix`） |
| `--from` / `--to` | | 対象期間 `YYYY-MM-DD`。省略すると対象月まるごと |

```
npm run write -- --type special --kind expiring --topic "「007」シリーズ" --slug 007-netflix --match "007" --month 2026-09 --emit
```

**`--match` / `--from` / `--to` のどれかは必ず要る。**
1つも無いとその月の全件になり、それは月次記事の担当なので生成が止まる。

**書き出す前に、素材が何件になったかを必ず確認する。**
0件なら `--match` が狭すぎるか、その時期に該当が無い。ユーザーに伝えて条件を見直す。
1〜2件しかない場合も、記事にするか確認する。

★ `--kind` を取り違えると記事の意味が反転する（「これから終わる」と「もう終わった」）。
  ユーザーの言葉が曖昧なら**必ず確認する**。品質ゲートも取り違えを止めるが、
  止まってから直すより先に確かめるほうが早い。

### 2c. 作品を下調べする（**ジャンル別・サービス別の記事では必ず**）

```
npm run research
```

`--emit` が書き出した素材の作品を、日本語版 Wikipedia で調べて `data/work-notes.json` に貯める
（1作品2.5秒。キーも課金も不要）。**そのあともう一度 `--emit` すると素材に入る。**

**なぜやるか**: 配信APIの素材は題名・年・ジャンル・出演者と英語のあらすじ1〜2文だけで、
これだけで書くと「◯◯が××する話です」で終わり、**その作品がなぜ好かれているのかが記事に出ない。**
作風・累計発行部数・受賞・シリーズの広がりは事実なので、調べて書けば推測にならない。

使い方の決まりは `templates/writing.md` 3節。**文章は写さず、事実だけを自分の言葉で書く。**
リサーチの行が無い作品は、素材の範囲だけで書く（無理に埋めない）。

### 3. 指示と素材を読む

`data/draft/prompt.md` を読む。以下が入っている。

- 記事の構成・文体・禁止事項（テーマパックのテンプレート）
- 今月そのまま使う固定文言
- 出力形式の指定
- 素材データ

**ここに書かれていることが正。** このコマンドの記述と食い違ったら prompt.md に従う。

### 4. 記事を書く

**`data/draft/response.md` に保存する。** 形式は厳密に守る。

```
TITLE: （30〜60文字）
DESCRIPTION: （60〜120文字・1行）
---BODY---
（Markdown本文。見出しは ## から）
```

frontmatter は書かない。日付・出典・カテゴリ・**ジャンル**はパイプラインが機械的に組み立てる。

> **ジャンル（`genre: 'anime' | 'western' | 'japanese'`）は軸がジャンルの記事だけに自動で付く。**
> いまは `arrivals`（`--genre anime` などで書くもの）が該当する。
> サービス別の記事には付かない（1本にアニメも洋画も邦画も入っていて、
> 1つのジャンルを名乗ると読者に嘘になるため）。**手で書き足さないこと。**
> ジャンル軸なのにジャンルが決まっていない場合は `--apply` が止まる。

**どの記事タイプでも共通して守ること**（品質ゲートで機械的に検査される）:

- **タイトルは `【{年}年{月}月】` で始める。** 初回も更新版も先頭は同じ。
  軸（サービス1社／ジャンル1つ／特報の主題）をどれか1つだけ名乗る。
  サービス別の記事に他社名を入れない。ジャンル別の記事にサービス名を入れない。
  2回目以降の版は**本数の直後**に `【9月12日更新】` を置く（`｜` より前）。

      初回　 【2026年9月】Netflixで見放題配信が終了予定の作品36本｜007シリーズ5作
      更新版 【2026年9月】Netflixで見放題配信が終了予定の作品42本【9月12日更新】｜追加は踊る大捜査線

  形の詳細は prompt.md の「記事の軸とタイトル」の節にある。**タイトルも品質ゲートが検査する。**
- 本文は**2,000字以上**（空白を除いた実質文字数）
- prompt.md の「今月そのまま使う固定文言」を**一字一句そのまま**使う
- **「★」の付いた注意書きは絶対に守る。** 素材データに書かれている:
  - `★邦題が未確認` → 与えられた原題のまま書く。日本語タイトルを推測しない
  - `★あらすじ未提供` → 話の筋を書かない。与えられた事実の範囲で書く
  - `★ローマ字のまま書くこと` → 人名を日本語表記に直さない
  - `★未定` → 日付を書かない
- 与えられた日付**以外の日付を書かない**。与えられていない作品を追加しない
- U-NEXT / Hulu / DMM TV について「配信中」と**断定しない**（配信状況のデータを持っていない）
- 記号は全角に統一する（`！` `？` `（）` を半角で書かない）

記事タイプ固有のルール（構成・締め方・扱ってよい範囲）は prompt.md の指示に従う。

### 4b. ショート動画の台本を書く（prompt.md に台本の節があるときだけ）

prompt.md の末尾に「ショート動画の台本」の節があれば、記事に続けて台本を書く。
**`data/draft/short.md` に保存する。`response.md` に混ぜてはいけない**
（混ぜると記事のパースが壊れる）。

```
NOTE: （この台本の軸を1行。記事のどの「まとまり」をフックにしたか）
---CUTS---
| # | ナレーション | テロップ | 補足 |
| --- | --- | --- | --- |
| 1 | … | … | … |
```

**フックは記事で見つけたまとまりをそのまま使う。** 別の切り口を新たに探さない。
30秒に載るのは4〜5本だけで、台本の役割は「まとまりを1つ見せて概要欄に送る」こと。

- 読み上げは**合計150〜170字**、1カット35字まで、カットは5〜7
- 最後のカットは残り本数を伝えてから「詳細は概要欄にて。」で終える
- **「台本に出してよい作品」に無い作品を出さない**（邦題が確定しておらず読み上げられない）
- 概要欄は書かない（記事URL・出典表記はパイプラインが組み立てる）

構成・禁止事項の詳細は prompt.md の台本の節にある。**そこに書かれていることが正。**

台本の節が無い記事タイプ（`ended` / `special`）では、この手順を飛ばす。

### 5. 検証して書き出す

```
npm run write -- --apply
```

品質ゲートで弾かれたら、指摘された箇所を `data/draft/response.md` で直して再実行する。
`--apply` は直前の `--emit` の記事タイプ・区分・対象月・特報のフラグを自動で復元するので、
引数を付け直す必要はない。

台本があれば同時に `shorts/<スラッグ>.md` に書き出される。
**台本の警告（`[台本/警告]`）は記事の公開を止めない。** 直せるものは直し、
直さない場合は理由を報告する。

### 5b. 画像を記事に入れる（**新しい記事を書いたら必ず**）

```
cd site && npm run sections -- --write
```

**これを飛ばすと、記事一覧・右の枠・追従枠のタイル画像が空になる。**

画像そのもの（`public/heroes/<スラッグ>.webp` など）は**ビルドが毎回作る**が、
`heroImage:` を frontmatter に書き込むのは `--write` を付けたこの1回だけ。
ビルド（`prebuild`）は `--write` を付けずに呼んでいる。
**ビルドが記事ファイルを書き換えるのを避けるため**で、この分担は変えない
（README「新しく記事を書いたときだけ」／`docs/APPEARANCE.md` 12節）。

- 何度実行しても結果は同じ。**忘れたと思ったら実行してよい**
- 本文のセクション画像（`## ◯月◯日…` の節）も同時に挿し込まれる。
  シリーズ記事は日付見出しを持たないので、入るのはヘッダー画像だけ
- 出力の「frontmatter ◯件を更新」が、いま書いた記事のぶん増えていることを確かめる

### 6. サイトのビルドを確認

```
cd site && npm run build
```

frontmatter のスキーマ検証もここで走る。通ればサイトに反映できる状態。

ジャンル記事なら、**記事ページの日付の左にジャンルのバッジ（アニメ／洋画／邦画）が出る。**
出ていなければ frontmatter に `genre` が入っていない。
値が `site/src/content.config.ts` の enum に無ければ、このビルドが落ちて教えてくれる。

## 報告

- 書いた記事（タイプ・区分。特報なら渡したフラグ）とタイトル、本文の文字数
- ジャンル記事なら、frontmatter に入った `genre` の値
- **その記事の独自性がどこにあるか**（見つけた「まとまり」など）
- 品質ゲートで警告が出た場合はその内容と、直したか直さなかったかの理由
- 台本を書いた場合は、**何を軸にしたか**と推定秒数。
  まとまりが弱く台本が成立しないと判断したなら、作らずにその理由を報告する
- **`heroImage` が frontmatter に入ったか**（手順5b。入っていないとカードの絵が空になる）

生成した記事のコミットとpushは**勝手に行わない**。ユーザーの判断を仰ぐ。
